## 0. 定版结论

采用 **Canvas 2D 主画布 + 离屏 raw WebGL2 人物画布**：现有场景、棋盘、特效与 HUD 继续走 Canvas 2D；人物由一张全视口透明 WebGL2 画布统一渲染，再在世界层合成。禁止引入 three.js/Cocos，禁止把背景和 UI 搬进 WebGL，禁止恢复 2D 人物帧作为运行时降级。

首轮 S1 只替换主角，敌方继续使用现有 2D 帧，目的是把正式运行时、CDN 缓存、动作、六向、合成和真机质量门一次打通。S2 再把敌方逐个换成 3D；接口从 S1 起按多角色设计，不写 hero 特判式死路。

当前正式战斗表现宿主仍是 `proto/battle_demo`，根 `game.ts` 仍消费旧 `ui/battle-render.ts`。S1 不借 2.5D 名义暗改整套微信战斗宿主：浏览器战斗页负责完整交互效果，微信小游戏使用独立 runtime smoke host 消费**同一份生产模块**完成真机门检。把 `battle-hex-render/session/input` 提升进根小游戏是后续独立接入卡，不与 S1 混单。

## 4. 坐标、六向与遮挡

### 4.1 单一坐标出口

`battle-hex-render` 先沿既有 `moveAnimDrawPosPx`、camera、`pieceHop` 算出人物脚底屏幕坐标，再组装 `CharacterRenderCommand`。创建 MoveAnim 时增加 `isJumpMove:boolean`，值从该次 `SnapshotActor.isJump` 锁定；当前演出有效期间 command.isJump 消费该值，演出结束/替换/死亡/重置时释放。没有有效 MoveAnim 时 command.isJump=false。这是保存已知意图，禁止从 hopPx、距离或坐标反推；session 的 300ms 快照窗口不延长，command 不再要求每帧等于原快照。3D pass 禁再次从 q/r 推屏幕坐标。此条为 seq=418 修订，替代 9e824cb5 的每帧直传要求。

像素补充（seq=418）：配置中的 `screenHeightPxAtReference` 为逻辑参考高；传入 pass 的运行时 profile 副本为物理参考高，由宿主统一乘一次 pixelRatio。保留 FE-B 现有桥接，禁止 pass 再乘一次。命令/投影使用物理像素，HUD 贴回除同一倍率。`renderer.beginFrame()` 已初始化 projection，同尺寸 resize 早退不构成投影缺陷；删除宿主 1×1 绕过及错误注释，按目标背衬直接创建。

WebGL 使用像素正交投影：`x_ndc=2*x_px/W-1`，`y_ndc=1-2*y_px/H`。模型地面锚对齐 `footX/footY`；3D jump 的 command.hopPx 恒0。人物参考高度沿既有 `PIECE` 定尺，禁止按模型 bbox 每帧自适应缩放。模型真实脚底随 root y 与骨骼姿态运动，不要求腾空期脚底仍贴地面锚。

jump 动作采样**只剥离 rootTrack 增量的 x/z，保留 y**：Root.translation=rest+[0,sampledY,0]，不得抹掉rest平移。竖直唯一来源为素材，经模型单位到屏幕像素的同一scale转换一次；3D jump 的 MoveAnim.hopHeight与command.hopPx均为0，不叠pieceHop、不逐帧脚底归零、不钳掉负y蹲姿。轻功判据继续取创建时锁定的isJumpMove，不能因hopHeight为0丢失jump。此条替代先前“全剥root、pieceHop唯一竖直”的规定，依据研发PM在seq=435及轻功口径handoff确认的消费规格；T30 F2仅作历史背景，不自动扩大到未迁移2D角色。

3D jump 的MoveAnim.duration固定1.5演出秒，动作与水平路径共用progress=clamp(elapsed/1.5,0,1)，不再消费按距离0.6–1.2s的jump时长；session逻辑格/300ms快照窗口保持。1×全局速度下墙钟1.5s；全局x2仍按既有演出钟同步加速（墙钟0.75s），禁止额外距离倍率。源jump_v6_1p5s有46个关键帧，首末时刻0和45/30=1.5s；单播采样fi=progress*(46-1)，按i0/i1正向插值，禁止用progress*46提前到尾。结束后从本次末姿（含y）混合到idle 180ms，不反播、不循环重启；死亡/reset/替换仍按既有演出释放规则。水平位移沿当前MoveAnim路径插值，禁止另建一条漂移轨。

### 4.2 六向

### 4.1.1 placed：随最终姿态平移的 HUD 布局框（seq=438，取甲）

`command.footX/footY` 是地面锚；`pass.placed` 是人物HUD布局框，两者不再混称脚底或精确像素bbox。pass在controller.sample完成（含交叉混合）后，用**该帧同一份最终pose**求Root相对rest的平移增量，经父节点变换与人物摆放矩阵的线性部分投影成屏幕物理像素delta。对现有水平清零、Y_UP且无额外父变换的主角，`deltaYpx=-scale*squashY*(poseRootY-restRootY)`；保留符号，负y蹲姿使布局框下移。存在父节点旋转/缩放时按实际矩阵求delta，不直接套简式。

`placed.top = baseTop + deltaYpx`、`placed.cx = baseCx + deltaXpx`，宽高沿既有稳定参考框（含死亡squash），不按逐帧衣摆/手脚bbox重定尺。baseTop为原放置框顶部，原hop仅对仍使用它的路径计一次；3D jump hop恒0。Root的rest位移不能重复计入。该补偿只用于placed：**人物矩阵/palette不再额外平移**，避免双抬升。

所有使用placed的HUD、攻钮、技能钮及热区由同一结果计算；宿主仍只除一次pixelRatio转回逻辑坐标，各消费者禁止自补root y。jump→idle的180ms混合、idle呼吸与其他clip均使用最终pose增量，不另采jump曲线、不根据state重算一份y；reset/换角色不残留上帧补偿。调试面明确标groundAnchor与hudLayout，不以placed.top+h量真实脚离地高度；脚底真实高度由渲染像素或专用几何锚测量。

验证：相同命令/固定参考框，比较保留root平移与清零root增量两份姿态，placed差值应等于同矩阵投影delta（≤1物理像素舍入误差）；正y/负y/0、起落、180ms混合中点、DPR1/2/3、死亡/reset均覆盖。真实“待输入+轻功”场景记录按钮圆心和命中框同帧同步，旧位误点不应命中新位按钮。正常渲染禁止每帧readPixels或CPU全网格蒙皮来求HUD框。

沿已验证出帧方向表冻结源视角：

| facing | source view yaw |
|---|---:|
| right | 270° |
| rightdown | 225° |
| rightup | 315° |
| left | 90° |
| leftdown | 135° |
| leftup | 45° |

运行时相机固定为正交相机；单位绕 Y 轴旋转为 `normalizeSigned(270° - sourceViewYawDeg[facing])`，即 right=0°、rightdown=45°、rightup=-45°、left=180°、leftdown=135°、leftup=-135°。禁止运行时镜像模型或负 scale。

### 4.3 层序

S1 只有主角是 3D。人物 pass 每帧先在透明离屏画布准备主角；既有 `drawPieces` 按 `depthKey` 排序遍历时，走到 hero 槽位只合成一次整张透明 WebGL canvas，因该 pass 仅含主角，仍可与前后 2D 敌人正确交错。HUD 的 `placed` 数据由 3D pass 返回，名字、血条、技能钮继续在 2D 层画。

S2 全员 3D 后，由 WebGL depth buffer 按 `depthKey` 给每个单位分配单调 Z；整张人物层在棋盘后、世界 FX 前合成一次。过渡期严禁同一角色同时画 2D 与 3D。

## 6. 资源、CDN 与缓存

### 6.1 清单策略

小型 profile 清单随代码发布，模型/动作 payload 走 CDN。`cdnBaseUrl` 由环境配置注入并进入微信 downloadFile 合法域名白名单；业务模块只持相对 `urlPath`。URL 必须内容版本化，例：`characters/hero/<sha12>/hero.glb`，禁止覆盖同 URL 内容。

进入战斗前执行：清单校验 → cache by SHA 命中 → 未命中下载临时文件 → `getFileInfo(digestAlgorithm='sha256')` 校验 → 原子登记为 last-known-good → 解析/上传 GPU。SHA 或 byteLength 不符立即删临时文件，禁止带病解析。

浏览器 adapter 使用 `fetch + crypto.subtle.digest`；微信 adapter 使用 `wx.downloadFile + FileSystemManager.getFileInfo/saveFile`。缓存索引只存 `{assetId, sha256, savedPath, byteLength, lastUsedAt}`，不存业务状态。

### 6.2 无 2D 降级时的失败行为

- 首次无缓存：自动重试 2 次（间隔 1s、3s）；仍失败则停在“角色资源加载失败”页，给显式重试，不进入战斗。
- 有 last-known-good 且清单 profile/schema 兼容：网络失败可使用旧 3D 内容；必须打 `stale-3d-cache` 诊断，不允许切 2D 帧。
- SHA 不符、GLB 结构不符、41 骨/1 primitive 不符：不使用该文件，也不覆盖 last-known-good。
- context lost：暂停人物提交但 session 继续保持；尝试重建一次并重传缓存资源。重建失败则暂停对局并显示错误，不让“隐形人物战斗”继续。

## 7. WebGL 管线与抗锯齿

沿 S0 基线：41 骨 palette 每单位每帧一次 `uniformMatrix4fv`，同一 VBO/IBO/texture/program 复用；20 单位就是 20 次 palette + 20 draw call，禁止 820 次 uniform 调用、UBO、骨骼纹理或实例化提前优化。

材质首版对齐 Leo 已认可观感台：纹理底色 + 环境光 2.15 + 方向光 1.15，方向 `(-0.4, 0.85, 1)` 归一；正交、无实时阴影、透明背景。色彩按 sRGB 采样→线性光照→sRGB 输出，避免裸 WebGL 把贴图洗灰。

抗锯齿策略固定为能力分支：

1. `gl.getContextAttributes().antialias===true`：直接使用 native MSAA，`edgeMode='native-msaa'`。
2. 实机返回 false：人物先渲到 RGBA8+depth FBO，再做一遍**alpha-aware FXAA**全屏 pass 输出到离屏 canvas，`edgeMode='fxaa'`。
3. FXAA 禁采透明区 RGB 造成黑边；所有采样和混合保持 premultiplied alpha。边缘对拍必须覆盖浅背景、深背景、头发和衣摆。

不采用盲目 1.25× 超采样：S0 的 20u 数据是在 1098×2400、renderScale=1 上取得，扩大内部缓冲会改变已证性能口径。FXAA 的新增成本须在 S1 真机重新测量。

## 10. 易错点清单

1. 把 41 骨写成每单位 41 次 palette 上传，制造 820 次 API 调用。
2. WebGL y 轴、Canvas y 轴和纹理 UV 翻转混在一起，人物倒置或 nonce 对拍假绿。
3. 用 q/r 在 3D 模块重新投影，镜头拖动和 moveAnim 出现双轨。
4. jump 同时消费 root y 与 `pieceHop`，高度翻倍。
5. 切 charge→strike 时重启 cast clip，造成动作抽搐。
6. 透明 FXAA 未按 premultiplied alpha 处理，浅底黑边。
7. 把请求的 `antialias:true` 当成实际启用，不读 `getContextAttributes()`。
8. 远程文件先覆盖 LKG 再验 SHA，下载损坏导致无可用回退。
9. S1 hero 3D 与旧 hero 帧/武器层同时画，形成重影。
10. 3D pass 返回的 placed bbox 与实际脚底不同源，HUD 和技能钮漂移。
11. 为“后续 App”直接引用 wx API；平台差异必须止于 adapter。
12. 把性能日志或表现 timeScale 接进 session/结算，破坏 UI 只展示红线。

## 11. 路线债务判断

- **现在最先爆**：CDN 冷启动失败路径、透明合成黑边、动作时钟与 moveAnim 双轨。S1 必须先锁这三项，不能先做材质花活。
- **未来 1 个月**：敌方 3D 化后，模型/贴图常驻内存、并发下载、全员深度排序和角色 profile 版本兼容会成为主债；S2 应引入有预算的 LRU 与整场预载，不把下载塞进战斗帧循环。
- **未来 2—3 个月**：武器/换装 attachment、不同骨架动作兼容、CDN 灰度与资源回滚会先于渲染算力成为维护瓶颈。attachment 从 S1 预留，但素材不过双门不启用。
- **App 阶段**：raw WebGL2 核心、profile、动画和缓存状态机可复用；宿主 canvas、下载缓存和生命周期只换 adapter。若未来要求原生渲染而非 WebView，再单独评估 GL/Metal 宿主，不在本方案承诺“零改移植”。

## 12. 架构决策记录

- 选 raw WebGL2，不选 three.js：S0 已验证我方最小栈，包体和微信兼容面可控，也更利于 App adapter。
- 选双 canvas，不选主画布全 WebGL：只有人物 3D，保留现有 2D 场景/UI 的收益远大于一次合成成本；S0 已证该合成链与 20u 容量。
- 选 FXAA，不选超采样：实机无 MSAA，FXAA 能显式补边且不改变 backbuffer 尺寸；超采样会让 S0 性能基线失效。
- S1 单主角、接口多角色：先控制改动面，同时避免下一批敌方接入时重写核心。
- 不做 2D runtime fallback：遵守 Leo 口径；以 LKG 3D、加载门和暂停错误页承担可靠性。
