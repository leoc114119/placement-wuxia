## 0. 定版结论

采用 **Canvas 2D 主画布 + 离屏 raw WebGL2 人物画布**：现有场景、棋盘、特效与 HUD 继续走 Canvas 2D；人物由一张全视口透明 WebGL2 画布统一渲染，再在世界层合成。禁止引入 three.js/Cocos，禁止把背景和 UI 搬进 WebGL，禁止恢复 2D 人物帧作为运行时降级。

首轮 S1 只替换主角，敌方继续使用现有 2D 帧，目的是把正式运行时、CDN 缓存、动作、六向、合成和真机质量门一次打通。S2 再把敌方逐个换成 3D；接口从 S1 起按多角色设计，不写 hero 特判式死路。

当前正式战斗表现宿主仍是 `proto/battle_demo`，根 `game.ts` 仍消费旧 `ui/battle-render.ts`。S1 不借 2.5D 名义暗改整套微信战斗宿主：浏览器战斗页负责完整交互效果，微信小游戏使用独立 runtime smoke host 消费**同一份生产模块**完成真机门检。把 `battle-hex-render/session/input` 提升进根小游戏是后续独立接入卡，不与 S1 混单。

## 4. 坐标、六向与遮挡

### 4.1 单一坐标出口

`battle-hex-render` 先沿既有 `moveAnimDrawPosPx`、camera、`pieceHop` 算出人物脚底屏幕坐标，再组装 `CharacterRenderCommand`。创建 MoveAnim 时增加 `isJumpMove:boolean`，值从该次 `SnapshotActor.isJump` 锁定；当前演出有效期间 command.isJump 消费该值，演出结束/替换/死亡/重置时释放。没有有效 MoveAnim 时 command.isJump=false。这是保存已知意图，禁止从 hopPx、距离或坐标反推；session 的 300ms 快照窗口不延长，command 不再要求每帧等于原快照。3D pass 禁再次从 q/r 推屏幕坐标。此条为 seq=418 修订，替代 9e824cb5 的每帧直传要求。

像素补充（seq=418）：配置中的 `screenHeightPxAtReference` 为逻辑参考高；传入 pass 的运行时 profile 副本为物理参考高，由宿主统一乘一次 pixelRatio。保留 FE-B 现有桥接，禁止 pass 再乘一次。命令/投影使用物理像素，HUD 贴回除同一倍率。`renderer.beginFrame()` 已初始化 projection，同尺寸 resize 早退不构成投影缺陷；删除宿主 1×1 绕过及错误注释，按目标背衬直接创建。

WebGL 使用像素正交投影：`x_ndc=2*x_px/W-1`，`y_ndc=1-2*y_px/H`。模型地面锚对齐 `footX/footY`；3D jump 的 command.hopPx 恒0。人物参考高度沿既有 `PIECE` 定尺（R2-3 起乘 `CHARACTER_3D_HERO_SCALE=0.78`，见 §4.4；派生口径不变），禁止按模型 bbox 每帧自适应缩放。模型真实脚底随 root y 与骨骼姿态运动，不要求腾空期脚底仍贴地面锚。

jump 动作采样**只剥离 rootTrack 增量的 x/z，保留 y**：Root.translation=rest+[0,sampledY,0]，不得抹掉rest平移。竖直唯一来源为素材，经模型单位到屏幕像素的同一scale转换一次；3D jump 的 MoveAnim.hopHeight与command.hopPx均为0，不叠pieceHop、不逐帧脚底归零、不钳掉负y蹲姿。轻功判据继续取创建时锁定的isJumpMove，不能因hopHeight为0丢失jump。此条替代先前“全剥root、pieceHop唯一竖直”的规定，依据研发PM在seq=435及轻功口径handoff确认的消费规格；T30 F2仅作历史背景，不自动扩大到未迁移2D角色。

3D jump 的演出时长、素材相位映射、水平通道与高度增益统一见 §4.1.2（v1.3 修订，替代本条原「固定 1.5 演出秒、动作与水平路径共用 progress」口径；「不再消费按距离 0.6–1.2s 的 jump 时长」与「禁止额外距离倍率」继续有效）。仍有效的原条文：单播采样 fi=φ×(46−1)（endpointInclusive），按 i0/i1 正向插值，禁止用 φ×46 提前到尾；结束后从本次末姿（含 y）混合到 idle 180ms，不反播、不循环重启；死亡/reset/替换仍按既有演出释放规则；水平位移沿当前 MoveAnim 路径插值，禁止另建一条漂移轨（§4.1.2 的水平通道是该路径插值的进度预映射，不是第二条轨）。session 逻辑格/300ms 快照窗口保持。

### 4.1.1 placed：随最终姿态平移的 HUD 布局框（seq=438，取甲）

`command.footX/footY` 是地面锚；`pass.placed` 是人物HUD布局框，两者不再混称脚底或精确像素bbox。pass在controller.sample完成（含交叉混合）后，用**该帧同一份最终pose**求Root相对rest的平移增量，经父节点变换与人物摆放矩阵的线性部分投影成屏幕物理像素delta。对现有水平清零、Y_UP且无额外父变换的主角，`deltaYpx=-scale*squashY*(poseRootY-restRootY)`；保留符号，负y蹲姿使布局框下移。存在父节点旋转/缩放时按实际矩阵求delta，不直接套简式。

`placed.top = baseTop + deltaYpx`、`placed.cx = baseCx + deltaXpx`，宽高沿既有稳定参考框（含死亡squash），不按逐帧衣摆/手脚bbox重定尺。baseTop为原放置框顶部，原hop仅对仍使用它的路径计一次；3D jump hop恒0。Root的rest位移不能重复计入。该补偿只用于placed：**人物矩阵/palette不再额外平移**，避免双抬升。

所有使用placed的HUD、攻钮、技能钮及热区由同一结果计算；宿主仍只除一次pixelRatio转回逻辑坐标，各消费者禁止自补root y。jump→idle的180ms混合、idle呼吸与其他clip均使用最终pose增量，不另采jump曲线、不根据state重算一份y；reset/换角色不残留上帧补偿。调试面明确标groundAnchor与hudLayout，不以placed.top+h量真实脚离地高度；脚底真实高度由渲染像素或专用几何锚测量。

验证：相同命令/固定参考框，比较保留root平移与清零root增量两份姿态，placed差值应等于同矩阵投影delta（≤1物理像素舍入误差）；正y/负y/0、起落、180ms混合中点、DPR1/2/3、死亡/reset均覆盖。真实“待输入+轻功”场景记录按钮圆心和命中框同帧同步，旧位误点不应命中新位按钮。正常渲染禁止每帧readPixels或CPU全网格蒙皮来求HUD框。

### 4.1.2 轻功演出重整：1.0s 窗 · 相位重映射 · 水平通道分离 · 正段高度增益（R2-1，v1.3）

依据：Leo 09-15 目验三症状（「还要往前挪一下再跳起来」「跳的好慢」「确实跳的不够高」，授权「你们看看怎么优化」）。实测基线（PM 像素复验 §4）：现窗 1.50s；素材 `jump_v6_1p5s` 弧线**前 ~40% 为深蹲（脚不离地）**、腾空只占相位 0.44~0.73；腾空峰值 47.5 逻辑像素（= 名义参考高 123.2 的 **0.386**；旧口径 113 像素含程序 hop 88）。素材 root y **峰对峰幅度** ≈43 逻辑像素——它是「蹲底 ↔ 弧顶」的跨度，**不是腾空高度，禁整体乘增益**；分段真值（施工方 CPU 蒙皮探针，`tasks/questions/Q3-T31-R2-轻功峰值判据冲突.md`）：**正段 +0.16655 模型单位 ≈20.9px、负段 −0.17658 ≈22.2px**（scale=123.2/0.98108=125.58 px/单位）。腾空峰值实测分解：k=1 → 41.2px（探针）/47.5px（PM 仪器），即「root 正段 ≈20.9px + 姿态收腿抬底 ≈20px（探针）/≈26.6px（PM 仪器口径）」。**不改素材、不改六向帧、不恢复程序 hop。**

**（1）演出窗（症状 B）**：`CHARACTER_3D_JUMP_MOVE_SEC` 1.5 → **1.0 演出秒**（x1 墙钟 1.0s；x2 沿既有演出钟同步 0.5s，禁额外距离倍率）。`progress = clamp(elapsed/1.0, 0, 1)` 仍是唯一墙钟进度。

**（2）相位重映射（症状 A 之时钟侧）**：素材相位 φ 与墙钟进度 p 解耦，按分段线性锚表映射；锚值全部进 `config/character-3d.ts`（禁散落渲染文件）：

| 墙钟 p | 素材相位 φ | 区段 |
|---|---|---|
| 0.00 | 0.00 | 起手 |
| 0.25 | 0.44 | 深蹲蓄势（素材 0~0.44）压缩进 0.25s |
| 0.75 | 0.73 | 腾空滞空（素材 0.44~0.73）扩展为 0.50s |
| 1.00 | 1.00 | 落地缓冲（素材 0.73~1）0.25s |

采样仍按 §4.1 zero-xz 条（只剥 root x/z、保留 y；endpointInclusive：fi=φ×45，正向插值）。

**（3）水平通道分离（症状 A 之位移侧）**：水平路径插值的进度参数改为 `h(p)`——p≤0.25 恒 **0**（深蹲期脚不离地即不得滑步，此即「先往前挪再跳」的根因修复）；0.25<p<0.75 取 `smoothstep((p−0.25)/0.5)`（水平位移只发生在腾空段，起跳/落地两端水平速度为零）；p≥0.75 恒 **1**（落地缓冲原地完成）。`MoveAnim` 创建时仅对 3D 轻功（`isJumpMove` 且 `hopHeight=0`）写入该通道与锚表；`moveAnimDrawPosPx` 为唯一消费点，镜头跟随与 command 的 footX/footY 自动同源。2D 角色（敌型）路径插值零改动。深蹲段不删——蓄势预备是跳跃可读性的核心，删除即成滑行瞬移。

**（4）高度增益（症状 C，口径变更；算术与取值经 Q3 裁定订正）**：arch 前口径「不加系数、沿素材」由本条废止（Leo 明确要更高）。在 zero-xz 采样上加**符号段增益**：素材 root y>0 段乘 `CHARACTER_3D_JUMP_Y_GAIN`，y≤0 段乘 1（**深蹲不加深**——加深蹲姿使身体先行下沉，与症状 A 的修正方向相悖）；y 过渡带 [0, 峰值×8%] 内线性渐入，防过零处速度折点。增益只作用正段 ⇒ 峰值随 k 线性、与负段无关：`峰值(k) ≈ 20.9·k + 姿态偏置（探针 ≈20px / PM 仪器 ≈26.6px）`。
**最终定版 k = 3.2**（Q3 裁定，判据带优先——Leo 指令是「不够高」，下调判据带无以对 39% 现基线交差）。预期读数：探针 ≈0.70、PM 像素仪器 ≈0.73~0.76（0.76=加性偏置模型 20.9×3.2+26.6=93.5px；0.73=线性斜率模型；两模型均带内）。§4.4 的 60% 比例下屏幕峰值 ≈54~56px、比例不变——增益作用于模型单位空间、先于 scale，与缩放正交。
**备选路线裁定**：「以蹲底为基线整弧 ×k」（Q3 丙）**不取**——重基线把深蹲中段位移塌向站立（探针复算：k=2 时 y=−0.09 → −0.0034，蓄势段视觉消失），且 y=0 的起末帧被抬离地面（悬空起跳/落地悬停）；「下调判据带至 [0.50,0.60]」**不取**——对 Leo「确实跳的不够高」（现 0.386）无法交代。

**（5）为何不双抬升、不与 placed/缩放互相干扰**：程序 hop 恒 0、pieceHop 不叠加（§4.1 原条保持，竖直唯一来源仍是素材 root y，增益只是对该来源的同源放大）；§4.1.1 的 placed 补偿读**同一份最终 pose** 求 Root 增量——增益在采样器一处生效，人物矩阵与 placed 两处消费者自动一致，不存在第二套时钟或第二次平移。落地缓冲由素材自身末段（相位 0.73~1）原地播放 + 既有 jump→idle 180ms 混合承担，不新增机制。

**（6）验收判据（机械，PM 像素仪器独立复测；逻辑像素、x1）**：
- 总窗：进度对墙钟斜率 ⇒ **1.00s ±0.02**；x2 ⇒ **0.50s ±0.01**。

### 4.1.3 特技/绝学表现窗固定 3s（R2-2，v1.3，Leo 已裁）

依据：Leo 09-15 原话「把整个特和绝的动画拉到 3s（如果原动作大于3s 则压缩时间，如果小于 3s则循环，不要改成动作的播放速度，这个交给后面的出招速度控制）」；>3s 分支已现场裁定**按窗压缩**（不取「裁切只播前 3s」）。本条不改动画资产、不改六向帧、不改 session 时间轴（charge=castDurationMs、strike=300ms 的 session 结构均保持）。

**（1）窗规则**：新常量 `HERO_3D_SKILL_WINDOW_SEC = 3.0` 演出秒（固定表现窗；**不设独立播放速度参数**）。charge 槽位把**整段源**映射进窗：源 >3s ⇒ 按窗压缩、在 3s 内播完一遍（现役 cast 源 4.5333s ⇒ 压缩比 0.662、等效速率 1.511×）；源 <3s ⇒ 循环填满 3s（1.5s 源恰 2 遍）。相位实现：charge `playWindowSec=3.0`、`loop=true`、`stateElapsed` 派生（phase=(elapsed/3)%1）。原 `HERO_3D_CAST_CYCLE_SEC`（840ms 一轮，等效 5.4× 加速）与 `HERO_3D_STRIKE_WINDOW_SEC`（280ms）**废止**，实现卡删除其定义与全部消费。

**（2）strike 槽位改「末姿保持」**：窗 3.0s 与 charge 态等长（现役默认档 castDurationMs=3000ms），charge 结束时源已播完 ⇒ strike（t1 后 300ms）不再从 2/3 起播重扫（原口径该段等效 **5.4×** 加速——末 1/3 段 4.5333/3≈1.511s 压进 280ms；与 charge 整段 5.4× 数值巧合相等，因 0.84=3×0.28 且 strike 段恰为整段 1/3，**并非同一段材料**；v1.3 曾误写 10.8×，Q3 复核订正），是「还是加速播放」观感的组成部分，改为**末姿保持至状态退出**（startRatio=1 ⇒ phase 恒 1），随后既有 100ms 混合回 idle。既有 2D directional 分支的 cast2→3 帧语义不变——本条只改 3D 槽位。

**（3）关系界定**：
- **x1/x2 全局倍速**：沿既有演出钟同步缩放（x2 墙钟整遍 1.5s），无额外倍率，与 §4.1 同一口径。
- **300ms 快照窗 / `isJumpMove` 演出锁**：无交互。技能演出相位由 `stateElapsedSec` 派生，不建 MoveAnim、不占轻功闩锁；300ms 窗仍是 isJump 专用。
- **session 时间轴**：零改动。现役默认档 castDurationMs=3000ms 与本窗数值相等属**巧合不是耦合**——两常量独立演化，禁止互相推导（易错点 16）。
- **T25 光影 / T26 名条**：不动（光影时长仍=castDurationMs；名条恒 1.000s，禁随窗缩放）。

**（4）后续「出招速度」系统接缝**：`types.ts` 的 `CharacterRenderCommand` 预留**可选**字段 `stateWindowSec`（本批只留契约条文，不实现）：出招速度系统上线时由宿主从 presentationCasts 注入 `finishAtSec−startedAtSec`，charge 槽位窗源由常量切到该字段（字段缺省回退常量），`HERO_3D_SKILL_WINDOW_SEC` 退化为 fallback。**前置条件**：接缝切换完成前，任何 castSpeed 非默认档的技能入库都会造成 3s 窗与 charge 态时长失配（源被截断 + 末姿跳变），须先触发接缝再入库。

**（5）验收判据（机械）**：
- charge 态整遍源播放 = **3.00s ±0.05**（x1；按 activeClipKey=cast 的相位 0→1 斜率仪器测）；x2 ⇒ **1.50s ±0.03**。
- 窗内相位单调递增，**无 840ms 周期回卷**（旧口径回归断言）。
- strike 态 300ms 内相位恒 1（末帧帧索引不变，无重扫）。

## 6. 资源、CDN 与缓存

### 6.1 清单策略

小型 profile 清单随代码发布，模型/动作 payload 走 CDN。`cdnBaseUrl` 由环境配置注入并进入微信 downloadFile 合法域名白名单；业务模块只持相对 `urlPath`。URL 必须内容版本化，例：`characters/hero/<sha12>/hero.glb`，禁止覆盖同 URL 内容。

进入战斗前执行：清单校验 → cache by SHA 命中 → 未命中下载临时文件 → `getFileInfo(digestAlgorithm='sha256')` 校验 → 原子登记为 last-known-good → 解析/上传 GPU。SHA 或 byteLength 不符立即删临时文件，禁止带病解析。

浏览器 adapter 使用 `fetch + crypto.subtle.digest`；微信 adapter 使用 `wx.downloadFile + FileSystemManager.getFileInfo/saveFile`。缓存索引只存 `{assetId, sha256, savedPath, byteLength, lastUsedAt}`，不存业务状态。

### 6.2 无 2D 降级时的失败行为

- 首次无缓存：自动重试 2 次（间隔 1s、3s）；仍失败则停在“角色资源加载失败”页，给显式重试，不进入战斗。
- 有 last-known-good 且清单 profile/schema 兼容：网络失败可使用旧 3D 内容；必须打 `stale-3d-cache` 诊断，不允许切 2D 帧。
- SHA 不符、GLB 结构不符、41 骨/1 primitive 不符：不使用该文件，也不覆盖 last-known-good。
- context lost：暂停人物提交但 session 继续保持；尝试重建一次并重传缓存资源。重建失败则暂停对局并显示错误，不让“隐形人物战斗”继续。

## 7. WebGL 管线与抗锯齿

沿 S0 基线：41 骨 palette 每单位每帧一次 `uniformMatrix4fv`，同一 VBO/IBO/texture/program 复用；20 单位就是 20 次 palette + 20 draw call，禁止 820 次 uniform 调用、UBO、骨骼纹理或实例化提前优化。

材质首版对齐 Leo 已认可观感台：纹理底色 + 环境光 2.15 + 方向光 1.15，方向 `(-0.4, 0.85, 1)` 归一；正交、无实时阴影、透明背景。色彩按 sRGB 采样→线性光照→sRGB 输出，避免裸 WebGL 把贴图洗灰。

抗锯齿策略固定为能力分支：

1. `gl.getContextAttributes().antialias===true`：直接使用 native MSAA，`edgeMode='native-msaa'`。
2. 实机返回 false：人物先渲到 RGBA8+depth FBO，再做一遍**alpha-aware FXAA**全屏 pass 输出到离屏 canvas，`edgeMode='fxaa'`。
3. FXAA 禁采透明区 RGB 造成黑边；所有采样和混合保持 premultiplied alpha。边缘对拍必须覆盖浅背景、深背景、头发和衣摆。

不采用盲目 1.25× 超采样：S0 的 20u 数据是在 1098×2400、renderScale=1 上取得，扩大内部缓冲会改变已证性能口径。FXAA 的新增成本须在 S1 真机重新测量。

## 11. 路线债务判断

- **现在最先爆**：CDN 冷启动失败路径、透明合成黑边、动作时钟与 moveAnim 双轨。S1 必须先锁这三项，不能先做材质花活。
- **未来 1 个月**：敌方 3D 化后，模型/贴图常驻内存、并发下载、全员深度排序和角色 profile 版本兼容会成为主债；S2 应引入有预算的 LRU 与整场预载，不把下载塞进战斗帧循环。
- **未来 2—3 个月**：武器/换装 attachment、不同骨架动作兼容、CDN 灰度与资源回滚会先于渲染算力成为维护瓶颈。attachment 从 S1 预留，但素材不过双门不启用。
- **App 阶段**：raw WebGL2 核心、profile、动画和缓存状态机可复用；宿主 canvas、下载缓存和生命周期只换 adapter。若未来要求原生渲染而非 WebView，再单独评估 GL/Metal 宿主，不在本方案承诺“零改移植”。

## 12. 架构决策记录

- 选 raw WebGL2，不选 three.js：S0 已验证我方最小栈，包体和微信兼容面可控，也更利于 App adapter。
- 选双 canvas，不选主画布全 WebGL：只有人物 3D，保留现有 2D 场景/UI 的收益远大于一次合成成本；S0 已证该合成链与 20u 容量。
- 选 FXAA，不选超采样：实机无 MSAA，FXAA 能显式补边且不改变 backbuffer 尺寸；超采样会让 S0 性能基线失效。
- S1 单主角、接口多角色：先控制改动面，同时避免下一批敌方接入时重写核心。
- 不做 2D runtime fallback：遵守 Leo 口径；以 LKG 3D、加载门和暂停错误页承担可靠性。

R2 增（v1.3）：
- R2-1 选「相位重映射＋水平通道分离＋正段增益」，不选素材子区间（裁掉深蹲/落地段会丢蓄势预备与缓冲，动作变成滑行瞬移；且需重导资产、周期长），不选恢复程序 hop（v1.1 已证「程序抛物线 × 动作弧线」双时钟打架正是原根因，回潮即复发）。增益只作用于正 y 段：全段乘系数会把深蹲也加深一倍，观感变「扎猛子」。
- R2-2 选「固定 3s 窗＋源整段映射＋strike 末姿保持」：>3s 按窗压缩是 Leo 已裁；压缩比 0.662 接近原速、远优于旧 5.4× 加速（charge 840ms 循环与 strike 280ms 重扫同为 5.4×，巧合相等非同段材料）；不设速度参数，接缝（stateWindowSec 预留）留给出招速度系统。
- R2-3 选「单参数 ×0.6＋朝向门归一化一次到位」：派生链全自动，无双算点；朝向门改归一化判据后成为尺度不变量，后续任何比例调整不再破门。

总研发工时 **30h（中置信，不含 PM/主架构复核与 Leo 真机等待）**。建议按 A/B/C 三卡串行发，不合成一张 30h 大卡。

### 13.2 风险与缓解

1. 增益过零折点：正段 ×2 在 y 过零处速度跳变 → 过渡带线性渐入化解；验收含起跳段无顿挫目验。
2. charge 3s 末相位回卷 × 100ms 交叉淡化：t1 前相位 ~0.99 回卷向 0，淡化源可能闪起手姿 → 淡化源相位在回卷处夹持到 1（实现细则，随卡验证）；known-minor，Leo 目验若可感知再升级处理。
3. 固定 3s 与 castDurationMs 失配（出招速度系统落地后）：接缝 §4.1.3(4) 已定，前置条件已明文。
4. 敌我同屏比例：主角 73.92px vs 2D 敌按 PIECE 定尺不变 → 观感差待 Leo 目验裁（§13.4-3）。
5. 归一化朝向门余量 1.45×：PM 复测抖动若吃掉余量 → 启用第二判据 fallback（§4.4）。
6. 【Q3】峰值判据的双仪器读数差（探针 vs PM 像素仪器，k=1 实测差 6.3px）：判据钉死 PM 仪器口径，探针仅预检；「×1.153 恒定比值」系 n=1 外推不作数（仪器差异物理上是边缘阈值造成的近似恒定像素偏置）。k 备案三档全部预验落带，单点仪器抖动由偏离处置吸收（§13.4-1）。
