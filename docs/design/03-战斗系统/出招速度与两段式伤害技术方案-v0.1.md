# 出招速度与两段式伤害技术方案 v0.2

> 分类：03-战斗系统 · 性质：研发施工蓝图（不改需求文档、不写游戏代码）
> 依据：《出招速度与两段式伤害需求文档》v1.3（2026-09-07，Leo 三裁）、《武功数据 schema》v0.2 `a9e1502`、《战斗交互行为规格》v2.4、现行 `systems/battle-session.ts` / `systems/battle-core.ts` / `types.ts`
> 状态：🔶 待研发线 PM 需求符合性审阅 → 通过后拆 BE/FE 卡
> v0.2 修订：采用 AS-6 动态目标语义；补齐施法者死亡消散边界、终局结算/表现分离、AS-6/SP-2 用例与工时。

## 1. 方案结论

### 1.1 定版主张

1. **技能从“提交即结算”改为“提交即排程、两个时刻结算”**。第一段在招式时长结束（落地起点）结算，第二段在 300ms 收招窗口结束结算；普攻仍在提交时单段结算。
2. **采用单一逻辑时钟 + 每个施法者一个 pending cast**。行动条继续按现有 tick 填充，提交时照 BAR-3 清零；活体施法中的单位不能再次取得行动权，但其他单位照常行动。
3. **AOE 在 t1 动态重搜一次**。t0 只保存**施法者提交时所在格（R1）**与 `rangeShape`；到 t1 以该格为锚重算范围，在当前 `all` 顺序中取存活敌人并保存为目标集。t2 不重搜，只从该集合剔除已死亡者。玩家点击格仅作受理/演出朝向，不改变 AOE 锚。
4. **施法者死亡使招式消散**。死亡判定提交的同一时点立即撤销 pending cast；未结算段不再掷骰、不写血量、不发 `skill/miss`。无打断边界只适用于活体施法者。
5. **伤害判定仍由 battle-core 的 F-04 链产生**。新增“技能伤害段”纯函数，传入 `damageRatio=0.5`；session 只负责排程、扣资源、写血量和转发既有事件，禁止复制命中、闪避、暴击或取整公式。
6. **终局分为结算态与表现态**。某个目标伤害使一方胜利/失败后，立即停止所有后续结算与新增伤害事件；FE 保留当前施放/收招表现帧至其 `finishAtSec`，表现不再改血量或发事件。
7. **事件契约零新增**。两段分别发既有 `skill` / `miss` 事件；命中带 `targetId`、`damage`，miss 带 `targetId`、`damage=0`。t1 空搜只发一条无目标 `skill`，不安排 t2 空事件。

### 1.2 需求真源与版本边界

本方案以需求文档 v1.3 的 AS-1～AS-9 为唯一业务口径：AS-1 使用 `3000 ÷ min(6, 武功出招系数 + 内功加成速度)` 的加法模型；AS-4 收招窗固定 300ms；AS-6 为 t1 动态重搜；AS-6b 为施法者死亡消散；AS-9 为终局停结算、FE 播完表现。v0.1 中“提交时 AOE 快照”“施法者死亡仍结算”“终局只丢未来队列”的文字全部作废，不得带入施工卡。

## 2. 数值与输入契约

### 2.1 出招时长

每次技能提交取得当前成长域快照值：

```text
skillSpeed    = skill.castSpeed ?? 0.8
internalSpeed = actor.internalCastSpeed ?? 0.2
speedSum      = min(6, skillSpeed + internalSpeed)
castDurationMs = 3000 / speedSum
```

- `3000`、`6`、`0.8`、`0.2` 是 MVP 口径；封顶得到最短 500ms，不再另写第二个 `max(500ms, …)` 分支。
- `castSpeed` 是武功当前等级产生的个体差异快照；session 不读 `level` 推导成长曲线。`internalCastSpeed` 由内功/成长域提供，不能塞进 `SkillDef`，也不能由 session 读取 `neigongLevel` 反推。
- 两个输入必须是有限数；`skillSpeed > 0`、`internalSpeed >= 0`。缺失使用 MVP 默认，显式非法值在装配入口 fail-fast。

### 2.2 收招窗口与普攻表现

- `finishWindowMs = 300`，复用现有 `CHOREO.strikeSec=0.3` 的秒/毫秒换算；BE 与 FE 引用同一共享常量，`battle-hex` 只作别名，BE 不反向依赖 UI config。
- 普攻伤害和 F-04 判定不受出招速度影响；普攻帧表现时长为 1000ms，只改表现计时，不延迟普攻事件或血量。

### 2.3 两段伤害取整

每段独立计算并独立 `floor`：

```text
segmentDamage = floor(max(atk - def, 1) × skill.grade × 0.5 × (crit ? 1.5 : 1))
```

两段之和允许与整次伤害再除二相差 1 点；session 不补差，也不把余数塞到第二段。

## 3. 运行时状态机

### 3.1 时间线

设接受提交的逻辑时刻为 `t0`，`t1=t0+castDurationMs/1000`，`t2=t1+0.3`：

| 时段 | session 状态 | 演出/结算 |
|---|---|---|
| `t0` | `pendingCast.phase='casting'` | 校验通过；扣一次内力、写一次冷却、BAR-3 清零、清选中；保存施法者提交时所在格（R1）与 `rangeShape`；施法者进入 `charge` |
| `[t0,t1)` | 施法锁定 | 施放帧整套循环；活体施法不被伤害打断；行动条继续 tick，但该 actor 不参与 ready 轮转 |
| `t1` | `phase='finish'` 或消散 | 先按 §3.3 重搜并固定目标集；空集发一条无目标 `skill` 并结束结算；非空集逐目标结算第一段；第一段致死立即检查终局 |
| `[t1,t2)` | 收招窗口 | 活体施法者播 `strike`；其他单位照常行动。若施法者在此期间死亡，pending cast 立即消散，第二段不再进入结算 |
| `t2` | 清理 pending | 不重搜；对 t1 保存的存活目标按原序逐个结算第二段，死者跳过且不消费 RNG；处理完成切 `idle`，释放施法锁。终局后该步只保留 FE 表现 |

`t1/t2` 即使落在一次较大的 `tick(dt)` 中，也按 `dueAt → castSeq → segment → targetOrdinal` 边界 drain；事件 `t` 写各自 `dueAt`，不是 tick 结束时刻。主循环仍采用现有 `dt≤0.05s` 上限，session 对更大 dt 也必须等价切分，不能漏段。

### 3.2 施法者死亡与终局边界

- 所有造成 HP 变化的路径在“写入 HP → 标记 `dead`”的同一事务内调用 `cancelPendingCastOnDeath(actorId, deathAtSec)`。该函数先从结算队列移除 t1/t2，标记 `settlementState='dissipated'`，不产生任何额外 `skill/miss` 事件；然后才允许 scheduler 处理下一个 due 项。
- 因而：死亡发生在 t1 前，t1 重搜和两段均不存在；死亡发生在 t1 后、t2 前，第一段已保留但第二段被撤销；死亡发生在 t2 结算中，则当前目标已经完成的段保留，后续目标/段不再开始。
- 同一逻辑时刻的 cast 段仍按 §5 的 `(dueAt, castSeq, segment)` 顺序处理。较早 `castSeq` 的伤害若先致死另一施法者，后者轮到时读取 `dead` 并消散；不会出现“同刻已死仍重搜/结算”。
- `terminal` 在每个目标伤害提交后立即检查。若胜负成立，停止当前段剩余目标、同刻剩余 cast 段及未来 settlement queue；不再产生任何伤害、miss 或 skill 事件。
- 终局只停止结算，不强制剪掉 FE 表现：保留已接受 cast 的 `finishAtSec`，在 `finishWindowMs=300` 内继续播放施放/收招帧；这些帧是纯视觉，不得写 HP、掷 RNG 或发事件。施法者死亡则由既有 `dead` 视觉覆盖，不恢复施法动画。

### 3.3 t1 动态 AOE 重搜算法

`PendingCast` 在 t0 不保存目标 ID，只保存**施法者提交时所在格（R1）** `anchorCell` 和技能 `rangeShape`。t1 到达时，执行一次且仅一次：

```text
resolveT1(cast, t1):
  if terminal || !alive(cast.actorId): dissipate(cast); return
  cells = projectRange(anchor=cast.anchorCell, shape=cast.rangeShape)
  ids = all.filter(e => alive(e)
                    && enemyOf(e, cast.actorId)
                    && cells.has(e.cell)).map(e => e.id)
  cast.targetIds = ids                 // 保留 all 顺序，不按坐标或 ID 排序
  cast.t1Resolved = true
  if ids.length === 0:
    emitAt(t1, {type:'skill', actorId, skillId})
    finishSettlement(cast, noTarget=true) // 不安排 t2 结算/空事件
    return
  resolveSegment(cast, segment=1, at=t1)
```

- `projectRange` 必须调用 ATK-2/现有范围 helper 的同一实现：锚点是**施法者 t0 提交时所在格（R1）**，不是玩家点击格，也不是施法者当前格；形状使用技能当时冻结的 `rangeShape`。
- 搜索读取 t1 的当前站位。因此，敌人在 t0 在圈内但 t1 已走出会被排除；t0 圈外而 t1 走入会被纳入；t1 后再走位不改变集合。
- `all` 是唯一确定性顺序来源；不做坐标、距离、ID 二次排序。目标集一旦保存，t2 只做 `alive(targetId)` 过滤；死者不消费 RNG，存活者按相同数组顺序结算。
- 空放仍扣资源、保留施放/收招表现；t1 只发一条无 `targetId/damage` 的 `skill`，不退款、不发 t2 事件。

### 3.4 入口与状态收敛

- `cast`、`attack(skillId)`、AI `planSkill` 都只能调用同一 `scheduleSkillCast`；玩家/AI 共用 t1 搜索、段结算和 RNG 路径。
- `attack(skillId)` 的兼容入口保留其点击单目标契约；若调用的是 AOE 技能，必须由已统一的 ATK-2 范围入口提供点击格（仅受理/演出）与 `rangeShape`，AOE 锚仍取施法者 t0 自身格，不得偷偷退回“立即单目标结算”。普攻 `attack(skillId=null)` 仍走既有 `doAttack`。

## 4. 接口与模块落点

### 4.1 最小类型增量（施工时落到 `types.ts`）

```ts
interface SkillDef {
  // ...existing fields
  castSpeed?: number;             // schema v0.2；旧技能缺省 0.8
}

interface CombatantInput {
  // ...existing fields
  internalCastSpeed?: number;     // 成长域快照；不读 level 反推
}

interface PendingCast {
  castSeq: number;                // session 内单调递增
  actorId: string;
  skillId: string;
  anchorCell: HexCell;            // t0 施法者提交时所在格（R1），t1 的 AOE 锚；点击格不入锚
  rangeShape: RangeShape;         // t0 冻结，t1 只重算一次
  targetIds: string[] | null;     // t1 写入，保留 all 顺序
  startedAtSec: number;
  landAtSec: number;
  finishAtSec: number;
  phase: 'casting' | 'finish';
  t1Resolved: boolean;
  settlementState: 'pending' | 'resolved' | 'no-target' | 'dissipated' | 'terminal-canceled';
}
```

`targetIds=null` 表示尚未到 t1，不能被施工代码当成空集合；空集合只有 t1 已执行后才写 `[]`。如实现需要继续播视觉，在结算 pending 删除后保留只读 `presentationCast`，不得复用已消散 cast 进行结算。

### 4.2 battle-core

新增不扣资源、不改 actor/target 的段结算函数：

```ts
resolveSkillSegment(
  actor: ActionActor,
  target: ActionActor,
  skill: SkillDef,
  damageRatio: 0.5,
  rng: Rng,
): { kind: 'skill' | 'miss'; damage: number; crit: boolean; missed: boolean }
```

函数内部复用 F-04 命中→闪避→暴击→破防→取整顺序；既有 `resolveAction` 签名和普攻路径不动。`castDurationMs`/`effectiveCastSpeed` 也由 core 纯函数提供，云端 `settle/core.js` 继续是正式数值真源，客户端只读展示。

### 4.3 battle-session scheduler

在 `createHexBattle` 闭包内增加 `pendingCasts`、`nextCastSeq` 与（如 FE 需要）只读 `presentationCasts`：

- `scheduleSkillCast(actor, skill, facing, faceTo)`：唯一资源扣除、冷却写入、BAR-3、`setAnim('charge')`、入队；在入队时从 actor 当前格复制 `anchorCell`（R1），不得在 t0 搜索或写 `targetIds`。`faceTo` 仅为点击格演出朝向。
- `drainDueCasts(now)`：按 §5 comparator 取 due 项；段 1 先执行存活检查与 t1 重搜，段 2 只读取保存集合；每个目标伤害后检查死亡/终局。
- `applyDamage` 的死亡回调必须同步调用 `cancelPendingCastOnDeath`；取消发生在 scheduler 取得下一个队列项之前。
- `pendingCasts.has(actor.id)` 作为 ready/AI/手动提交门。施法中 bar 可 clamp 到 100，但不重复发 `bar-max`；pending 清除后下一轮再按 BAR-2 发一次。

建议 `tick` 可观察顺序：

1. 推进逻辑时钟、行动条和现有移动/非施法动画；
2. drain 所有 `dueAt <= t` 的 cast 段（段内即时死亡/终局检查）；
3. `checkEnd()` 兼容普通行动路径；
4. 过滤 `!pendingCasts.has(actor.id)` 后运行 BAR-2 ready 队列和 AI/手动动作；
5. 到达 90s 再走既有 timeout。

### 4.4 FE、共享常量与宿主

- 共享配置提供 `finishWindowMs=300`、`basicDurationMs=1000`；`config/battle-hex.ts` 的 `CHOREO.strikeSec` 只引用别名。BE/FE 不各自复制 300ms。
- `ui/battle-hex-render.ts` 只按 `animState` 和既有事件画，不导入 battle-core、不计算速度/伤害；两段 `skill/miss` 各自产生一次 T21 冒字和血条下移。
- hero `charge` 为 cast clip 1..3 循环，`strike` 为 clip 2→3 单播；legacy 敌型按既有 profile 降级到 `atk`。终局后渲染器继续消费表现帧，忽略任何 settlement 事件（因为 scheduler 已不再发）。
- `proto/battle_demo/main.ts` 将同一逻辑 dt 同时传给 session 与 view；x2 只能有一个速度真源，禁止只加速血条/行动条而不加速 cast 帧。

## 5. 确定性与事件纪律

同一 session 的 due 项按以下全序比较：

```text
(dueAtSec, castSeq, segmentOrdinal, targetOrdinal)
```

1. `dueAtSec` 先序；同刻按 t0 分配的 `castSeq` 升序。
2. 一个 cast 的段 1 项在其段 2 项前。段 1 的“重搜”发生在该 cast 取得队首时，随后按保存的目标数组连续处理；不会在两个目标之间插入另一 cast 的重搜。
3. 同段内 `targetOrdinal` 即 t1 搜索时 `all` 的索引顺序。每个仍存活目标每段调用一次 F-04 RNG；死者、空放、消散、终局截断均不消费 RNG。
4. 段内每个目标提交伤害后立即检查 `dead` 和 `terminal`；终局边界一旦成立，当前段剩余目标和所有未来 settlement 项均丢弃。较早 cast 的段若致死较晚 cast 的施法者，后者轮到时消散。
5. `emitAt` 只改变事件时间戳，不改变逻辑时钟；时间沿用现有两位小数格式。相同 seed + 相同操作序列（含 rejected、t1 前移动）必须得到完全相同的 HP、事件类型、targetId、damage、crit、`t`。

## 7. 验收矩阵与易错点

### 7.1 基础时序（AS）

| 编号 | 用例/检查 | 必须锁定 |
|---|---|---|
| AS-T1 | `0.8+0.2` | 3000ms |
| AS-T2 | 和超过 6 | 500ms，无额外 clamp 分支 |

### 7.2 SP-2 全等专项清单

| 场景 | 重放必须相等的内容 | RNG/顺序门 |
|---|---|---|
| 同 seed、同提交与 rejected 操作 | HP、事件、`t`、targetId、damage、crit | rejected 不消费 RNG |
| t1 前走位相同 | t1 目标 ID 数组与两段事件 | 锚固定为施法者 t0 格；重搜只读 t1 站位，按 `all` |
| t0 圈内走出 / 圈外走入 | 目标集与事件 | 不读取 t0 旧集合 |
| t1 后走位 | t2 目标 ID/事件 | 不二次重搜 |
| t1→t2 目标死亡 | t2 无该目标事件 | 死者不消费 RNG |
| t1 为空 | 只有一条无目标 skill | 空放不安排 t2、不消费 RNG |
| 施法者 t1 前/后死亡 | 未完成段无事件 | 消散不消费 RNG |
| 同 dueAt 多 cast | 事件序列与最终状态 | `(dueAt, castSeq, segment, targetOrdinal)` |
| 终局截断 | 终局边界后无新增伤害事件 | FE 帧不属于 settlement 流 |

易错点：

- 把动态重搜误做成 t0 快照，或在 t2 重新按当前格搜一次；
- 对 t1 已保存目标中的死者继续掷骰，或因空放发第二条事件；
- 施法者被击杀后仍让 pending cast 进入 due 队列；
- 只在整批 drain 结束才检查终局，导致同刻后续目标/段产生事件；
- 把 `castSpeed` 与 `internalCastSpeed` 相乘/再乘等级，或在 session/UI 复制伤害公式；
- 以 tick 当前时刻覆盖 `dueAt`，或 x2 只加速逻辑不加速表现。

## 8. 架构决策与拍板节

- **采用**：session scheduler + core 纯段函数 + t1 动态重搜 + t1 目标集缓存；事件契约零新增。理由：满足 v1.3 竞技性语义，保持 battle-core F-04 单一真源，并让 AI/玩家共享同一条时序。
- **采用**：死亡判定内联取消 pending；终局 settlement/presentation 分离。理由：死亡与终局都在确定的 HP 提交边界生效，避免“已死仍施法”与终局后伤害，同时不剪掉 FE 已接受的表现帧。
- **采用**：`finishWindowMs=300` 作为 BE/FE 共享常量，普攻表现 1000ms；不在 UI 或云端重复定义。
- **不选**：提交时目标快照、t2 二次重搜、施法者死亡继续结算、第二段新事件类型、session/FE 自行计算伤害。这些均与 v1.3 或单一真源冲突。
- 当前无待 Leo 业务裁定；PM 只需按本方案做需求符合性与技术门检，之后即可发 BE 卡。
