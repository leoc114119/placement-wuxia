# 出招速度与两段式伤害技术方案 v0.3

> 分类：03-战斗系统 · 性质：研发施工蓝图（不改需求文档、不写游戏代码）
> 依据：《出招速度与两段式伤害需求文档》v1.4（2026-09-07，Leo L 环二次终裁）、《武功数据 schema》v0.2 `a9e1502`、《战斗交互行为规格》v2.4、现行 `systems/battle-session.ts` / `systems/battle-core.ts` / `types.ts`
> 状态：🟡 v0.3 语义修订待研发线 PM 需求门与 Leo L 环；BE seq=92、FE seq=94 的既有实现作为增量基础
> v0.3 核心变化：段 1 改为 t0 提交即时结算；段 2 改为 t1=t0+整个出招时长动态重搜；取消独立 300ms 收招结算节点；施法循环帧周期固定 280ms。

## 1. 方案结论

### 1.1 定版主张

1. **提交即结算段 1、单 pending 结算段 2**。技能通过校验后在 `t0` 立即确定当前范围并结算 50% 段 1；只为段 2 保留一个 `pendingCast`，在 `t1=t0+castDurationMs` 重搜并结算。相比 v0.2 的 t1/t2 双 due 项，队列少一个结算节点，且“出手必中”与命中帧天然同刻。
2. **采用单一逻辑时钟 + 每个施法者一个 pending cast**。行动条继续按现有 tick 填充，提交时照 BAR-3 清零；活体施法中的单位不能再次取得行动权，但其他单位照常行动。
3. **两套目标集合**。段 1 使用 t0 即时范围集合；段 2 在 t1 以施法者 t0 自身格（R1）为锚、按 `rangeShape` 重搜一次并固定。玩家点击格仅作受理/演出朝向，不改变 AOE 锚。
4. **施法者死亡使招式消散**。死亡判定提交的同一时点立即撤销 pending cast；未结算段不再掷骰、不写血量、不发 `skill/miss`。无打断边界只适用于活体施法者。
5. **伤害判定仍由 battle-core 的 F-04 链产生**。新增“技能伤害段”纯函数，段 1 仅将闪避失败门强制为命中（forceHit），段 2 完整走 F-04；session 只负责排程、扣资源、写血量和转发既有事件，禁止复制暴击或取整公式。
6. **终局分为结算态与表现态**。某个目标伤害使一方胜利/失败后，立即停止所有后续结算与新增伤害事件；FE 保留当前施放/收招表现帧至其 `finishAtSec`，表现不再改血量或发事件。
7. **事件契约零新增**。两段分别发既有 `skill` / `miss` 事件；段 1 时间戳为 t0，段 2 为 t1。t0 空放发一条无目标 `skill` 且不创建段 2；t1 重搜为空时不发事件、不退款。

### 1.2 需求真源与版本边界

本方案以需求文档 v1.4 的 AS-1～AS-9 为唯一业务口径：AS-1 使用 `3000 ÷ min(6, 武功出招系数 + 内功加成速度)`；AS-2 施法循环帧周期 280ms；AS-3 段 1 在 t0 即时且出手必中；AS-4 段 2 在 t1=整个出招时长末端、收招窗 300ms 独立结算概念取消；AS-6 为 t0 即时集合+t1 动态重搜；AS-6b 为施法者死亡消散；AS-9 为终局停结算、FE 播完表现。

## 2. 数值与输入契约

### 2.1 出招时长

每次技能提交取得当前成长域快照值：

```text
skillSpeed    = skill.castSpeed ?? 0.8
internalSpeed = actor.internalCastSpeed ?? 0.2
speedSum      = min(6, skillSpeed + internalSpeed)
castDurationMs = 3000 / speedSum
```

- `3000`、`6`、`0.8`、`0.2` 是 MVP 口径；封顶得到最短 500ms，不再另写第二个 `max(500ms, …)` 分支。
- `castSpeed` 是武功当前等级产生的个体差异快照；session 不读 `level` 推导成长曲线。`internalCastSpeed` 由内功/成长域提供，不能塞进 `SkillDef`，也不能由 session 读取 `neigongLevel` 反推。
- 两个输入必须是有限数；`skillSpeed > 0`、`internalSpeed >= 0`。缺失使用 MVP 默认，显式非法值在装配入口 fail-fast。

### 2.2 普攻表现与保留常量

- 旧 `finishWindowMs=300` 不再是技能结算节点；可因其他表现兼容暂留，但 BE/FE 不得用它推导段 2 时间。段 2 唯一时间锚是 `t1=t0+castDurationMs`。
- 普攻伤害和 F-04 判定不受出招速度影响；普攻帧表现时长为 1000ms，只改表现计时，不延迟普攻事件或血量。

### 2.3 两段伤害取整

每段独立计算并独立 `floor`：

```text
segmentDamage = floor(max(atk - def, 1) × skill.grade × 0.5 × (crit ? 1.5 : 1))
```

两段之和允许与整次伤害再除二相差 1 点；session 不补差，也不把余数塞到第二段。

## 3. 运行时状态机

### 3.1 时间线

设接受提交的逻辑时刻为 `t0`，`t1=t0+castDurationMs/1000`（不再定义 t2）：

| 时段 | session 状态 | 演出/结算 |
|---|---|---|
| `t0` | `pendingCast.phase='casting'` | 校验通过；扣一次内力、写一次冷却、BAR-3 清零；按 t0 范围立即结算段 1（出手必中）；非空且未终局才保存段 2 pending；施法者进入 `charge` |
| `[t0,t1)` | 施法锁定 | 施放帧整套循环；活体施法不被伤害打断；行动条继续 tick，但该 actor 不参与 ready 轮转 |
| `t1` | `phase='finish'` 或消散 | 活体且未终局时，以 R1 锚重搜并固定段 2 目标，逐目标结算第二段；空搜不发事件；完成即清 pending、回 idle |

`t1` 即使落在一次较大的 `tick(dt)` 中，也按 dueAt 边界 drain；事件 `t` 写 t0/t1，不是 tick 结束时刻。主循环仍采用现有 `dt≤0.05s` 上限，session 对更大 dt 也必须等价切分，不能漏段。

### 3.2 施法者死亡与终局边界

- 所有造成 HP 变化的路径在“写入 HP → 标记 `dead`”的同一事务内调用 `cancelPendingCastOnDeath(actorId, deathAtSec)`。该函数移除 t1 pending，标记 `settlementState='dissipated'`，不产生额外事件。
- 段 1 在 t0 致死另一方时立即检查终局；施法者在 t0 后、t1 前死亡，段 2 消散；施法者在 t1 结算中死亡，已完成目标段保留，后续目标停止。
- 同一 t1 的 pending 按 `castSeq` 顺序处理。较早 cast 致死较晚 cast 的施法者时，后者轮到即消散，不会“同刻已死仍结算”。
- `terminal` 在每个目标伤害提交后立即检查。若胜负成立，停止当前段剩余目标、同刻剩余 cast 段及未来 settlement queue；不再产生任何伤害、miss 或 skill 事件。
- 终局只停止结算，不强制剪掉 FE 表现：保留已接受 cast 的 `finishAtSec=t1`，继续播放至循环末帧；这些帧是纯视觉，不得写 HP、掷 RNG 或发事件。施法者死亡则由既有 `dead` 视觉覆盖。

### 3.3 t0 即时段 1 / t1 动态段 2 算法

`PendingCast` 在 t0 保存施法者自身格（R1）`anchorCell`、技能 `rangeShape` 与段 1 的 `targetIds0`；只有非空段 1 且未终局才保存段 2 pending。t1 执行一次且仅一次动态重搜：

```text
scheduleT0(actor, skill, t0):
  targets0 = search(anchor=actor.cell@t0, shape=skill.rangeShape, now=t0)
  if targets0.length === 0:
    emitAt(t0, {type:'skill', actorId, skillId})
    keepPresentationUntil(t0 + castDuration)
    return noPendingSegment2
  for target of targets0:
    resolveSkillSegment(actor, target, skill, 0.5, rng, {forceHit:true})
  if terminal: return noPendingSegment2
  createPending({anchorCell: actor.cell@t0, rangeShape: skill.rangeShape,
                 targetIds0: targets0, dueAt: t0 + castDuration})

resolveT1(cast, t1):
  if terminal || !alive(cast.actorId): dissipate(cast); return
  cells = projectRange(anchor=cast.anchorCell, shape=cast.rangeShape)
  ids = all.filter(e => alive(e)
                    && enemyOf(e, cast.actorId)
                    && cells.has(e.cell)).map(e => e.id)
  cast.targetIds1 = ids                // 保留 all 顺序，不按坐标或 ID 排序
  cast.t1Resolved = true
  for targetId of ids: resolveSkillSegment(cast.actor, targetId, cast.skill, 0.5, rng)
  clearPendingAndReturnIdle()
```

- `projectRange` 必须调用 ATK-2/现有范围 helper；锚点是施法者 t0 自身格，不是点击格或当前格。
- 段 1 搜索读取 t0 当前站位；段 2 搜索读取 t1 当前站位。t1 后走位不改变段 2 集合。
- `all` 是唯一确定性顺序来源；死者、空放、消散、终局截断不消费 RNG。t0 空放只发一条无目标 skill；t1 空搜静默。

### 3.4 入口与状态收敛

- `cast`、`attack(skillId)`、AI `planSkill` 都只能调用同一 `scheduleSkillCast`；玩家/AI 共用 t1 搜索、段结算和 RNG 路径。
- `attack(skillId)` 的兼容入口保留其点击单目标契约；若调用的是 AOE 技能，必须由已统一的 ATK-2 范围入口提供点击格（仅受理/演出）与 `rangeShape`，段 1 仍按 t0 AOE 范围逐目标即时结算，不得退回只打点击目标。普攻 `attack(skillId=null)` 仍走既有 `doAttack`。

## 4. 接口与模块落点

### 4.1 最小类型增量（施工时落到 `types.ts`）

```ts
interface SkillDef {
  // ...existing fields
  castSpeed?: number;             // schema v0.2；旧技能缺省 0.8
}

interface CombatantInput {
  // ...existing fields
  internalCastSpeed?: number;     // 成长域快照；不读 level 反推
}

interface PendingCast {
  castSeq: number;                // session 内单调递增
  actorId: string;
  skillId: string;
  anchorCell: HexCell;            // t0 施法者提交时所在格（R1），t1 的 AOE 锚；点击格不入锚
  rangeShape: RangeShape;         // t0 冻结，t1 只重算一次
  targetIds0: string[];            // 段 1 t0 集合，保留 all 顺序
  targetIds1: string[] | null;     // 段 2 t1 集合，保留 all 顺序
  startedAtSec: number;
  finishAtSec: number;
  phase: 'casting' | 'finish';
  t1Resolved: boolean;
  settlementState: 'pending' | 'resolved' | 'no-target' | 'dissipated' | 'terminal-canceled';
}
```

`targetIds1=null` 表示尚未到 t1，不能被施工代码当成空集合。t0 空放不创建结算 pending；如实现需要继续播视觉，在结算 pending 删除后保留只读 `presentationCast`，不得复用已消散 cast 进行结算。

### 4.2 battle-core

新增不扣资源、不改 actor/target 的段结算函数：

```ts
resolveSkillSegment(
  actor: ActionActor,
  target: ActionActor,
  skill: SkillDef,
  damageRatio: 0.5,
  rng: Rng,
  options?: { forceHit?: boolean },
): { kind: 'skill' | 'miss'; damage: number; crit: boolean; missed: boolean }
```

函数内部复用 F-04 命中→闪避→暴击→破防→取整顺序；`forceHit` 只跳过段 1 的闪避失败门，暴击与其余链路不变。既有 `resolveAction` 签名和普攻路径不动。`castDurationMs`/`effectiveCastSpeed` 也由 core 纯函数提供，云端 `settle/core.js` 继续是正式数值真源，客户端只读展示。

### 4.3 battle-session scheduler

在 `createHexBattle` 闭包内增加 `pendingCasts`、`nextCastSeq` 与（如 FE 需要）只读 `presentationCasts`：

- `scheduleSkillCast(actor, skill, facing, faceTo)`：唯一资源扣除、冷却写入、BAR-3、`setAnim('charge')`；从 actor t0 自身格复制 `anchorCell`，立即搜索 `targetIds0` 并结算段 1；非空且未终局才入一个 t1 pending。`faceTo` 仅为点击格演出朝向。
- `drainDueCasts(now)`：只处理 t1 段 2；按 §5 comparator 取 due 项并重搜一次；每个目标伤害后检查死亡/终局。
- `applyDamage` 的死亡回调必须同步调用 `cancelPendingCastOnDeath`；取消发生在 scheduler 取得下一个队列项之前。
- `pendingCasts.has(actor.id)` 作为 ready/AI/手动提交门。施法中 bar 可 clamp 到 100，但不重复发 `bar-max`；pending 清除后下一轮再按 BAR-2 发一次。

建议 `tick` 可观察顺序：

1. 推进逻辑时钟、行动条和现有移动/非施法动画；
2. drain 所有 `dueAt <= t` 的 cast 段（段内即时死亡/终局检查）；
3. `checkEnd()` 兼容普通行动路径；
4. 过滤 `!pendingCasts.has(actor.id)` 后运行 BAR-2 ready 队列和 AI/手动动作；
5. 到达 90s 再走既有 timeout。

### 4.4 FE、共享常量与宿主

- 新时序不再把 `FINISH_WINDOW_MS=300` 当作段 2 结算锚；旧常量如因其他表现兼容暂留，不得参与技能 settlement。共享 `BASIC_DURATION_MS=1000` 仍只约束普攻表现保持窗。
- `ui/battle-hex-render.ts` 只按 `animState` 和既有事件画，不导入 battle-core、不计算速度/伤害；t0 事件触发命中反馈，cast 帧以独立 `CAST_FRAME_PERIOD_MS=280` 循环至 t1，t1 事件触发第二跳并回 idle。
- hero `charge` 为 cast clip 1..3 循环；循环末帧即收势，不再额外等待 strike 结算窗；legacy 敌型按既有 profile 降级到 `atk`。终局后继续消费冻结快照表现态。
- `FX.slashSec=0.28` 保持独立瞬时斩击弧；不与 cast 280ms 或普攻 1s 强绑。
- `proto/battle_demo/main.ts` 将同一逻辑 dt 同时传给 session 与 view；x2 只能有一个速度真源，禁止只加速血条/行动条而不加速 cast 帧。

## 5. 确定性与事件纪律

同一 session 的 t1 due 项按以下全序比较：

```text
(dueAtSec, castSeq, targetOrdinal)
```

1. `dueAtSec` 先序；同刻按 t0 分配的 `castSeq` 升序。段 1 已在 t0 的既有 action 顺序内完成，不进入未来 due 队列。
2. 段 2 的 `targetOrdinal` 即 t1 搜索时 `all` 的索引顺序；重搜一次后按数组连续处理，不在两个目标之间插入另一 cast 的重搜。
3. 每个仍存活目标每段调用一次 F-04；死者、空放、消散、终局截断均不消费 RNG。段 1 的 forceHit 不额外引入第二套 RNG。
4. 段内每个目标提交伤害后立即检查 `dead` 和 `terminal`；终局边界一旦成立，当前段剩余目标和所有未来 settlement 项均丢弃。较早 cast 的段若致死较晚 cast 的施法者，后者轮到时消散。
5. `emitAt` 只改变事件时间戳，不改变逻辑时钟；时间沿用现有两位小数格式。相同 seed + 相同操作序列（含 rejected、t1 前移动）必须得到完全相同的 HP、事件类型、targetId、damage、crit、`t`。

### 7.2 SP-2 全等专项清单

| 场景 | 重放必须相等的内容 | RNG/顺序门 |

| 同 seed、同提交与 rejected 操作 | HP、事件、`t`、targetId、damage、crit | rejected 不消费 RNG |
| t1 前走位相同 | t1 目标 ID 数组与两段事件 | 锚固定为施法者 t0 格；重搜只读 t1 站位，按 `all` |
| t0 圈内走出 / 圈外走入 | 目标集与事件 | 不读取 t0 旧集合 |
| t1 后走位 | 段 2 目标 ID/事件 | 不二次重搜 |
| t1 目标死亡 | 段 2 无该目标事件 | 死者不消费 RNG |
| t0 为空 / t1 为空 | t0 空=一条无目标 skill；t1 空=无事件 | 无退款、不消费 RNG |
| 施法者 t1 前/后死亡 | 未完成段无事件 | 消散不消费 RNG |
| 同 dueAt 多 cast | 事件序列与最终状态 | `(dueAt, castSeq, segment, targetOrdinal)` |
| 终局截断 | 终局边界后无新增伤害事件 | FE 帧不属于 settlement 流 |

易错点：

- 把段 1/段 2 目标集合混为一个快照，或在 t1 后再次重搜；
- 对 t1 已保存目标中的死者继续掷骰，或因空放发第二条事件；
- 施法者被击杀后仍让 pending cast 进入 due 队列；
- 只在整批 drain 结束才检查终局，导致同刻后续目标/段产生事件；
- 把 `castSpeed` 与 `internalCastSpeed` 相乘/再乘等级，或在 session/UI 复制伤害公式；
- 以 tick 当前时刻覆盖 `dueAt`，或 x2 只加速逻辑不加速表现。

## 8. 架构决策与拍板节

- **采用**：t0 段 1 内联 + 一个 t1 pending 段 2；段 1/段 2 各自目标集合，段 2 以 R1 锚动态重搜。理由：满足 v1.4 的出手必中、命中帧同步与慢招可躲，同时删去 v0.2 多余 due 节点。
- **采用**：死亡判定内联取消 pending；终局 settlement/presentation 分离。理由：死亡与终局都在确定的 HP 提交边界生效，避免“已死仍施法”与终局后伤害，同时不剪掉 FE 已接受的表现帧。
- **采用**：施法循环帧周期 280ms，与 walk 140ms、`FX.slashSec=0.28s`、普攻表现 1000ms 各自独立；不把旧 300ms 收招窗带入 settlement。
- **采用**：普攻表现 1s 与 `FX.slashSec=0.28s` 分离；前者是 `basic` 保持窗，后者是进入攻击态的瞬时斩击弧，不把独立特效时长误并入普攻节奏。
- **不选**：v0.2 的 t1 段 1+t2 段 2、独立 300ms 收招结算、t0/t1 共用快照、t2 二次重搜、施法者死亡继续结算、session/FE 自行计算伤害。这些均与 v1.4 或单一真源冲突。
- FE seq=94 技术复核：`fe37cf4` + `676c8c6` 在独立副本通过 typecheck/lint/build、battle `303 passed + 14 skipped`、behavior `14/14`；既有 shot/e2e/DBG 证据随交付登记保留。两项单列均不构成技术阻塞：斩击弧按独立特效口径保留 0.28s；终局由冻结 `SnapshotActor.animState` 继续渲染，结算队列已停且 `presentationCasts` 仅供内部审计。
- 当前待办从“主架构技术验收”转为研发线 PM 需求门与 Leo L 环；若 Leo 要求终局遮罩下的精确帧边界或斩击弧改为 1s，应另立表现规格卡，不在本次 FE 接线回补。
