# 出招速度与两段式伤害技术方案 v0.1

> 分类：03-战斗系统 · 性质：研发施工蓝图（不改需求文档、不写游戏代码）
> 依据：《出招速度与两段式伤害需求文档》v1.2（`9081e29`）、《武功数据 schema》v0.2（`a9e1502`）、《战斗交互行为规格》v2.4、现行 `systems/battle-session.ts` / `systems/battle-core.ts` / `types.ts`
> 状态：🔶 待 PM 需求符合性审阅 → Leo 拍板后拆 BE/FE 卡

## 1. 方案结论

### 1.1 定版主张

1. **技能出招必须从“提交即结算”改为“提交即排程、两个时刻结算”**。第一段在招式时长结束（落地起点），第二段在收招窗口结束；普攻仍在提交时单段结算。
2. **采用单一逻辑时钟 + 每个施法者一个 pending cast**。行动条继续按现有 tick 填充，提交时照 BAR-3 清零；施法中的单位不能再次取得行动权，但其他单位照常行动。
3. **伤害判定仍由 battle-core 的 F-04 链产生**。新增“技能伤害段”纯函数，传入 `damageRatio=0.5`；session 只负责排程、扣资源、写血量和转发既有事件，禁止在 session/UI 复制命中、闪避、暴击或取整公式。
4. **AOE 目标在提交时快照**，保持 `all` 数组顺序；落点时不重新搜射程、不因目标移动改变集合。结算时目标已死亡则跳过该段且不消费 RNG；该提案是异步施法下保持点击确认语义和 SP-2 确定性的最小闭合方式，需 PM 在拆卡前确认。
5. **不新增 `BattleUiEvent` 类型或字段**。两段分别发既有 `skill` / `miss` 事件；命中事件带 `targetId`、`damage`，miss 带 `targetId`、`damage=0`。空放保留一条无目标 `skill` 事件，在第一段时刻发出。

### 1.2 需求真源冲突处理

需求文件的 AS-1 行仍残留 v1.1 的“三系数连乘”文字，但文件头、六点第 4 条及 `9081e29` 已明确取代该模型。**本方案以 v1.2 的“系数相加后除 3000”作为唯一实现依据**；PM 发卡前应把 AS-1 行改成同一文字，避免施工代理读到两套公式。该处是需求文档修订请求，不在本方案中直接改需求原文。

## 2. 数值与输入契约

### 2.1 出招时长

对每次技能提交，先取得当前等级快照值：

```text
skillSpeed    = skill.castSpeed ?? 0.8       // 武功自身系数，旧数据兼容默认值
internalSpeed = actor.internalCastSpeed ?? 0.2 // 内功系统输出；不放进 SkillDef
speedSum      = min(6, skillSpeed + internalSpeed)
castDurationMs = 3000 / speedSum
```

- `3000`、`6`、`0.8`、`0.2` 是 MVP 口径；封顶后自然得到最短 `500ms`，不再写第二个 `max(500ms, …)` 特判。
- `castSpeed` 是武功当前等级的**数据快照**，session 不根据 `level` 自行推导成长曲线；成长曲线由武学/成长域提供。
- `internalCastSpeed` 是成长域输出，不是 `SkillDef` 字段。建议在 `CombatantInput` 增加可选字段（向后兼容），或由装配层在创建 session 时注入等价的 actor context；禁止把它塞进每个技能对象造成重复口径。
- 两个输入均须为有限数；`skillSpeed` 必须 `>0`，`internalSpeed` 必须 `>=0`。缺失走上述 MVP 默认，非法显式值在装配入口 fail-fast，禁止静默改成 0 或 NaN。

### 2.2 收招窗口与普攻表现

- `finishWindowMs` 建议定为 **300ms**，直接复用现有 `CHOREO.strikeSec=0.3`，不另造一套时间常量。它是表现常量，但由于第二段落点消费它，必须在 BE/FE 两卡共同引用。
- 普攻伤害和 F-04 判定不受出招速度影响；普攻帧表现时长改为 **1000ms**（需求 v1.2 Leo 裁定），只改表现计时，不延迟普攻事件或血量。

### 2.3 两段伤害取整

每一段独立计算并独立 `floor`：

```text
segmentDamage = floor(max(atk - def, 1) × skill.grade × 0.5 × (crit ? 1.5 : 1))
```

因此两段之和可能与“整次伤害再除二”相差 1 点，这是 50/50 + 各段独立暴击/闪避的必然结果；不得在 session 端补差或把余数塞到第二段。

## 3. 运行时状态机

### 3.1 时间线

设接受提交的逻辑时刻为 `t0`，`t1=t0+castDurationMs/1000`，`t2=t1+finishWindowMs/1000`：

| 时段 | session 状态 | 演出/结算 |
|---|---|---|
| `t0` | `pendingCast.phase='casting'` | 校验通过；扣一次内力、写一次冷却、BAR-3 清零、清选中；施法者进入 `charge` |
| `[t0,t1)` | 施法锁定 | 施放帧整套循环；不重新选目标、不受伤害打断；行动条按现有 tick 继续填充，但该 actor 不参与 ready 轮转 |
| `t1` | `phase='finish'` | 施法者切 `strike`；对提交时快照中仍存活的目标逐个做 50% 独立判定并发 `skill/miss`；第一段致死立即发既有 `death` |
| `[t1,t2)` | 收招窗口 | 播 `cast` 的第 2→3 帧（legacy 敌型按既有 `atk` 降级）；其他单位照常行动 |
| `t2` | 清理 pending | 对快照目标中仍存活者逐个做第二段 50% 独立判定；已死亡目标跳过且不消费 RNG；处理完切 `idle`，释放施法锁 |

`t1/t2` 即使落在一次较大的 `tick(dt)` 中，也必须按 `dueAt → castSeq → segment(1→2)` 的总序处理；事件的 `t` 写排程时刻（不是 tick 结束时刻）。主循环继续采用现有 `0.05s` 上限，session 内部应对更大 `dt` 做同样的边界切分或等价 drain，保证不会因大步长漏掉段落状态。

### 3.2 不打断与终局

- 施法者被另一单位击杀时，已经接受的 pending cast 仍按 `t1/t2` 结算（“无打断”是伤害语义）；死亡只让其渲染优先显示 `dead`，不撤销结算队列。
- 若第一段击杀最后一个敌人，立即进入胜利终局，第二段不再对已死目标结算；终局后不再启动新行动。若项目希望在胜利界面仍播完纯表现收招，可由 FE 保留视图动画，但不得再写血量/事件。
- 终局事件先于尚未到时的后续战斗行动；待处理的其他 actor cast 不再造成战斗结算，避免胜负已定后出现伤害事件。该行为只影响终局边界，不构成对施法者受击的“打断”。

### 3.3 目标集合与 AOE

- `cast` 主路径：使用激活时冻结的射程集合，提交时按 `all` 顺序抓取存活敌 ID。
- `attack(skillId)` 兼容路径：仍只抓取被点击的单一目标，**不偷偷扩成 AOE**；最终 FE 迁移到 `cast` 后再由 ATK-2 统一走范围语义。
- AI：`planSkill` 取得的目标集合在 AI 行动提交处冻结，走同一 scheduler；玩家/AI 共用 segment resolver 和 RNG 顺序。
- 目标在施法期间移动、离开原射程或进入另一格，不重新判定范围；目标若已死亡则该段跳过。若 PM 选择“动态追踪”而非本方案的提交快照，必须另开规格变更并重写 AS-6/SP-2 测试，不能在施工时自行切换。

## 4. 接口与模块落点

### 4.1 建议的最小类型增量

以下是接口形状，不是本方案阶段的代码提交：

```ts
// types.ts：向后兼容旧 CombatantInput；成长域负责填充当前值
interface SkillDef {
  // ...existing fields
  castSpeed?: number;       // schema v0.2；旧技能缺省按 0.8
}

interface CombatantInput {
  // ...existing fields
  internalCastSpeed?: number;
}

// battle-core.ts 或 systems/cast-speed.ts：不含 session/UI 状态
interface CastSpeedContext {
  skillSpeed: number;       // 已归一化的 SkillDef.castSpeed ?? 0.8
  internalSpeed: number;    // actor.internalCastSpeed ?? 0.2
  speedSum: number;         // min(6, skillSpeed + internalSpeed)
  durationMs: number;       // 3000 / speedSum
}

interface PendingCast {
  castSeq: number;          // 单 session 单调递增，确定同刻顺序
  actorId: string;
  skillId: string;
  targetIds: string[];      // 提交时快照，保持 all 顺序
  startedAtSec: number;
  landAtSec: number;
  finishAtSec: number;
  phase: 'casting' | 'finish';
}
```

`SkillDef.castSpeed` 建议先做可选字段，旧 fixture 缺字段时使用 0.8；完成存量数据迁移后再在下一次 schema major 版本改为必填。`internalCastSpeed` 永远不进 `SkillDef`，也不由 session 读取 `neigongLevel` 反推。

### 4.2 battle-core

新增一个不扣资源、不改 actor/target 的段结算函数（名称可按实现习惯调整）：

```ts
resolveSkillSegment(
  actor: ActionActor,
  target: ActionActor,
  skill: SkillDef,
  damageRatio: 0.5,
  rng: Rng,
): { kind: 'skill' | 'miss'; damage: number; crit: boolean; missed: boolean }
```

- 函数内部复用现有 F-04 命中→闪避→暴击→破防→取整顺序；不在 session 重写公式。
- 既有 `resolveAction` 保持行为和签名不变，普攻、旧 headless 用例零回归；新函数只作为新增能力。
- `castDurationMs`/`effectiveCastSpeed` 也应由 core 的纯函数提供，云端 `settle/core.js` 继续是正式数值真源；客户端只读展示，不再自行算伤害或成长。

### 4.3 battle-session

在 `createHexBattle` 闭包内增加：

- `pendingCasts: Map<string, PendingCast>`（每 actor 至多一个）和 `nextCastSeq`；
- `scheduleSkillCast(actor, skill, targetIds)`：唯一资源扣除、冷却写入、BAR-3、`setAnim('charge')`、入队；
- `drainDueCasts(now)`：按 `(dueAt, castSeq, segment)` 排序，调用 core 段函数、应用 hp、`emitAt(dueAt, …)`、死亡判定；
- `pendingCasts.has(actor.id)` 作为 ready/AI/手动提交门；不把 pending cast 重新塞回 `selection`。

`cast`、`attack(skillId)`、AI `planSkill` 三条技能入口只能调用 scheduler，禁止保留一条“玩家延迟、AI 立即”或“兼容入口立即结算”的旁路。普攻 `attack(skillId=null)` 和移动附带普攻继续调用既有 `doAttack`，不进入 scheduler。

建议 `tick` 的可观察顺序为：

1. 计算加速后的逻辑 `dt`，推进时钟、行动条和现有移动/非施法动画；
2. drain 所有 `dueAt <= t` 的 cast 段（事件 `t` 使用各自 `dueAt`）；
3. `checkEnd()`；
4. 过滤 `!pendingCasts.has(actor.id)` 后运行 BAR-2 ready 队列和 AI/手动动作；
5. 到达 90s 再走既有 timeout。

如果某 actor 在施法期间 bar 先达到 100，保持 clamp 但不发该 actor 的 `bar-max`；pending 清除后下一轮再按 BAR-2 正常发一次。这样不会出现“施法中获得第二个回合”或 bar-max 重复事件。

### 4.4 渲染与宿主

- `config/battle-hex.ts`：新增/复用 `CAST.finishWindowMs=300`、`CHOREO.basicSec=1`；hero directional 的 `charge` 映射为 `cast` clip 1..3 循环，`strike` 为 clip 2→3 单播；`ANIM_LOOP_GROUPS` 增加 `charge`。敌型 profile 继续按裁定把 `charge/strike` 映射到 `atk`，不要求敌型 cast 素材。
- `ui/battle-hex-render.ts`：只按快照 `animState` 和既有 `BattleUiEvent` 画，不导入 battle-core，不计算速度/伤害。事件消费白名单已逐条处理 `skill/miss`，两段自然产生两次 T21 冒字；不得用“每次施法只冒一次”的去重。
- `proto/battle_demo/main.ts`：session 与 view 使用同一逻辑 dt。现有 `speedOn` 已由宿主持有，调用 `updateView` 时传 `dt * (speedOn ? SPEED_FACTOR.fast : SPEED_FACTOR.normal)`，或由 session 暴露只读 `presentationDt`，二选一但只能有一个速度真源。禁止 x2 只加速血条/行动条而不加速 cast 帧。
- renderer 若一帧收到两个 due 事件，事件仍全部消费；host 的 `dt≤0.05s` 与 session 边界切分保证正常播放中间 `strike` 状态。大步长 node 用例只断言事件顺序/时间，不把最终 snapshot 当成逐帧动画证据。

## 5. 确定性与事件纪律

1. 每次接受技能提交先分配 `castSeq`，目标 ID 只复制不排序。
2. 同一 `dueAt` 按 castSeq、段 1→2、目标数组原顺序处理；FACE-1 多目标平局 RNG 仍在逐目标判定之前消费，沿用现有规则。
3. 每个存活目标每段调用一次 F-04 RNG 链；miss/死亡跳过目标不消费随机数。相同 seed + 相同操作序列（包含 rejected）必须得到完全相同的 hp、事件类型、targetId、damage、crit 和 `t`。
4. `emitAt` 只改变事件时间戳写入，不改变逻辑时钟；时间统一保留现有两位小数格式。
5. 空放：资源在 `t0` 一次扣除，动画仍经历 `charge→strike→idle`；`t1` 发一条 `{type:'skill', actorId, skillId}`，不带 `targetId/damage`，`t2` 不再发第二条空事件。

## 7. 验收矩阵与易错点

| 编号 | 用例/检查 | 必须锁定 |
|---|---|---|
| AS-T1 | `0.8+0.2` | 3000ms |
| AS-T2 | 和超过 6 | 500ms，且无额外 clamp 分支 |
| AS-T3 | 提交后立刻查 hp/资源/bar/事件 | hp 不变；内力/冷却/bar 已变；无段事件 |
| AS-T4 | `t1-ε / t1 / t2-ε / t2` | 只在两个边界各结算一次，事件 `t` 为 dueAt |
| AS-T5 | 两段命中/闪避/暴击组合 | 每段独立 F-04，50% 各自 floor |
| AS-T6 | 第一段致死、目标先被他人击杀 | 第二段不对死者结算、不消费 RNG |
| AS-T7 | AOE 2~6 目标 | 目标序固定，段序固定，资源只扣一次 |
| AS-T8 | 施法者中途死亡 | pending cast 仍按时结算（非终局） |
| AS-T9 | 空放/兼容 `attack`/AI | 空放一条无目标 skill；兼容单目标；AI 同 scheduler |
| AS-T10 | 同 seed + 同操作（含拒绝） | hp、事件、时间戳全等 |
| AS-T11 | 普攻 | 单段即时数值，动画 1s，不读 castSpeed |
| AS-T12 | x2 与大 dt | 逻辑时长减半；due 顺序不变；不漏段、不重复段 |
| AS-T13 | FE 帧与 T21 | cast 循环、strike 2→3、两次数字/血条反馈 |

易错点清单：

- 把 `castSpeed` 与 `internalCastSpeed` 相乘，或再乘 `level`；两者应先求和，成长值由数据域提供。
- 在 session 里复制 `resolveDamage`，导致暴击/取整与 core 分叉。
- 以 tick 当前 `t` 覆盖 `dueAt`，使不同帧率产生不同事件时间。
- AOE 第二段重新按当前格搜敌、对死者继续掷骰，破坏 AS-6/SP-2。
- 施法中继续把 actor 放进 ready 队列，或重复发 `bar-max`。
- 为第二段新造 `skill2` 事件/字段，令 T21 与旧宿主白名单分叉。
- 只改 session 的 x2，不把同一逻辑 dt 传给渲染，造成帧循环与伤害落点错位。

## 8. 路线级判断与拍板节

### 8.1 接下来最先爆的债

若先施工而不冻结 `internalCastSpeed` 的成长域来源，下一期成长系统接入时会出现“客户端默认 0.2、服务端按内功等级重算”的对局分叉；若允许 FE 自算 `castDurationMs`，x1/x2 与网络重放也会再分叉。**建议先让 BE 卡冻结 context 字段和 core 纯函数，再让成长线只提供快照值**，这是未来 1~2 个月最需要先清的接口债。

### 8.2 待 PM/Leo 确认的业务口径

1. 本方案的 AOE **提交时目标快照**是否作为 AS-6 的正式解释；若不采纳，必须给出动态追踪的目标/范围/死亡语义。
2. `finishWindowMs=300` 是否沿用现有 `CHOREO.strikeSec` 定版；若改值，BE/FE 共用同一常量，不能各卡自定。
3. 终局时是否只停止后续战斗结算（本方案推荐），还是要求把已排程 cast 的纯表现也播完；无论选择哪项，禁止终局后新增伤害事件。

### 8.3 架构决策记录

- **方案 A（推荐）**：session scheduler + core 新增纯段函数；事件契约零新增。理由：改动集中、保住 battle-core 既有 14 用例、T21 无需分叉、AI/玩家共享一条时序。
- **不选**：在 session 复制伤害公式、在 FE 用计时器扣血、给第二段新增事件类型、或把 castSpeed 公式放到 UI config。上述做法都会制造数值真源/帧率/事件消费分叉。
