> 方案日期：2026-09-09
>
> 输入：PM2 → 主架构 projbus seq=242；第一批 26 行武器 manifest `assets/_trial_20260909/t45_hero_weapon_left_derivation_seq232/manifest-26rows-seq232.json`；既有《战斗人物六向帧接线方案》§4.2。
> 实施基座：`origin/main` `8b6d050a`；建议施工分支：`task/hero-weapon-layer`。

## 1. 结论与边界

**建议定版：将第一批武器素材一次性导入正式 runtime 路径，按“身体帧键 → 已定位武器覆盖层”渲染；不在运行时再次旋转剑层，也不引用 `_trial/` 路径。**

理由：交付的每张 sword layer 为 240×320 RGBA 画布，已按其对应身体帧完成位置、角度和剪影处理；对它再以 `angleDeg` 作 Canvas 旋转会产生双旋转和握点漂移。`gripPointPx`、`fistCenterPx`、`angleDeg` 是导入预检与回归断言的契约数据，而非本批运行时变换参数。

本卡只接主角。现行规格明确 NPC/敌人直接使用带武器角色帧，**本次不得**给山贼或未来朴刀建立运行时独立武器层。为保留结构一致性，配置抽象支持任意 `spriteKey`，但当前仅允许 `hero` 有条目；敌方条目须有后续需求卡授权。

第一批覆盖 26 个身体帧：idle 6、walk 10、atk 10。缺口为 `walk_rightdown_2`/`walk_leftdown_2` 与 `atk_right_1`/`atk_left_1`，由第二批补齐。首批接线可展示已覆盖帧；未覆盖帧**显式空手并给出开发诊断**，禁止借邻帧、镜像或静态剑层填补。全状态“武器不断帧”仅在第二批 48 行齐备并通过预检后放行。

## 2. 正式落库与加载校验

### 2.1 导入目标（唯一 runtime 来源）

施工卡新增以下正式资源，均从已通过门检的候选源逐字节复制，并在同一实质提交中包含产物、索引与校验结果：

```text
assets/characters/hero/weapon45/
  weapon_idle_right.png
  ...（26 张：与 manifest frameId 一一对应）
  masks/
    ...（有遮挡的 18 张；无 mask 帧不创建占位文件）
  manifest.runtime.json
```

`_trial/` 仅保留候选、溯源与 QA，不得由 production loader 引用。正式 manifest 采用同一 14 字段模板，路径改为 runtime 路径、`status=runtime-release`，并补充由导入脚本产出的路径级 SHA 清单；不改写候选 manifest。

### 2.2 双阶段校验

1. `tools/preflight_hero_weapon_layer.mjs` 在 CI/预览启动前读取候选与 runtime manifest：严格核 14 字段、26 行无重复 `bodyFrame`、candidate/runtime body SHA 相等、每张 sword/mask 的存在性、PNG 240×320 RGBA、SHA、`angleDefinition`、`layerOrder=weapon_front`、合法 mask 策略，以及 runtime 索引与 manifest 的逐项双向一致。
2. runtime loader 只按 `config/hero-weapon-layer.ts` 加载已验证的正式资源；图片缺失或解码失败时仅绘制身体，并把 `hero-weapon-missing:<bodyFrame>` 写入 preview asset gate。预检失败为非零退出，不能以空手降级把 CI 判为通过。

运行时不做文件 SHA 运算；SHA 是构建/预览门禁，避免把资源完整性责任转嫁给玩家设备。

## 3. 类型与 profile 接口

新增只读配置 `config/hero-weapon-layer.ts`，不把素材坐标散写进渲染器：

```ts
type WeaponLayerOrder = 'weapon_front';
type WeaponOcclusion =
  | { kind: 'none' }
  | { kind: 'body-alpha-tight-fist-roi'; maskSrc: string; maskSha256: string };

interface WeaponLayerFrame {
  bodySrc: string;              // 以 body frame 完整路径作稳定键
  weaponSrc: string;            // 正式 assets/characters/hero/weapon45 路径
  weaponSha256: string;
  gripPointPx: readonly [number, number];
  fistCenterPx: readonly [number, number];
  angleDeg: number;             // 预检/回归元数据，本批不作运行时旋转
  layerOrder: WeaponLayerOrder;
  occlusion: WeaponOcclusion;
}

type WeaponLayerProfile = Readonly<Record<string, ReadonlyMap<string, WeaponLayerFrame>>>;
export const WEAPON_LAYER_PROFILES: WeaponLayerProfile = { hero: HERO_WEAPON_FRAMES };
```

键为 `spriteKey → bodySrc`，而不是 `actor.id`、显示名、帧数组下标或 `facing` 猜测。渲染器先沿既有 `directionalFrameOf` 取得 `(clip, facingHex, ordinal)`，再从同一 hero directional profile 得到实际 body path，并用其查询武器层。这样第二批 cast 只需增加资源、manifest 行和 map 项；不改 session、数值或选帧逻辑。

`maskPolicy` 的裁决：它是**配置化的资源契约**，不是逐帧可执行脚本。当前唯一实现枚举为 `body-alpha-tight-fist-roi`（映射到上面的 `kind`）；每帧差异只由 `maskSrc` 表示。未来增加别的遮挡算法，先扩枚举和预检，再由新需求卡启用，禁止字符串自由发挥。

## 4. Canvas 绘制管线

对每一个已排序角色，现有绘制次序扩为：

```text
地形 → hero 身体 → 预合成 sword-minus-fist 覆盖层 → HUD → world FX → 组件/UI
```

具体规则：

1. 按现有 `left/top/w/h` 绘制空手身体；其脚底比例、`feetOffsetPx`、移动插值与死亡判定均零改。
2. 武器源与身体源都是同尺寸 240×320 画布，覆盖层以**相同**的 `left/top/w/h` 绘制；本批旋转中心为“无”，不调用 `translate/rotate`。握点/拳心/角度由预检确认它们已在源图中实现。
3. 有 mask 时，loader 在离屏 240×320 canvas 一次性预合成：先 `source-over` 绘制 weapon，再 `globalCompositeOperation='destination-out'` 绘制 tight-fist mask，得到剑层在拳区挖孔的缓存。合成结果再绘回主 canvas，底下先画好的身体拳部自然露出。
4. 不使用 `destination-in`：它会保留拳区内的剑、裁掉剑身，语义相反。也不把 mask 直接 `source-over` 到主 canvas，避免将 alpha 遮罩画成可见色块。
5. `dead` 和 `jump` 不查询武器层；跳跃、死亡保持空手，严格遵从本次范围。其它未配置身体帧也保持空手并报开发诊断。

这保证 T25 world FX 仍在人物/HUD 后绘制，T27 directional 仍负责身体选帧，武器层不改两者的时序或资源分支。

## 8. 风险时间轴

现在的首要风险是第二批前的四个消费帧缺口：若把“临时空手”误标为全状态完成，会在基本攻击和右下行走中出现武器闪断。一个月内最易爆的是资源完整性债：若让 production loader 直接引用 `_trial/`，候选清理或重新生成会造成静默坏链。两到三个月后才是资源驻留与包体债：本卡先按场景预加载 26 张，并把分包/LRU 留给资源工程卡，禁止现在扩大到通用资源系统。
