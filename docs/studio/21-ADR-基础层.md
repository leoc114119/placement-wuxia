## ADR-001 原生 Canvas 2D 渲染循环与场景管理方案

**状态**：✅ 已采纳（2026-08-19 Leo 审批）

### 背景
- 技术栈锁死：TypeScript + 原生 Canvas 2D，无引擎；微信小游戏**无 DOM**。
- MVP 需要：主循环、场景切换（挂机主界面 / 6v6 战斗演出）、倍速与快进。
- 风险：自研渲染/场景框架可能失控；引入第三方又违背锁死技术栈。

### 决策
- 自研**最小 SceneManager**（约百行级）：场景实现统一接口 `onEnter/onExit/update(dt)/draw(ctx)`，`game.ts` 持单例，MVP 用 `switch` 切换。
- 主循环：`requestAnimationFrame`（微信小游戏全局提供，`setTimeout` 兜底）；**固定逻辑步长** `LOGIC_TICK=50ms`，逻辑不跟帧率走。
- 倍速在**逻辑层**做时间缩放（1x/2x/4x/快进到结果），渲染仍逐帧。
- 整帧重绘 Canvas 2D；绘制分层：背景 → 棋盘 → 单位 → 特效 → UI。
- UI 控件（按钮/面板命中）用 canvas 自绘 + 简单的矩形/九宫格命中检测。

### 理由
- 6v6 战棋 + 放置 UI 的渲染复杂度低，自研 200 行内可控，符合"打开文件 10 秒能看懂"。
- 固定逻辑步长是放置/战斗倍速最稳的基石（变速不丢帧、不掉结算）。
- 无 DOM 环境排除了 DOM UI 方案，自绘是唯一一致路径。

### 影响 / 代价
- 所有画面走 canvas：按钮九宫格切图、文本绘制（`ctx.fillText`）、像素比适配（`dpr`）需自管。
- UI 命中检测要自己写（无 HTML 事件），MVP 用矩形命中即可。
- Canvas 真实渲染效果 CodeBuddy 测不了 → 交 Leo 微信环境验收（诚实边界）。

### 备选被否理由
| 备选 | 被否理由 |
|---|---|
| WebView(DOM)+canvas 混合 | 小游戏环境无 DOM 组件；风格与性能不统一；违背技术栈锁死 |
| 引入 Pixi.js / Phaser | 违背"原生 Canvas 2D"锁死；包体膨胀（主包 ~4MB 限制） |
| Cocos / Laya 引擎 | 技术栈锁死"原生 Canvas 2D"，直接排除 |

## ADR-002 "客户端只展示 / 后端只结算"的边界与防作弊约束落地

**状态**：✅ 已采纳（2026-08-19 Leo 审批）

### 背景
- 核心防作弊诉求：数值唯一真值在云函数；客户端不算数值。
- 但纯客户端展示会遇到两个现实问题：① 离线收益 UI 需要即时展示（不能等网络）；② 战斗是 6v6 全自动，若完全等云端结算，演出与结算如何分离。

### 决策
- **三条硬规则**：
  1. **公式只在云函数 settle**：客户端 `config/numbers.ts` 只放**只读展示参数**（倍速档、文案阈值、动画时长等），不含任何结算公式（`core.js` 不打包进客户端）。
  2. **客户端允许"预估"，但预估永不权威**：UI 可用展示参数算近似值做动画/文案（标注"约"），不落库、不参与任何校验；真实值一律以 settle 返回的 `delta/player` 覆盖。
  3. **云端全量校验**：settle 内做时间戳（用 `serverTs` 与 `lastSettleAt` 差）、资源、前置、武学已学、幂等（requestId）校验；扣减走云数据库事务/原子更新。
- **战斗结算与演出分离**：战斗在云端一次性跑完，返回 `battleLog`（纯动作序列）；客户端 Battle 场景只做**播放器**，不做任何判定。

### 理由
- 防作弊在源头：客户端没有公式，改包也拿不到权威数值。
- 战斗"云端跑完 + 本地播放 log"既保住防作弊，又让演出流畅（log 驱动动画，无逐帧请求）。
- 预估只用于展示，避免"离线收益必须等网络"的体验断层。

### 影响 / 代价
- 离线收益 UI 有"预估 ≠ 最终"的毫秒级误差，需在文案上标注"约"。
- settle 云函数承担全部校验与结算逻辑 → 必须是 `core.js` 纯函数 + DB 薄壳，否则不可测（见 `23-测试策略` §4）。
- 所有数值改动只发生在云函数侧；客户端只能改展示层 → 改数值不发版客户端，但**验证成本落在云端测试**。

### 备选被否理由
| 备选 | 被否理由 |
|---|---|
| 客户端先结算再同步 | 作弊面大（改内存/改请求即可刷资源），违背防作弊第一性 |
| 纯客户端无后端 | 与 02 技术选型（云开发防作弊）直接冲突 |
| 战斗逐 tick 请求云端判定 | 请求量爆炸、演出卡顿；不如"一次跑完 + log 播放" |

## ADR-003 云函数接口契约冻结的字段设计

**状态**：✅ 已采纳（2026-08-19 Leo 审批）

### 背景
- 守则 4"接口先定"：云函数接口、数据结构在开工前定死，按契约写。
- 云开发按调用计费、函数数量需克制；客户端与云函数分别部署，字段不一致会埋雷。

### 决策
- 统一返回信封：`{ code, msg, data }`；`code=0` 成功，错误码表 v0.1 冻结（见主架构 §5.4）。
- **3 个云函数**：`settle`（所有结算动作，以 `action` 枚举聚合）、`save`（显式落库兜底）、`load`（读档）。
- **settle 以 `action` 聚合**：`idle` / `learn` / `battle` / `mapUnlock` / `heal`（v0.1 先实现前 3）。
- 所有请求带 `requestId`（幂等）与 `clientTs`（仅日志）；`playerId` 以云函数上下文 `OPENID` 为准，客户端可不传。
- 契约类型集中在 `types.ts`（客户端）与 `cloudfunctions/common/contract.js`（后端副本），靠契约测试对齐。

### 理由
- 一次冻结减少反复改云函数；`action` 聚合避免"一个功能一个函数"的数量膨胀（云开发冷启动与费用）。
- `requestId` 幂等是放置类高频结算（周期/退出/回前台）防重复发放的必需品。
- `OPENID` 为准杜绝伪造 playerId。

### 影响 / 代价
- 字段变更必须走 ADR 更新流程（本文件修订 + 主架构 §5 同步），不许悄悄加字段。
- 云函数侧要维护契约副本 → 增加契约测试成本（但可自动化）。

### 备选被否理由
| 备选 | 被否理由 |
|---|---|
| REST HTTP（云托管 API） | 多一层网关与鉴权；小游戏 `callFunction` 更简单，冷启动与权限天然管理 |
| 每功能一个云函数 | 函数数量膨胀（学武/战斗/刷怪/买药…），冷启动面大、管理成本高 |
| 客户端传 Player 快照给 save | 快照不可信（可伪造），违背防作弊；save 只做显式落库确认 |

## ADR-004 数值集中 config/numbers.ts 与类型约束 types.ts 的咬合方式

**状态**：✅ 已采纳（2026-08-19 Leo 审批）

### 背景
- 守则 2"数值集中"与守则 5"类型约束"需要同时满足：数值集中一处，且数据结构有类型约束。
- 若 `config/numbers.ts` 无类型，配置漏字段、改错字段编译期发现不了。

### 决策
- `types.ts` 定义 `GameNumbers` 接口（含展示配置全部字段）与所有数据结构（`Player`、`Skill`、`BattleLogEntry`、契约类型等），**纯类型、零运行时**。
- `config/numbers.ts` 以 `export const NUMBERS: GameNumbers = {...}` 实现该接口，**单向依赖 config → types**。
- 其他模块只读 `NUMBERS`，禁止 `import { 某裸值 }` 后再加工成新数值；禁止任何文件硬编码数值（eslint 规则 + 静态扫描）。
- 云函数结算公式所需常数**不**在客户端 `numbers.ts`，而在云函数 `settle/core.js` 内的独立配置区（与客户端物理隔离）。

### 理由
- 类型即文档：改配置漏字段立刻编译报错，AI/人都不易手滑。
- 单向依赖保证 `types.ts` 是唯一依赖根，无循环。
- 客户端展示参数与云端结算公式物理分离，守住 ADR-002 边界。

### 影响 / 代价
- 加一个配置字段 = 改 `types.ts` 接口 + `numbers.ts` 值，两处同步（一次改两个文件，但编译期兜底）。
- 云函数侧常数不受客户端类型约束 → 用契约测试覆盖"两端数值一致性"（如客户端展示参数与云端公式的联动字段）。

### 备选被否理由
| 备选 | 被否理由 |
|---|---|
| 类型与值放同一文件 | 混合职责，违背"模块职责单一"；types.ts 是依赖根，掺值会产生运行时循环风险 |
| 纯对象无类型 | 漏字段/错类型编译期不报，违背守则 5 |
| 客户端与云端共享 numbers.ts | 公式进客户端包 → 违背防作弊（ADR-002） |

## ADR-005 存档结构设计

**状态**：✅ 已采纳（2026-08-19 Leo 审批）

### 背景
- 存档要：安全（防作弊）、可迁移（后期加字段）、可回滚（版本）、防时间回拨。
- 云数据库 collection `players`，文档 id = OPENID。

### 决策
- **单文档存档**：一个 `Player` 文档承载全部状态（结构见主架构 §5.3b），包含 `version`、`lastSettleAt`（服务端写入）。
- **云端为唯一真值**：settle 事务内更新；客户端本地缓存只是启动快照，退出不写本地权威存档。
- **服务端时间为锚**：所有挂机结算用 `serverTs − lastSettleAt`；`lastSettleAt` 只由服务端写，防回拨。
- **版本迁移**：`version=1` 起步；改结构时新增迁移函数（`migrate(fromVersion, doc)`），load 时执行。
- **save 语义**：显式落库确认/心跳，不接收客户端快照（ADR-003）。

### 理由
- 单文档简单可靠，MVP 无跨集合一致性需求；`OPENID` 即文档 id，天然防串号。
- 服务端时间为锚解决放置游戏最典型的"回拨刷挂机收益"。
- version + 迁移函数让"不动历史、小步改"在数据层也可行（旧档可升不可废）。

### 影响 / 代价
- 单文档在高频写（在线每 60s 结算）下有并发写压力 → settle 用原子更新/事务，冲突时重试。
- 存档字段变更必须配迁移函数，禁止直接改结构不迁移。
- 离线收益校验依赖 `lastSettleAt` 正确性 → 测试要点（`23-测试策略` §4 模拟运行用例）。

### 备选被否理由
| 备选 | 被否理由 |
|---|---|
| 分集合存（player/资源/武学分表） | MVP 无此复杂度；跨集合事务成本高，收益为零 |
| 本地存储为主 | 易作弊、易丢档（清缓存即消失），违背"云端唯一真值" |
| 客户端传时间戳结算 | 可伪造，违背防回拨 |
