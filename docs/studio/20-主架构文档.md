## 0. 一句话架构

> **原生 Canvas 2D 客户端只做「展示与演出」，数值唯一真值在微信云函数 settle；模块单向依赖、禁止循环；接口在开工前冻结。**

## 1. 架构总览

```
┌─────────────────────────────────────────────────────────────┐
│                     客户端（微信小游戏，TypeScript）             │
│                                                             │
│  game.ts 入口                                               │
│   └─ SceneManager（场景切换）                                 │
│        ├─ ui/（只读展示 + 演出播放，零计算）                     │
│        ├─ systems/（只做"发请求"与"展示态管理"，不算数值）        │
│        └─ net/cloud.ts（云函数调用封装，唯一网络出口）            │
│                                                             │
│  config/numbers.ts（只读展示配置，非权威）   types.ts（类型单一来源）│
└──────────────────────────┬──────────────────────────────────┘
                           │ wx.cloud.callFunction（唯一通道）
┌──────────────────────────▼──────────────────────────────────┐
│                 微信云开发（后端，Node.js）                     │
│                                                             │
│  cloudfunctions/settle（数值结算唯一真值，全部校验+落库）         │
│  cloudfunctions/save  （显式落库兜底/心跳）                     │
│  cloudfunctions/load  （读档）                                │
│  云数据库 collection: players（唯一权威存档）                    │
└─────────────────────────────────────────────────────────────┘
```

**分层原则（沿用 02 规格）：客户端只展示，后端只结算；公式只在后端。**

## 2. 模块边界与依赖规则

### 2.1 模块职责总表

| 模块 | 职责 | 禁止做的事 | 依赖方向 |
|---|---|---|---|
| `types.ts` | 全部数据结构/接口/枚举定义，**纯类型，零运行时逻辑** | 不 import 任何业务模块；不写函数体 | 被所有模块依赖（依赖根） |
| `config/numbers.ts` | 客户端只读展示配置（倍速档位、文案阈值、动画时长等）；**非数值权威** | 不含结算公式；不被 UI 之外模块反向依赖 | → types.ts |
| `game.ts` | 入口：启动、主循环、SceneManager 装配 | 不含业务计算；不直接调云函数 | → scenes → ui/net/config |
| `ui/` | 画界面、播放演出；**只读**展示字段 | 不算数值；不直接调云函数；不持有游戏状态（状态由场景/系统持有） | → types.ts（读展示字段）、config |
| `systems/` | 组织玩法流程：发起云函数调用、维护"展示态"（战斗演出序列、结算结果缓存） | 不实现数值公式；不画界面 | → net、types |
| `net/cloud.ts` | 云函数调用唯一出口：封装 `wx.cloud.callFunction`、错误归一、requestId 生成 | 不包含任何玩法逻辑 | → types（契约类型） |
| `scenes/` | 场景对象（Boot/Main/Battle 等），实现 update/draw/onEnter/onExit | 不包含数值计算 | → ui、systems、net |
| `cloudfunctions/settle` | **数值结算唯一真值**：全部公式、校验、原子扣减、落库 | 不依赖客户端任何代码 | → 云数据库 |
| `cloudfunctions/save` | 显式落库兜底/心跳 | 不做数值计算 | → 云数据库 |
| `cloudfunctions/load` | 读档返回 | 不做数值计算 | → 云数据库 |

### 2.2 依赖方向（防循环）

```
types.ts  ←  config/numbers.ts  ←  ui/  ←  scenes/  ←  game.ts
                ↑                    ↑
           systems/  ──────────────┘（systems 只被 scenes 用）
                ↑
           net/cloud.ts  ←  systems/
                ↑
           cloudfunctions/（契约对齐，不物理依赖）
```

**三条硬规则：**
1. **单向依赖**：`game → scenes → systems/ui → net → types`；`config → types`；禁止反向。
2. **禁止循环**：`ui` 不得 import `systems`；`systems` 不得 import `ui`（各自通过 `scenes` 装配；数据经 types 传递）。
3. **后端不依赖前端**：云函数与客户端仅靠 `types.ts` 里的契约类型"对齐"，不共享代码文件（云函数独立部署）。

### 2.3 依赖检查落地

- 在 `tsconfig` 用 `paths` 别名（`@types`/`@ui`/`@systems`/`@net`/`@config`）+ 自定义 eslint rule：禁止 `ui/` import `systems/`、禁止 `systems/` import `ui/`、禁止 `game.ts` 之外文件调 `wx.cloud`。
- 静态检查脚本扫描 import 图，发现循环依赖 → 打回（见 `23-测试策略.md` 静态检查项）。

## 3. 数据流：挂机 → 结算 → 存档 完整链路

### 3.1 总链路（标注云函数边界）

```
[客户端]                          [云函数边界]                  [云端]
启动
 ├─ net.load({}) ────────────────► load ───────────────► 读 players 集合
 │                                 ◄──── { code, data:{ player, serverTs } }
 ├─ 展示 player（只读）
 │
挂机中（客户端本地计时，仅驱动 UI 动画）
 ├─ 到结算节奏（在线每 60s / 退出时 / 回前台时）
 │   net.settle({ action:'idle', offline:false }) ───► settle
 │       ├─ 校验：playerId(OPENID)、requestId 幂等、时间戳
 │       ├─ 结算：按 serverTs − lastSettleAt 产学点/熟练度
 │       ├─ 原子更新 players 文档（事务）
 │       ◄──── { code, data:{ delta, player, serverTs } }
 ├─ 用 delta 播动画（学点跳动），player 覆盖展示快照
 │
学武功 / 战斗 / 治疗等 → 同理走 settle（action 区分，见 §5）
 │
退出
 ├─ net.save({}) ────────────────► save（兜底落库确认）
```

### 3.2 关键边界规则

| # | 规则 | 说明 |
|---|---|---|
| B1 | **客户端永远不结算** | 客户端拿到的 `player` 只是"展示快照"；所有增长只来自 settle 返回 |
| B2 | **结算时点集中** | 在线周期结算、退出结算、回前台补结算、离线首次进入补结算；不逐秒请求 |
| B3 | **服务端时间为真** | 所有挂机时长以 `serverTs` 与存档 `lastSettleAt`（服务端写入）之差计算，客户端时间仅用于节奏提示 |
| B4 | **幂等** | 每次请求带 `requestId`；settle 按 requestId 去重，网络重试不重复结算 |
| B5 | **存档唯一真值在云端** | 客户端本地缓存仅是启动快照，不持久化为权威 |

### 3.3 离线收益的"预估 vs 真实"

- 客户端**允许**在 UI 上显示"离线预估收益"（用 `config/numbers.ts` 中**只读展示参数**算一个近似值，仅用于动画/文案，**不落库、不权威**）。
- 真实收益 = settle 返回的 `delta`。预估与真实可能差毫秒级，展示文案标注"约"。
- 该设计写入 ADR-002。

## 4. 渲染循环与场景管理

### 4.1 主循环

```
wx 启动 → game.ts 初始化 Canvas（wx.createCanvas() 主屏）
       → 装配 SceneManager → Boot 场景加载资源 → 切 Main
       → requestAnimationFrame(loop)
loop(dt):
  1) 固定逻辑步长：累计时间，按 LOGIC_TICK（默认 50ms）执行 scene.update(tick)
     —— 逻辑与渲染分离，倍速/暂停/快进在逻辑层做时间缩放
  2) scene.draw(ctx)：整帧重绘（Canvas 2D，全量绘制即可，6v6 规模足够）
  3) 调度下一帧
```

| 项 | 决策 |
|---|---|
| 渲染 API | `CanvasRenderingContext2D`（`wx.createCanvas().getContext('2d')`） |
| 帧循环 | `requestAnimationFrame`（微信小游戏全局提供），降级 `setTimeout` 兜底 |
| 逻辑步长 | 固定 `LOGIC_TICK=50ms`，逻辑不跟帧率走（防变速/掉帧错乱） |
| 倍速 | 战斗场景支持 1x/2x/4x/快进到结果：逻辑步长倍数累加，渲染仍按帧 |
| 绘制顺序 | 每场景内固定分层：背景 → 地图/棋盘 → 单位 → 特效 → UI 面板 |

### 4.2 场景管理（最小实现，无第三方框架）

```
SceneManager（单例，由 game.ts 持有）
  ├─ switch(sceneId)   切换：current.onExit() → 新 scene.onEnter() → current = new
  ├─ push/pop          （预留，MVP 仅用 switch）
  ├─ scene 接口        onEnter() / onExit() / update(tick) / draw(ctx)
```

| 场景 | 职责 | 说明 |
|---|---|---|
| Boot | 初始化、加载配置、首帧 | 资源极少，加载即完成 |
| Main | 挂机主界面：学点跳动、武功面板、进入战斗 | 挂机循环的 UI 宿主 |
| Battle | 6v6 战斗演出：按 settle 返回的 battleLog 播放 | **纯演出**，无战斗计算 |
| （后续）Map / Learn / Heal | 视冲刺拆分扩展 | 同一套 Scene 接口 |

**关键约束**：Battle 场景**不计算**战斗——战斗结果由 settle 一次性返回 `battleLog`（每 tick 的动作序列），客户端只按 log 播放动画（见 ADR-002 / 契约 §5.2）。

## 5. 云函数接口契约（冻结版，开工前定死）

> 统一信封：`{ code, msg, data }`；`code=0` 成功，非 0 失败（错误码表见 §5.4）。
> 传输经 `wx.cloud.callFunction({ name, data })`，**不是 HTTP**；下文以"请求/响应"表述逻辑契约。

### 5.1 通用字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `requestId` | string | ✅ | 客户端生成的幂等键（uuid），settle 按此去重 |
| `clientTs` | number | ✅ | 客户端发送时间戳（仅日志/抖动统计，**不参与结算**） |
| `playerId` | string | 否 | 预留；安全上以云函数上下文 `OPENID` 为准，客户端不传也合法 |

### 5.2 `settle`（数值结算，唯一真值）

**请求**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `action` | enum | ✅ | `idle` / `learn` / `battle` / `mapUnlock` / `heal`（v0.1 先实现前 3，后 2 预留） |
| `payload` | object | 按 action | 见下表 |

| action | payload 字段 | 说明 |
|---|---|---|
| `idle` | `offline: boolean` | 在线周期/退出/回前台统一走此；offline=true 表示离线补结算 |
| `learn` | `skillId: string` | 学武功；云端校验：学点/银两/前置武功等级/是否已学 |
| `battle` | `stageId: string` | 战斗结算；敌方阵容/掉落由云端按 stageId 查表；战斗在云端跑完 |
| `mapUnlock` | `stageId: string` | （预留）解锁判定 |
| `heal` | `itemId: string` | （预留）买药/治疗 |

**响应 data**

| 字段 | 类型 | 说明 |
|---|---|---|
| `delta` | object | 本次增量：`{ studyPoint, exp, silver, loot[], skillUps[] }`（学点/实战/银两/掉落/武学升级），UI 动画用 |
| `player` | Player | 结算后的**完整新状态**（展示快照），结构见 §5.3 |
| `serverTs` | number | 服务端结算时间（后续 idle 结算的基准） |
| `battleLog` | object[] | **仅 action=battle 返回**：每 tick 动作序列（单位、行为、目标、伤害/位移），供 Battle 场景播放；结构在 types.ts 冻结 |

### 5.3 `save` / `load`

**save（显式落库兜底）**

| 请求 | 响应 |
|---|---|
| `{ requestId, clientTs }`（playerId 用 OPENID） | `{ code, msg, data:{ saved: true, serverTs } }` |

> 语义说明：settle 每次已事务落库，save 仅作为退出/心跳时的**显式持久化确认**与将来多人阶段的占位；**客户端不传 snapshot**（不可信）。

**load（读档）**

| 请求 | 响应 |
|---|---|
| `{ requestId, clientTs }`（playerId 用 OPENID） | `{ code, msg, data:{ player, serverTs } }`；无档时 `data.player = null`，客户端引导建号 |

### 5.3b Player 存档结构（types.ts 冻结骨架）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | = OPENID（云端写） |
| `version` | number | 存档版本，迁移用（当前 1） |
| `level` | number | 主角等级（展示） |
| `stats` | object | 六维：臂力/根骨/机敏/定力/悟性/胆识 |
| `resources` | object | `{ studyPoint, silver, exp, neili }`（学点/银两/实战/内力） |
| `learnedSkills` | Skill[] | 已学武学（含等级/熟练度） |
| `equipped` | object | 当前武器/防具（决定范围形态与攻防） |
| `currentMap` | string | 当前地图/关卡 id |
| `unlockedMaps` | string[] | 已解锁关卡 |
| `lastSettleAt` | number | 服务端最后结算时间（唯一权威） |
| `status` | enum | 正常 / 失血过多（推图失败惩罚，12 设计） |

### 5.4 错误码表（v0.1 冻结）

| code | 含义 | 客户端行为 |
|---|---|---|
| 0 | 成功 | — |
| 1001 | 参数校验失败 | 提示后重试 |
| 1002 | 资源不足（学点/银两） | 提示，刷新展示 |
| 1003 | 前置条件不满足（武学前置/等级） | 提示 |
| 1004 | 重复请求（幂等命中，返回已结算结果） | 静默使用返回 |
| 1005 | 存档不存在 | 引导建号 |
| 2001 | 云数据库错误 | 提示稍后重试 |
| 2002 | 内部错误 | 提示稍后重试 |

### 5.5 契约冻结纪律

- 契约字段**开工前定死**；变更须走 ADR 流程（见 `21-ADR-基础层.md` ADR-003）。
- `types.ts` 中定义 `SettleRequest / SettleResponse / Player / BattleLogEntry` 等契约类型，客户端 `net/cloud.ts` 与云函数两侧按同一类型实现（云函数侧复制维护，靠契约测试对齐，见 `23-测试策略.md` §4）。

## 7. 架构评审：对照 AGENTS.md 六条施工守则

| # | 施工守则 | 本架构如何保证可实现 | 结论 |
|---|---|---|---|
| 1 | 增量开发：一次只做指定功能 | Epic/Story 拆分到可验收粒度（`22-冲刺计划`），每 Story 只动指定文件；`23-测试策略` 的"审查记录"跟踪改动范围 | ✅ 可实现 |
| 2 | 数值集中：公式只在 `config/numbers.ts` | 本架构明确 **`config/numbers.ts` 只是客户端只读展示配置，结算公式唯一真值在云函数 settle**（守则的"公式只在后端"在 02 已定）；eslint 规则 + 静态扫描禁止其他文件硬编码数值 | ✅ 可实现（含一处需澄清：见 §8 R1） |
| 3 | UI 只展示：UI 只读数据画出来 | `ui/` 零计算、不持有状态、不直接调云函数；`systems/` 负责发请求与展示态，`ui/` 只消费 | ✅ 可实现 |
| 4 | 接口先定：云函数接口开工前定死 | 本文件 §5 契约冻结 + ADR-003；`types.ts` 契约类型两侧共用 | ✅ 可实现 |
| 5 | 类型约束：数据结构定义在 types.ts | `types.ts` 为依赖根；`config/numbers.ts` 以 types 类型实现（ADR-004）；eslint 强制 | ✅ 可实现 |
| 6 | 不动历史：验收过的不整体重写 | Story 验收门禁（Leo 三关）+ 审查记录；小步改，重构走单独 Story | ✅ 可实现 |
