## 3. 流转流程

```
我方装卡（需求表+数据+用例+验证）→ DoR 全过 → 发单
  → ZCode 领单 → 【答疑阶段（Leo 2026-08-22 定）】
      · 通读任务卡引用的规格文档 + 素材清单
      · 产出问题清单 questions/Q1-Txx.md：理解复述（概述要做的事）+ 疑义逐条（# | 问题 | 引用依据 | 建议）
      · 无疑问也要交「无疑问 + 理解复述」，不得跳过
  → 我方一轮确认：CodeBuddy 出 answers/A1-Txx.md 汇总答复；需求级歧义项 Leo 拍板
  → CodeBuddy 宣布「✅ 确认开工」→ 任务卡移 working/（此前留 inbox/）
  → ZCode 按需求表施工（架构自定，边界不可碰，需求含糊随时再问）
  → ZCode 提交（代码层自测 DoD：三零+用例+node 模拟；GUI 项标"留 L 环点验"）
  → CodeBuddy C 环：六项检查 + 跑用例 + 审计门脚本复跑 + 对照方案建议提问题（ZCode 需回应）
      —— UI 视觉类验收不在 C 环自证范围，凭工具层证据（像素审计/坐标定位）+ L 环目验
  → Leo L 环按验证要求 GUI 点验 → 签字 → 下一张卡
```

> **三环验收分工（08-22 定版）**：Z 环=代码层自检；C 环=工程审查+工具层审计门；L 环=真实环境 UI 目验。任何一环不得用「自己生成的视觉产物」自证通过。
> **答疑期状态口径**：任务卡留 inbox/，index.json `col: "questions"`；确认开工才移 working/（与 tasks/README 状态机同步）。

## 6.5 主架构七步工作流（v0.6 增 · 2026-09-02 Leo 定版）

主架构（独立 5.3 对话）参与研发的标准闭环，每次供主架构提示词按此模板：

1. **答疑**：主架构先输出理解复述+疑义清单 → PM/Leo 确认后才准动笔（提示词两段式：第一段只答疑，第二段才写方案）
2. **出设计方案**：按确认的理解落盘方案文档（架构/接口/任务拆分建议）
3. **Leo 对齐**：方案开放问题与关键决策交 Leo 拍板
4. **分发前后端**：主架构按方案拆单（FE/BE 按方案参与，可双线同单，见 §6.6 铁律 2），PM 落卡发单
5. **主架构技术验收**：开发完成后主架构审代码（架构符合度/接口契约/质量；v0.7 起加验：实现与方案一致性/有无偷懒/有无过度设计/易错点数据结构复测，见 §6.6 铁律 7）——验收链第一环
6. **Leo 验收**：L 环终验
7. **交付 PM**：归档收口、任务箱关账

> 实战首例：战斗界面接入（技术方案 v0.1 cb064bd，T-B1/T-F1 → T15/T16）。首轮教训：主架构未走答疑直接出方案（靠开放问题清单兜底），v0.6 起固化为两段式。

### 6.5b 验收期调整分轨（2026-09-02 Leo 定版）

| 轨 | 适用 | 流程 |
|---|---|---|
| **直接轨** | 表现层调整优化、细微美术布局微调（改了马上能看、不动需求文档） | Leo 直接对话子代理执行；子代理改完在任务箱线程登记一行 |

## 6.6 研发线流程铁律（v0.7 增 · 2026-09-03 Leo 九条定版 · 每个需求/缺陷都必须走）

> 依据：09-02 战斗缺陷全景复盘（`docs/reviews/战斗缺陷全景复盘-2026-09-02.md`）+ Leo 九条拍板。
> 适用：研发线一切需求与缺陷，无例外；与 §6.5 七步工作流、§3 流转流程叠加生效。

### 6.6a 九条铁律

| # | 铁律 | 环节 | 执行者 |
|---|------|------|--------|
| 1 | **口径复述点头**：Leo 定版 → PM 复述原文 → Leo 点头 → 原文入规格（带条目号），后续一切引用条目号 | 需求进线 | PM→Leo |
| 2 | **拆单按方案不按模块**：主架构分析需求出方案后拆单给前端/后端——不按模块归属切，一个任务可双线参与 | 派单 | 主架构拆单，PM 落卡 |
| 3 | **不打断不接管**：子代理独立完成自己的任务；PM/他人可查状态，禁止中断、接管、并发编辑其工作区 | 研发过程 | 全员 |
| 4 | **测试用例先行**：子代理领单第一交付=完整测试用例清单（脚本化自测），先列用例后实现；缺陷单=复现红用例先行 | 领单 | 子代理 |
| 5 | **查状态代替超时判定**：不设超时中断，卡不卡查状态即知 | 研发过程 | PM |
| 6 | **回执进固定表格**：交付回执统一写 `tasks/回执总表.md`（一行一交付），不再新建 per-task md 文档 | 交付 | 子代理/PM |
| 7 | **主架构双职责**：① 方案必须附**易错点清单**（容易出问题的点给子代理参考，重点问题做更完善设计）；② 交付后主架构参与验收：实现与方案逻辑一致性/有无偷懒/有无过度设计/易错点数据结构复测 | 方案+验收 | 主架构 |
| 8 | **PM 行为测试**：C 环不只复跑脚本，必须通过子代理交付的**模拟接口**（demo 调试挂载点/测试 harness，随任务交付并附使用说明）实测行为 | C 环 | PM |
| 9 | **bug 派单先主架构分析**：先定位关键点再指定处理子代理；关键点不确定 → 前后端**一起查**，出联合调查报告后再动手——严防"病在前端、后端瞎改" | 缺陷派单 | 主架构→子代理 |

### 6.6b 链路视图

```
需求轨：Leo 反馈/定版
  →①复述点头+原文入规格 →⑨/②主架构答疑+分析+方案(附易错点清单) →②拆单(可双线)
  →④领单先交用例清单 →③⑤研发(不打断/查状态) →④脚本自测+四门自检(输出原文)
  →⑦主架构验收(一致性/偷懒/过度设计/易错点复测) →⑧PM C环(四门复跑+模拟接口行为测试)
  →Leo L环 →⑥回执表格+归档(红转绿登记/每任务一 commit)

缺陷轨：Leo 反馈
  →PM 登记现象原文+缺陷号+锁红用例(行为套件红名单)
  →⑨主架构分析定位(不确定→前后端联合调查出报告，禁止未调查先动手)
  →指定子代理 →④复现红用例先行 →修复 →⑦⑧验收同上 →红转绿登记
```

### 6.6c 角色边界（09-03 Leo 纠正确认）

- **PM**：需求保真（复述点头）/缺陷登记/工单起草/C 环复跑+行为测试/流程执法/文档——**不诊断根因、不亲手改码、不给工单附修法**（09-02 误诊与并发改码两案例为戒）。
- **主架构**：枢纽职责——分析定位、方案+易错点、拆单、验收。
- **子代理**：查修一体+测试先行，自主完成、不被打断。
- 修复完成的唯一定义=**红转绿+无新红+四门自检输出原文**（四门见复盘报告附录 B.3）。
