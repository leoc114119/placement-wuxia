## 一、普攻六向试点复盘

### 1.1 最终产出与方法论

- **产出**：`battle45/atk_{right,rightup,rightdown,left,leftup,leftdown}_{1,2,3}.png` 18 帧现役（另有 down 向 3 帧保留备用），六向总览 `atk_6dir_final.png`。
- **四件套方法论**（全部经实战验证）：
  1. **序列表法**：一个动作一张多格图（16:9 三格横排）连贯生成——帧间连贯/身位/比例天然一致。逐帧独立生成已判废（帧间不连贯，批 1a 26 分教训）。
  2. **母版+转面派生**：动作先在一个方向（right 正侧）做"母版"定稿（动作真源），其他方向以母版表当参照转面（配该向锚+白模朝向带）——保证"跨向同招"。左系=右系镜像零生成。
  3. **局部修正法**（Leo 授）：成品当主原图 img2img 只改指定部位（2 分/轮）——换手/幅度/方向微调的精准收敛手段，比从零重生成省且稳。
  4. **Leo 标注图法**：方向/方位类歧义由 Leo 在图上亲手画箭头定案，标注图直接作 img2img 参照——主会话无方位感，此为方位问题的终极交互。

### 1.2 问题全记录与根因分类

| # | 问题 | 损耗 | 根因类别 | 已有对策 |
|---|---|---|---|---|

### 1.3 成本模型

- **首套学费**：普攻六向试点总账 ≈28 分（其中作废/探索 24 分——方法未定型期的必然损耗）。
- **标准化后边际成本**（流程定型，从零生成一个新动作六向）：
  - 动作示意图绘制+Leo 过目：0 分
  - right 母版序列表：2 分（+局部修正余量 2~4 分）
  - rightup/rightdown 转面：4 分（+修正余量 2~4 分）
  - 左系镜像：0 分
  - **合计 ≈8~14 分/动作/角色**（对比首套 28 分，降 50%+；且一次定型后所有角色复用该流程）
- **对照外部成本**：AI 管线 $0.5~2/sprite（约 3.5~14 元/百张量级），画师手绘 $20~100+/sprite——本项目 2 分/张（≈0.28 元）的成本结构在 AI 管线里也属低位。

### 1.4 流程标准化（新动作 SOP v2，待落规范）

```
动作设计示意图（主会话 PIL 绘制，§1c 规格）
  → Leo 过目拍板（动作逻辑/幅度/方向——不达生成不动）
  → right 母版序列表（三参照：画风锚+该向锚+示意图，16:9）
  → 主会话目验（左右臂/幅度/连贯）→ Leo 过
  → rightup/rightdown 转面派生（母版表+对应锚+白模带）
  → 目验（跨向同招+刺向纵深+左右臂）
  → 局部修正法迭代（2 分/轮，上限 2 轮，不过升级 Leo 标注图）
  → 左系镜像派生（0 分）→ 入库
```

## 二、外部方案调研（2025-09 工业实践）

### 2.1 序列一致性的学术与工具前沿

- **Sprite Sheet Diffusion**（[arXiv 2412.03685](https://arxiv.org/html/2412.03685v1)）：以参考图保持角色一致性生成动作序列——学术确认"参考图锚定+序列生成"是正解，与我们"母版表当参照"同构。
- **专用工具成熟**：[PixelLab.ai](https://www.pixellab.ai/)（像素角色骨架动画）、[Retro Diffusion](https://www.retrodiffusion.ai/)（真像素网格输出）、[spritesheets.ai](https://www.spritesheets.ai/)（一致调色板输出）。
- **对我们**：mxai 接口（gpt-image-2）通用性强但非像素专精；PixelLab 类专用工具可作为"备份通道"评估（新管线选型挂账，不紧急——现管线已跑通）。

### 2.2 混合管线共识

工业社区（[SLYNYRD 2025](https://www.slynyrd.com/blog/2025/3/24/pixelblog-55-top-down-character-animation)、r/aigamedev 多帖）共识 = **AI 生成基础帧 + 人工/程序化清理**：
- 小尺寸像素画"一像素之差"毁一致性——肢体粗细/长度跨帧一致是核心质检点（对应我们的体宽锁/高度门）；
- 视频生成→抽帧→像素化路线可行但工程坑明确（**闪烁稳定化/调色板锁定/去运动模糊**三大件，[实践复盘](https://sarthakmishra.com/blog/building-animated-pixel-art-hero)）——对本项目为**备选路线**（若未来要流畅大动作），现阶段不引入（引外部视频模型成本与闪烁治理不划算）。

### 2.3 NPC 变体与成本共识

- **[确定性 palette swap 优先](https://www.reddit.com/r/gamedev/comments/1prj0f0/i_made_a_really_simple_free_online_palette_swap/)**：同款角色/服装换色变体=零边际成本（工具免费/程序化），远优于 img2img 逐个重生成——直接适配我们"同模敌人变体"需求。
- **AI 换装**（[SD inpaint+姿势保持](https://www.youtube.com/watch?v=7AIEIB-GSfg)）：结构性变化（不同款式衣服）才用 img2img，姿势/身份靠原图锚定——与我们局部修正法同原理。
- 成本对照：[AI vs 画师](https://www.sprite-ai.art/blog/ai-sprite-generator-vs-artist) 100 张规模 AI $50~200 vs 画师 $2,000~10,000+。

### 2.4 对本项目的吸收结论

| 外部做法 | 本项目动作 |
|---|---|
| 参考图锚定+序列生成 | 已实现（母版表法），保持 |
| AI 生成+程序化清理混合 | 已实现（归一/体宽锁/残留清除），保持 |
| palette swap 做 NPC 变体 | **新采纳**：进复用体系（§3.4） |
| 原图 inpaint 局部换装 | **新采纳**：换装主路线（§4） |
| 视频抽帧像素化 | 备选挂账（流畅大动作需求出现再评估） |
| 像素专精模型（PixelLab 等） | 备选挂账（现管线跑通不换道） |

## 三、复用体系设计：动作模板库 × 角色皮肤包

### 3.1 核心概念：动作与皮肤解耦

**关键认知（试点验证）**：动作的"可复用资产"是**设计+流程+prompt 骨架**，生成产物（帧图）不可跨角色直接复用——新角色形象不同，参照链里的画风锚/母版表必须换成新角色自己的。

```
动作模板库（一次建设，全角色复用）
├── 动作设计：示意图序列 + 动作逻辑文字定稿（Leo 已拍板的"剑术突刺三拍"等）
├── 流程模板：序列表构造参数 + prompt 骨架 + 验收 checklist（左右臂/纵深/连贯/幅度）
├── 门口径：分向/分姿势族的宽高比带、高度门、体宽锁
└── 方向派生规则：right 母版 → rightup/rightdown 转面 → 左系镜像

角色皮肤包（每角色一次建设）
├── 形象锚三件套：该角色各向待机锚（画风/体格/朝向真源）
├── 白模/朝向参照（全角色共用，已入库）
└── 该角色的服装/武器规格（§4）
```

**新角色/新敌人生产 = 动作模板库逐动作 × 该角色皮肤包重跑**：
1. 用该角色待机锚替换参照组里的形象锚位
2. 动作设计示意图/方向派生规则/prompt 骨架原样复用
3. 产出该角色全套动作帧


**目录约定（主架构建议，趁单角色期低成本升级四层）**：`assets/characters/{role_id}/{skin_id}/battle45/{action}_{dir}_{n}.png` + 每皮肤 `manifest.json`（帧清单/锚点/门检记录）——现 hero 单目录现状迁四层，为多角色/换装期预留，避免三轨并存蔓延。
### 3.2 成本模型（批量生成预算）

| 对象 | 帧数 | 生成成本估算 | 备注 |
|---|---|---|---|
| 主角全套（5 动作×6 向） | 5 动作×18 帧=90 帧产物 | ≈40~70 分 | 普攻流程已验证，其余动作照模板跑；含修正余量 |
| 敌人（山贼类，4 动作×6 向，无轻功） | 4×18=72 帧产物 | ≈32~56 分/敌 | 同模板；可再砍（见 3.3） |
| 同模敌人变体（换色） | 72 帧产物 | **≈0 分**（palette swap 程序化） | §3.4 |

### 3.3 敌人 NPC 的降本选项

1. **方向裁剪**：敌人在棋盘上朝向玩家的方向集可裁剪（如仅 down/斜向 4 向+镜像，砍到 3 向实绘）——**需 Leo 拍板战斗表现要求**；
2. **动作裁剪**：MVP 敌人=待机+行走+普攻+死亡（已定，无轻功无施放）；
3. **palette swap 变体**：山贼甲定稿 → 山贼丙丁戊换色派生（零生成），同关卡群怪不重样。

## 四、换衣与换兵器系统适配

### 4.1 三方案对比

| 方案 | 做法 | 成本/帧 | 优点 | 缺点 |
|---|---|---|---|---|
| **A. Paperdoll 分层**（[工业标准](https://gamedev.stackexchange.com/questions/210899/how-do-i-compose-rpg-character-with-different-equipment)） | 身体裸帧+服装层+武器层分部件绘制，FE 按固定 z 序逐帧叠加 | 服装部件按帧对齐绘制 | 一次部件化无限组合；FE 切换零成本 | **AI 生成流程难做部件对齐**（前后手遮挡关系/逐帧对位）；不同体型穿同装违和；MVP 收益低 |
| **B. AI 换皮重绘**（[inpaint 换装](https://www.youtube.com/watch?v=7AIEIB-GSfg) 同原理） | 服装设计定稿 → 逐帧 img2img"原样重绘仅换服装"（原图锚定姿势） | 2 分/帧 × 帧数 | 与现管线完全同构（局部修正法的推广）；视觉统一；帧即成品零 FE 改动 | 线性成本（帧数×服装套数）；换装回退需保留原帧 |
| **C. Palette swap**（[零成本变体](https://pixelpaletteswap.com/)） | 同款服装程序化换色 | **0** | 零成本无限变体 | 只能换色不能换款式 |

### 4.2 推荐架构：三轨制

1. **武器 = 硬分层（已定 §4b，不变）**：武器小而形状独立，锚点系统（weapon_anchor 常量表，§8.3 已定）天然适配——身体帧空拳/空手，武器贴图按锚叠加，**换武器零重做动作帧**。这条已验证（拔剑式突刺的虚握拳手型帧就是给剑叠加载体）。
2. **换装 = AI 换皮重绘（方案 B）为主**：服装设计稿先 Leo 过目 → **按序列表整表换皮（主输入=母版/动作序列表整张，禁逐帧单独重绘——逐帧会复刻批 1a 帧间不连贯教训，主架构修订项）** → 切格归一入库。换装套按"服装 ID"独立目录存储。成本口径：动作帧 5 动作×3 帧×6 向=90 帧/套（不含待机锚），≈180 分/套（**偏贵，见 4.3 降本**）。
3. **变体 = palette swap（方案 C）为辅**：同款服装换色（NPC 群众/同模敌型/阵营色区分）零成本程序化。

### 4.3 换装成本降本三招（关键补充）

1. **服装变化分档**：换色档（palette swap 0 分）→ 换饰档（只改配饰/颜色局部，局部修正 2 分/帧×可见帧）→ 换款档（全帧换皮 2 分/帧）——大部分日常服装需求落在前两档。
2. **服装可见帧裁剪 = 定案不裁剪（主架构）**：帧动画 140ms/帧连播下，帧间服装细节跳变是高频闪烁，比画风漂移更刺眼——换皮必须全帧一致处理，禁"代表性帧换皮+其余继承"。
3. **方向继承**：服装换皮只需对右系 3 向实绘帧处理，左系镜像自动继承（0 分）——换装成本直接减半（108→54 帧/套 ≈108 分/套）。

### 4.4 换兵器适配（已基本就绪）

- 武器分层+锚点系统 §4b/§8.3 已定：身体帧空手、武器贴图独立、weapon_anchor={x,y,angle} 常量表（angle 冻结垂向右下、出招跟手不转）。
- **新武器适配 = 只产武器贴图（挂鞘态+手持态 2~3 张）+ 锚点标定，动作帧零改动**——这正是当初武器剥离立项的收益兑现。
- 待办：武器锚点需按动作帧逐帧标定（普攻突刺帧的手位已定型，标定时机成熟）——归战斗实装卡。

## 九、v1.2 续研：迁移到 Codex 原生生图

### 9.1 迁移结论

1. **新任务的生成与图像编辑统一使用 Codex 原生 ImageGen**；`scripts/mxai_gen.py`、`scripts/mxai_img2img.py`、`scripts/mxai_web_cutout.js` 从新任务入口退出，保留为历史批次的只读复现材料，本次不删除。
2. Codex 原生 ImageGen 是**会话内工具**，不是仓库 CLI，也没有把精确宽高、输出路径和透明背景作为本地脚本参数暴露。因此迁移单位应是“可审计作业包”，不能把旧命令机械改名。
3. 原生能力负责文生图、参考图编辑和语义扣图；本地确定性工具负责复制归档、尺寸归一、对齐、镜像、alpha/尺寸/基线/包络门检和 contact sheet。生成与机械加工必须分步，原始输出永不覆盖。
4. OpenAI 官方说明 GPT Image 支持图像生成、图像编辑、高保真输入及透明背景输出；但本项目实际能否获得透明通道只认文件检测，不以 prompt 或预览棋盘格为证。能力依据：[GPT Image 2](https://developers.openai.com/api/docs/models/gpt-image-2)、[Images API reference](https://developers.openai.com/api/reference/resources/images)。

### 9.2 本次原生试产的实证边界

- Leo 已目验通过右上方向第 2 帧第四稿的动作味道：`assets/_trial_20260905/t45_native_opt/candidates/atk_rightup_2_attempt4.png`。
- 该文件实测为 **1086×1448、无 alpha**；看到的棋盘格是画面像素。它只能标记为 `visual-approved candidate`，不能直接覆盖 240×320 RGBA 正式帧。
- 原生编辑可以保持人物与动作的大意，也能按连续反馈调整手臂方向；对像素级身份保持、精确画布和直接透明输出没有形成稳定保证。
- 以后继续执行 Leo 的硬上限：**每帧最多 2 次生成/编辑尝试**。第 2 次仍不过门即登记失败，不用其他说法硬凑。当前第四稿是 Leo 在对话中逐次明确批准追加的特例，不改后续默认上限。

### 9.3 透明底与扣图决策树

```text
Codex 原生输出
  → 读取真实尺寸、色彩模式、alpha 极值和四角像素
  ├─ 有 alpha，背景 alpha=0，主体边缘无脏边
  │    → 跳过扣图，直接进入归一/对齐门
  └─ 无 alpha、全不透明、棋盘格烘焙或边缘不干净
       → 第 1 选择：用 Codex 原生编辑做一次“只移除背景、主体零改动”
       ├─ 实测 alpha 合格 → 进入归一/对齐门
       └─ 仍不合格 → 若输入为已约定的纯色隔离底，走本地确定性边界扣图；
                      白衣、白裤、发丝等无法可靠分离时停报，不自动破坏主体
```

因此，**扣图能力仍有必要，但从每张必跑改为条件分支**。原生输出直接带合格 alpha 时不扣；当前第四稿必须扣，因为它没有透明通道。为减少白衣误伤，新生产优先要求“真实透明背景”；若连续两次仍烘焙背景，则后续任务书应改用与角色主色不重叠的纯色隔离底，并冻结色值。纯白底不再作为白衣角色的默认方案。

扣图后的判定仍是机械门：240×320、RGBA、外围透明连通、主体单连通或白名单小部件、脚底 y=300、水平中心 x=120、无文字/武器/影子/背景残留。任何视觉上像透明但 `hasAlpha=no` 的文件都判失败。

### 9.4 复用机制 v2：三份真源，一个清单

原 v1.1 的“动作模板库 × 角色皮肤包”保留，并补成三份互相独立的真源：

| 真源 | 冻结内容 | 复用范围 |
|---|---|---|
| `MotionTemplate` | 动作三拍/帧数、近远肢、朝向派生、幅度、禁止项、示意图 | 跨角色复用 |
| `CharacterBible` | 五官、发型、体型、头身比、服饰基线、各向锚 | 同角色跨动作复用 |
| `ProductionVariant` | skin、palette、武器层、该批 prompt、生成轮次和 Leo 目验状态 | 单角色/皮肤/批次 |

所有运行时产物只由一份 `manifest.json` 对外描述，避免文件名、prompt、接线常量各自成为真源。建议字段如下：

```json
{
  "schemaVersion": 1,
  "roleId": "hero",
  "skinId": "base",
  "paletteId": "default",
  "generator": "codex-native",
  "actionMap": { "basic": "atk" },
  "frames": [
    {
      "id": "atk_rightup_2",
      "file": "atk_rightup_2.png",
      "direction": "rightup",
      "frameIndex": 2,
      "size": [240, 320],
      "footY": 300,
      "centerX": 120,
      "alphaMode": "straight",
      "weaponAnchors": [{ "name": "main", "x": 0, "y": 0, "angle": 0 }],
      "sourceJob": "20260905-t45-rightup2-a4",
      "review": { "leoVisual": "approved", "mechanical": "pending" }
    }
  ]
}
```

`weaponAnchors` 中示例坐标不得直接使用；它只是 schema 占位，正式值由标定产生。换皮时锁手部区域；只要手位发生变化，就必须按 `skinId` 重验锚点。左系仍按已拍板方案交付独立 PNG，但必须由右系确定性镜像派生，并把镜像来源写入 `sourceJob`。

### 9.5 作业目录与状态机

管线中间物与运行时素材分树：

```text
assets-pipeline/characters/{role_id}/{skin_id}/{action}/{job_id}/
├── request.md       # 冻结要求、每帧最多两次、停止条件
├── refs.json        # 参考图绝对/仓库相对路径及各自职责
├── prompts/         # 每次调用的完整提示词
├── raw/             # Codex 原生输出原件，只增不改
├── normalized/      # 扣图、缩放、对齐后的候选
├── qa/              # alpha/尺寸/包络/锚点/diff 记录
└── contact/         # Leo 目验总览

assets/characters/{role_id}/{skin_id}/battle45/
├── {action}_{dir}_{n}.png
└── manifest.json
```

状态只允许单向推进：

```text
requested → generated → normalized → mechanical-pass → leo-approved → runtime-ready
                         └──────────→ failed（保留原因与尝试数）
```

Leo 的审美通过与机械门必须分开记录。本次第四稿是 `generated + leo-approved`，机械状态仍为 `pending`；完成扣图、归一和对照后才能成为 `runtime-ready`。正式入库必须显式复制，禁止生成工具直接写入 `assets/characters/`。
