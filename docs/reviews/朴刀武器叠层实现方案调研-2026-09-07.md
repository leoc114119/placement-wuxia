## 1. 给 Leo 的结论

**建议先验证 D：裸刀 + 身体原有握拳的局部遮挡。保留 B′：按握姿分类的独立手件，作为 D 无法成立时的候选。暂不批准量产。**

D 不另画一只手，不把肤色绑到每把刀上。以原身体帧里的拳头作为可见握持面，让刀柄的一小段被拳面遮住，刀身仍遵守朝向前后层级。皮肤、袖口、描边直接来自身体，解决的是“原拳与刀柄的遮挡关系”。这比单纯把完整裸刀放在拳头前面多一道局部遮挡，但不必重画已验收身体。

**限制同样明确：遮罩不能把错误的拳形变成正确握姿。**如果手掌摊开、刀柄轴线与手腕方向冲突，或两拳的位置无法支持长柄双手握持，D 会失败；不能靠扩大遮罩藏掉整个刀柄来假装通过。B′也需要按掌面/手背/侧握分姿势族，不能宣称一张“通用手”包办所有角色和动作。

现阶段最值得验证的不是“哪只新手最好看”，而是**现有身体的握拳能否通过正确遮挡直接利用**。推荐顺序 D → B′，A 保留为特定武器的定制例外；C 程序画手不作为当前画风的首选。此为研究建议，不自动解除暂停令。

## 2. 冻结条件与发现的口径缺口

| 项目 | 本次采用的口径 |
|---|---|
| 身体 | 甲乙各 31 张 PNG（各 30 身体帧 + 1 共用白骨）；核查目录和 manifest 均为31。现件不重画、不覆盖 |
| 渲染 | 微信小游戏 Canvas 2D；不引入 WebGL、Spine 或新引擎 |
| 武器 | 六向独立件、身体与武器剥离；右系三向、左系确定性镜像 |
| 层级 | right/left/rightdown/leftdown 为 front，rightup/leftup 为 back（seq124/128）。§4c 仍留“统一前景”旧句，报告按本单最新裁定，不改原规格 |
| 锚点 | 身体源画布 x/y，握持点为旋转原点，angle 单位 degree；逐帧标定，不运行时猜手位 |
| 范围 | 敌型 idle/walk/atk；die 不配锚。以后主角 cast 必须持武器，jump 可隐藏，不用隐藏施法掩盖难帧 |
| 换色 | 运行时离屏换色，禁止预生成换色变体入包；v1.2 含真机失败后 CDN 回退讨论，本单未授权执行回退 |

**palette_truth.json 的实际内容与“手部真值”名称不等价。**文件 source 是 idle/atk/walk right 的 alpha>200 不透明像素直方图；只有 RGB/hex/px，缺少逐帧手部 ROI、皮肤/袖口/描边标签、采样坐标、明暗阶映射。甲 top20 几乎全是近黑值，乙混有红色和棕色。因此它可以作为原始统计参照，**不能直接支撑皮肤色差阈值或 palette swap 的肤色映射**。本次未修改它；B′进入试产前需补具名手部 ROI 和亮/中/暗/描边色阶，阈值由 PM/Leo 另定。

七条产用原则继续沿用：D 保留完整身体文件，附加的是遮挡数据，非把整图拆成新身体组件入库；裁片仅用于验证或运行时临时计算。手件若需要高密度细节才能接缝，应按“简单件才可生成”停止放量。颜色与尺寸门不能替代 Leo 握感目验；不给正式件叠加无关代码装饰。

检索日期 2026-09-07。高=官方或实现源码直接证据；中=机制可迁移的推断；未证实=不能用作该游戏内部实现事实。开源再实现只代表该项目，不能冒充原厂客户端。

## 5. D 的实现草案与失效条件（待批准）

定义 B 为完整身体，W 为在身体画布坐标中完成握点平移/旋转的裸刀，M 为经过标定的“应在刀柄前方的原拳区域”。

- front 四向：先 B，再 W 的可见部分；在临时武器缓存中将与 M 重叠的刀柄 alpha 清除。只允许遮刀柄握持区，不能把整把刀沿身体轮廓抹掉。
- back 两向：先 W 再 B，身体自然遮住武器。若这导致握点完全不合理或刀刃应跨到身体前方，记录失败，提交局部前后片方案 E 的规格评估；不偷偷推翻按向切层。
- M 是身体坐标中的数据，不跟着刀一起旋转。W 才围绕握持点转；所有层共享身体屏幕缩放/位移/震动，不能分别取整而造成抖动。
- 能只做几何 clip 的区域可作快路径，但真机需验证。稳妥候选是在缓存构建时按像素应用 M，随后只 drawImage；不每帧 getImageData，也不在主画布 destination-out 挖洞（会把场景一起擦掉）。
- 灰度/半透明遮罩需要验证边缘颜色与 alpha 合成，不能简单把原拳透明裁片再叠一次而让轮廓加深。原拳被重复 source-over 会改变半透明像素；选择遮武器而不是重复画拳可避开这一类重叠。
- 镜像以已交付左帧为基准重验。若右到左经历质心平移，离散像素映射是 `x_left = 239 - x_right + dx`；连续边界坐标为另一约定。dx 必须读来源记录，不能只做239-x；角度与图片镜像不能叠加两次翻转。正式契约需研发明确坐标约定。

D 不需要“人工智能识别手”，也不需要运行时找手。标定一次握点、刀柄轴线与遮挡轮廓，运行时消费确定数据。原拳轮廓不足以产生手指包柄关系时应明确失败，不把色相/位置对齐等同于握感过门。

## 6. 微信小游戏可行性与真实性能边界

### 6.1 API 证据与兼容性

微信开发者文档网页本次读取失败，转查**腾讯官方小游戏 API 类型库**（不是小程序 Canvas 文档）。仓库说明类型随文档生成；其中 wx.createCanvas 注释说明首个为屏幕画布，后续为离屏画布。RenderingContext 注释列出 iOS/Android 部分混合模式限制，包括 source-in、source-out、destination-atop、lighter、copy，且可能不报错但结果错误。[S7]

因此：**不能把浏览器 source-in 染色教程当作小游戏已验证方案**；离屏能力也不代表 Worker 或后台线程能力。建议使用目标基础库实际支持的离屏Canvas，读取像素→按语义索引查表修改RGB、保留alpha→写回→缓存；各API先在目标机检查。官方类型说明是兼容风险证据，不是所有当前微信版本必定失败的实测结论。

MDN建议缓存重复绘制，减少每帧重复缩放与状态切换；这是 Canvas 通用优化依据，不能把其中 DOM/CSS 多Canvas示例直接搬到小游戏。[S8] Canvas 合成语义说明用于解释遮罩，不代替微信兼容验收。[S9]

### 6.2 可以算出的容量与不能宣称的速度

| 算项 | 计算值（理论RGBA8，不是进程内存实测） |
|---|---|
| 单张240×320身体 | 307,200 bytes = 0.293 MiB |
| 两敌62个文件全部独立解码 | 18.164 MiB；相同白骨可去重，但按内容去重不是文件相同就必然自动发生 |
| 每敌30个持刀组合全画布缓存 | 每敌8.789 MiB，两敌17.578 MiB，**是新增缓存** |
| 假设手ROI32×32 | 每张4 KiB；相对整帧像素处理量小75倍（ROI尺寸是示例，尚未标定） |
| 7棋子、身体+武器 | 每帧14次角色层 drawImage，60fps时840次/秒 |
| 7棋子、身体+武器+手 | 每帧21次，60fps时1,260次/秒；不含地形、UI、特效，也不等于GPU draw call |
| 7张全画布每帧读一次写一次、60fps | RGBA逻辑搬运约246 MiB/s；还未计复制、同步、上传；不是设备带宽需求实测 |

**当前没有本项目 iOS/安卓真机的毫秒数据，不能承诺7人三层稳定60fps，不能给全平台统一缓存MB上限。**31张/敌是文件核查；上述容量是算术下界，真实成本还包含JS数组、Canvas backing store、GPU副本及临时对象。PNG压缩体积不能代替解码内存。双DPR放大若复制进缓存，像素与内存近似按DPR平方增长；应优先在源分辨率缓存，再按统一显示变换绘制。

缓存粒度建议：B′优先缓存小手件的 palette 变体；D先按当前使用组合懒建/有界预热，优先尝试武器可见bbox而不是每帧全画布；完整合成身体+武器缓存只是可测备选，不能默认全排列。缓存键含body/weapon/source hash、frame、palette、anchor/mask版本、尺度策略；以逻辑图元数和字节预算驱逐，不能只按“2个skin”假定内存可控。加载失败或缓存未就绪的显示方式须另按研发卡定，不临时降成空手。

### 6.3 交研发的真机验证设计（本次未执行）

样机至少低端安卓、主流安卓、iOS各一台，记录机型/系统/微信/基础库/屏幕与DPR/温度；先检查像素读写、drawImage(Canvas)、alpha、旋转、clip。加入纯色棋盘和半透明边界正确性样例，防“无异常但像素错误”。

在同一战场负载上比较：基线单层、A双层、B′缓存手件三层、D缓存武器双层、完整预合成缓存。按1/4/7棋子，分别测冷加载、首次换色、稳态、方向/动作频繁切换、连续换装20轮、离场回收；每组预热30秒、记录120秒、重复3次，顺序轮换并保留温度信息。

输出主循环帧间隔 p50/p95/p99、长帧次数（>33.3ms与>50ms，仅统计分桶）、换色/缓存构建耗时、命中率、构建峰值、可观测内存/回收趋势、截图；CPU计时不等于GPU提交完成。若工具无法读取某种内存，明确标NA。项目目标若为60fps总帧预算16.67ms，30fps为33.33ms；**这是预算换算，非本报告自定验收目标**。预算分配和放行阈值交主架构/PM，不虚构“每层0.1ms”。

## 7. 试产验证点与后续落地顺序

1. Leo选择是否批准 D 的零生成验证路线，并由 PM 明确允许局部遮罩数据；暂停令此前维持。本报告不实际改贴图或写渲染代码。
2. 美术标定甲/乙 right idle、right atk_2、rightup atk_2、rightdown walk_1 共8个现有帧；含前后层、出手幅度和移动姿势。先用现有武器作**技术占位**即可验证对位；占位剑不作为朴刀审美/刃面透视通过证据。未来主角增加 cast 三相位难帧验证，不能以敌型通过替代主角通过。
3. 对每帧冻结身体SHA、握点、刀柄轴、原拳ROI/遮挡轮廓；生成“完整裸刀叠前 / D遮挡 / 后向层序”对照，原尺寸与放大视图同时交 Leo。明确检查刀柄从拳中贯出、无双拳、无双描边、袖口连续、刀刃不被误切。
4. 若D某帧握姿失败，登记失败类型；不要全量重生成身体。按失败姿势族提出B′或F小补丁试产。B′先补皮肤/袖口语义色板；不使用全图top20直接替换皮肤。
5. D路线通过视觉后才扩敌型60个身体帧锚/遮挡检查（左系可派生，但必须复核镜像平移）；die两条显式豁免。武器六向件是否甲乙共用须两种体型验证后裁定，本单不改变原“各一套”规格。
6. 研发另卡做最小缓存/分层 spike，按§6.3收真机数据；PM批准数据契约后才接线。候选契约字段：bodyFrameHash、weaponViewId、gripPoint、angleDeg、layerOrder、occlusionRef、paletteId、mirrorSource与offset、revision；这是草案，不写进正式manifest。

机器门可检查：源图SHA未变、坐标与遮罩范围、帧数齐套、die豁免、朝向映射、遮挡不越批准区域、镜像加偏移一致、调色后alpha不变、缓存键包含版本。握感与连播仍由Leo目验；色差/拳宽/描边容差须以合格样本制定，不能用本报告捏造阈值。

## 8. 风险与待拍板事项

- **第一风险是几何而不是色差**：原拳并非所有视角都能成为握刀手，D要承认失败边界。
- 后向整刀在身体后可能出现“刀消失过多”；若必须局部穿到前景，需要E或局部分片的规格批准。
- 无语义ROI的精确RGB换色会漏掉连续明暗/抗锯齿或误染衣服；近似色域映射也不能自动分辨同色不同材质。
- 小件旋转采样会糊边或抖边；锁定源尺度、统一变换，最近邻/平滑按实际风格对照选，不拿“像素游戏”直接决定。
- “零新增手图”不等于零标定工时；D需逐帧遮挡，B′需姿势族与袖口适配，E需动作帧武器资源。
- **待Leo拍板**：是否优先试D；失败帧是否允许B′/F；甲乙裸刀共用是否允许；随后由PM/主架构冻结遮罩契约与真机门限。本报告仅提交这些选择，不替代批准。
