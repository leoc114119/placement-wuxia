## 三、代表性缺陷五问根因链

### 3.1 N1 · 普通移动穿人（四次报绿、三次复现、本次根因闭环）

**① 现象**：点绿格移动，角色贴地直线滑过其他角色身体（规格 BASE-7/MV-1：普通移动不可穿任何单位）。同缺陷此前至少三次"修复+全绿"，Leo 三次复现。

**② 真根因（文件:行 + 证据）**：
- 结算层无病：绿格=BFS 不可穿（battle-session.ts:245-247 `walkCells`→hex.ts:82 `reachable`，occupied 既不落脚也不借道）；行为套件绿锁用例（移动力 2、隔敌对侧格∉绿格、提交无位移无事件）通过。
- 断点在**演出触发层**：`submit(move)` → `doMove` 置 `animState='walk'`（battle-session.ts:397）→ 紧接着 `basicIfAdjacent` 发现落点相邻有敌 → `doAttack` 把 `animState` 覆写为 `'basic'`（battle-session.ts:402-408 → 352-354）——**同一同步调用栈，任何一帧快照都没呈现过 'walk'**。
- FE 演出启动条件锚在快照状态：`walkRise = !prevAnim && !moveDone && animState === 'walk' && renderPos≠pos`（battle-hex-render.ts:414-416）→ 永假 → moveAnim 不启动。
- 绘制回退路径：`ma ? moveAnimDrawPosPx(ma) : hexToWorld(actor.renderPos…)`（battle-hex-render.ts:722）——renderPos 是 **session 侧直线插值**（battle-session.ts:522-526，`renderQ = moveFromQ + (hex.q-moveFromQ)*moveT`）→ 从起点到终点直线滑行，穿过中间单位。
- **最小复现证据（node，scratch 探针 09-02 22:35）**：hero(5,8)、敌(6,8)、走(7,8)（落点与敌相邻）：
  - `[N1-A] submit ok: true | animState(紧接submit): basic | renderPos {q:1,r:8} → pos {q:3,r:8}`
  - `[N1-B] moveAnim 是否启动: false`
  - `[N1-E] 穿格记录: 帧4~13 连续进入 e1 格（距中心 41→4→43px），画位与 e1 中心最小距离: 4px`
  - 对照组（落点不与敌相邻，无 ATK-3）：`moveAnim 启动: true，穿格记录: []`，且打印 `DBG[move-start]`（=walkRise 分支执行）。
- **真浏览器复验（behavior_e2e BE4，两次连跑一致）**：`moveAnim启动=false renderPos穿敌格=true（-1,11→1,11 敌0,11）`，截图 `proto/battle_demo/shots/behavior_be4_n1_through.png`。

**③ 为什么 148 个单测没拦住**：`computeMovePath`（含"绕行不穿占格"）有纯函数级用例（battle-hex-render.test.ts，`fa9cf80`/`298bf31` 加）——**函数是对的，但在该场景从未被调用**；触发它的 `walkRise` 条件与 `animState` 时序的交互没有任何用例覆盖"submit→逐帧快照→updateView"集成序列。session 侧用例只断言事件与 pos（结算语义），不看 animState 在 submit 瞬间的值。

**④ 为什么 16 断言 e2e 没拦住**：shot.mjs 的 walk 单调性断言选"最远可达格"点击后采样投影单调——**"直线穿人"的投影序列完全单调**，断言与缺陷正交；且该用例不控制落点是否与敌相邻（ATK-3 是否触发靠布局运气）。

**⑤ 为什么修不好/修 A 破 B**：三轮修复分别动 moveCells 并集（D-01①）、isJump 真值（②）、FE 路径演出（③），都在**各自的层内正确**；但"演出是否启动"这个决策点横跨 session（animState 时序）与 FE（walkRise 条件），两轮修复都没人看它。ATK-3 自动普攻是 L 环验收期才加的特例（`2983d4b` ④ 前后），加的时候没人重查 walk 的可见性窗口——**补丁间共享的隐含前提（"walk 状态至少存活一帧"）无人看守**，这正是规格 §八"病灶"机制在演出层的重演。

### 3.2 N2 · 特/绝选中后点红色射程格无反应

**① 现象**：选特/绝后红格高亮正常，点击红格（含敌棋所在格）无任何反应。此前一轮"修复"（`fa9cf80` A 命中改逻辑 hex）后复现。

**② 真根因（复合，三层证据）**：
- **受理/结算层无病**：node 全链 `[N2-A] dispatch:[attack te] | e1 hp 100→89 | hero neili 60→59 | events 尾部 [bar-max, skill]`；真浏览器点**静止**敌格 BE1 绿：`事件=["skill"] 内力60→59 敌hp70→59 选中=null`。
- **机制①（空红格=死区）**：拳系特技红区=射程 2 圆=18 格，场上仅 2 敌 → 大多数红格是空格。input 层对"攻击技选中+点击射程内空格"**无任何分支**（battle-input.ts:135-157：目标命中→施放；`skill && !inAttack`→取消；inAttack 的空格→**静默落空**）。规格 ATK-2 定义施放="点射程格上的**敌棋子**"、ATK-5 只定义"不在射程格的空格=无操作"——**"射程内空格"是规格缺口**，实现取了字面零反馈。e2e BE2 实证：`点空红格(-2,12) 选中jue→jue 事件10→10 fx0→0 toast=|`（零派发零反馈）。
- **机制②（演出位错位→静默取消）**：敌移动演出中 renderPos≠pos，玩家点**看到的位置** → 命中层按 pos 匹配（battle-input.ts:129-131，`fa9cf80` A 的修法）落空 → 该可见格不在 attackCells → `skill && !inAttack` → 派发 `cancelSkill` → **选中静默丢失**。时序证据 `[N2-F] 输入态出现 3 次，敌棋仍在移动演出的 3 次`（100% 重叠窗口）；e2e BE3 实证：`敌 pos={q:0,r:11} 可见位={q:0,r:13} 点击后选中=null（期望保持 jue）`。`fa9cf80` A 只修了"动画位点击误判"单向（pos 匹配），没修"可见位≠pos 时用户点空"的反馈缺失——**同一断点的另一半**。
- **机制③（UI 热区压棋盘，新发现 D-13）**：BE3 首跑时敌棋可见格屏幕坐标 (404,622) 落入右下 ctrl 热区（x∈[358,441] y∈[614,780]）→ 点击被截获为 `setMode(auto)`（托管）→ SEL-7 连带清选中。即：**走到屏幕右下区域的敌人不可选中，点它直接切托管模式**。取证：该轮 40s 超时现场 `mode:"auto"` + 事件流 `bar-max:e2/basic:e2/…`。

**③ 为什么 148 单测没拦住**：battle-session 用例走 `submit(attack)` 直达受理层（跳过命中层）；battle-hex-render/battle-ui 的输入用例喂的是构造快照（renderPos==pos 的静止态），机制②③的"分离态/热区重叠"几何从未进样本；机制①是规格缺口——没有真源条目就没有对应用例。

**④ 为什么 16 断言 e2e 没拦住**：shot.mjs ③ 测的是**普攻**点敌（无技能选中态），且用 `cellCss(foe.renderPos)` 在敌静止后点击；**整个 e2e 没有一条"选技能→施放"的断言**——N2 的主路径零覆盖。

**⑤ 为什么修不好**：`fa9cf80` A 是"点敌命中"单点修复，没有把"点击→必有可观测后果"作为行为面断言；红区交互语义（空格/敌格/取消的边界）在规格里只有正面路径，修复者各自按字面实现——没有行为矩阵就没有"漏了哪格"的检查表。

### 5.2 快照驱动 vs 演出计时的双轨边界（N1/D-04 的共同结构）

- 事件流（`move`/`skill`/`basic`）已经存在且有序，但演出启动**不用事件**（main.ts:257 的 events 游标只消费 rejected）——"事件驱动演出"是自然的收敛方向（列入 §8 待拍板，架构方向不自作主张）。

### B.1 复现先行铁律

1. **任何修复开工前，必须先存在一个"正在失败"的测试锁住现象**：

1. **根因假设必须用最小复现证实或证伪后才能派修法**：

### B.4 交互分析铁律（四层取证，禁止跳层下结论）

凡"点击没反应/行为不符预期"：

```
第一层 命中判定层（点没点到）
  观测：input.up 是否派发（dispatch 记录）/ 落在哪个分支（按钮热区/ctrl/plaque/棋盘格/格→cell 换算）
  工具：__demo.btnCss/cellCss/cssOf + getView().layout；构造 dispatch 记录器
  已知陷阱：可见位 renderPos≠逻辑 pos（BE3）；UI 热区压格（D-13）；出画布格（镜头 clamp）
第二层 意图受理层（受理了没有）
  观测：session.submit(req) 返回值 + rejected 事件（reason: bar/range/invalid）
  注意：submit false 且无事件（ATK-5 无操作）≠ rejected——三种"没受理"要分清
第三层 结算层（算了没有）
  观测：events 流（move/skill/basic/miss/death…）+ 快照 hp/neili/bar/cooldown
第四层 演出层（画了没有）
  观测：getView().moveAnims（是否启动/何时释放）/ fx / animState 时间线 / sampleHeroDraw 或 startFrameLog 逐帧录制
  已知陷阱：animState 单槽位同栈覆写（N1）；双轨交接（§5.2）
```

- 每层留下观测输出原文，才允许进下一层；四层结论齐了才叫"定位完成"。
- 修复验证同样按四层回放：修复层的观测点变化 + 其余三层不回归。
