## 一、你已经有这个后台的雏形了

| 已有 | 位置 | 它是什么 |
|---|---|---|
| 任务实体 + 状态列 | `tasks/box.db` → `tasks(project_id,id,title,status,owner,col,thread,summary,updated_at)` | 五列看板（inbox/working/questions/done/archive） |
| 审计事件流 | `tasks/box.db` → `events(seq,t,dir,ev,detail)` | 追加式事件日志 |
| CLI | `scripts/task.py`（init/list/board/move/event/card） | 通道化变更，禁手改 DB |
| 看板页面 | `dashboard.html` | Leo 的窗口 |
| 跨工具投递门禁 | `scripts/projbus/`（delivery/ack/SHA 门禁/幂等） | 已通车双宿主 |
| 工序实现 | `scripts/` 36 个脚本（生成/抠底/清杂/归一/切帧/审计） | 已存在，但**未被系统化编排** |

**缺的三类实体**：①**素材/批次/帧**（产物实体）②**工序执行记录**（谁在哪一步、用了什么参数）③**门**（判据 + 机器可跑的结果 + 证据路径）。

**缺的一个执行器**：现在这些脚本靠会话里的代理逐批现写现调，所以状态活在对话里、活在它当轮的记忆里——这正是"受 AI 上下文影响"的机制。

---

## 二、核心设计：AI 降级为无状态工位

> **系统每次只给 AI 一个 job spec（作业 JSON），AI 回产物目录；它不需要记住任何跨批上下文。**

这一条直接消灭今天暴露的四个病：

| 今天的病 | 为什么消失 |
|---|---|
| 线程涨到 1.65GB、压缩 68 次、"回一条就停" | 不再需要长会话——每次调用是自包含的小作业，用完即弃 |
| 自报"29/30 通过" | 门由系统跑，不由执行者自报；执行者只能提交产物 |
| 把候选说成 final、放行措辞反复更正 | 状态由系统按门结果推进，代理**无权限改状态** |
| 每批重新实现归一层、重新踩同一个坑 | 归一是系统的一个工序，写一次、版本化、永远生效 |

**AI 保留的工位**（唯一不可替代的三件）：写 prompt、出生成候选、判姿势语义。其余全部变成系统代码。

## 三、数据模型草案（贴现有 SQLite，同栈同库或同目录新库）

```sql
batches(id, klass, direction, coefficient, scale_table_json, anchor_sha, spec_version, state)
frames(batch_id, name, family, seq, source_path, source_sha, out_path, out_sha,
       bbox_w, bbox_h, centroid_x, foot_y, state)
stages(batch_id, frame_name, stage, status, actor, params_json, started_at, ended_at, log_path)
gates(id, batch_id, frame_name, stage, rule_ref, params_json, result, evidence_path, ran_at)
artifacts(sha256, path, produced_by, at, note)   -- 落库纪律的机器化
```
- `batches.scale_table_json` = 三锁里的"一族一表"（Leo 圈定值落库）
- `gates.rule_ref` = 规范红线编号 → 断言实现（判据与规范同源，改规范即改门）
- 复用 `events` 作审计流，不另建

## 四、状态机（关键：只能由系统推进）

```
draft → raw(已生成) → isolated(已隔离) → cleaned(已清杂) → normalized(已归一)
      → gated(机械门过) → reviewed(Leo 过目) → approved(已验收) → integrated(已落库/接线)
```

- 确定性工序由系统执行 → 自动推进；
- 每个跳跃必须挂在**门的结果**上，门跑不过**原地退栈**；
- **代理只能提交产物，不能改状态**；Leo 的审美门在 `reviewed` 一跳（系统给对照图页，他点通过/打回，结果落库）。

## 五、工位划分

| 工位 | 谁执行 | 内容 |
|---|---|---|
| 确定性工位（系统代码） | 系统 | 隔离 / 清杂 / 归一 / 切帧 / 门检 / 出对照图 / 落库 / **回归复现** |
| 模型工位（系统调用） | AI | 写 prompt / 出候选 / 判姿势语义——收 job JSON，回产物目录 |
| 人工工位 | Leo | 审美门 + 圈定（尺度表/系数）——看对照图页点按钮，结果落库 |

## 六、必须说清的边界与风险

1. **系统管流程与判据，不会让画面变好**。生成仍随机、审美仍归 Leo——系统能做的是把"画面漂移"变成生成时就可测的量（刚体探针），把"要不要重做"变成有依据的判定。
2. **最大风险是过度建设**。别一上来做 12 类通用平台。P0 只做 T45 战斗帧这一类，端到端跑通再泛化。
3. **本地优先**：Python + SQLite + 本地页面，与 `box.db` 同栈，不引云服务、不引外部依赖（单人项目，运维成本要为零）。
4. **一个待定的架构问题**：**并入现有任务箱，还是另起一套？** 我建议并入——一个真源、一块看板，你的 dashboard 加一个"素材流水线"页即可；另起一套会出现两个状态源，反而回到今天的问题。
