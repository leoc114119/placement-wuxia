# Codex 原生美术管线执行手册 v1.3

> 状态：项目级 Codex skill；同时是仓库内可审查的执行真源。
> 适用：角色、动作帧、换装、武器、UI、场景的原生生图/编辑、条件扣图、规格化、门检与交接。
> 决策：Codex 原生是默认通道；仅 §5.1 的动作帧单图异常回退可调用一次 mxai `seedream-5.0-pro`（Seedream 5 Pro），历史脚本暂不删除。

## 1. 开工真源

每个新任务先读 `AGENTS.md`、`CODEX-ART-README.md` 和本次需求文档。只加载本类资产需要的规范：角色帧读《角色帧规范》，战斗素材读《战斗素材盘点与产用原则》，T45 读对应 T45 需求文档；历史复盘只在排查同类失败时读取。

需求、规格、验收标准、预算或正式入库权限有实质疑义时，暂停依赖该决定的资产分支并经本任务 question/`ART-ARCH` 登记；继续其他独立检查和已授权产物。文件检索、图像检查、确定性加工方法及任务范围内的 prompt 组织可自主完成。当前任务已有明确决定时记录来源后执行，不重复确认。

## 2. 工具路由

- 新生成、参考图编辑、局部修正和语义扣图默认只用 Codex 原生 ImageGen。
- `scripts/mxai_gen.py`、`scripts/mxai_img2img.py`、`scripts/mxai_web_cutout.js` 和其他外部生图 API 仍禁止作为普通新任务、批量换源或自动重试通道；唯一例外是 §5.1 明确限定的动作帧单图回退。
- 本地工具只承担确定性工序：复制、切帧、镜像、纯色背景连通域扣图、尺寸归一、对齐、压缩、门检、contact sheet。任务书明确禁止脚本加工时，以任务书为准。
- 原生输出先进入 `raw/`，禁止直接写入或覆盖正式资产。
- 禁止安装依赖、修改游戏代码或自行实现代码降级；需要研发改动时登记方案，交研发任务卡实施。

## 3. 参考图纪律

调用 ImageGen 前逐张打开并确认内容。参考职责按需组合：

1. 目标原帧或动作母版：只管姿势与构图；
2. 角色身份锚：只管五官、发型、服饰、色板与比例；
3. 目标朝向锚：只管前后层次和可见面；
4. Leo 标注图：只管唯一允许改动的部位或方向。

提示词逐图声明职责和冲突优先级，只挂解决本次问题所需的图。调用前在 `refs.json` 写明每张图的实际路径、目验结果、允许负责的内容和禁止负责的内容；任何一项未写清时不发起生成。

contact sheet 只用于审阅和对照，不得作为身份锚、姿势锚或后续生成输入。需要复用其中一格时，必须回到该格的原始单帧文件并重新打开核验。

### 3.1 主角色锚复用生成 NPC 的职责分离

复用主角色素材时，主角色图只能承担明确授权的几何参照职责，例如可见总高、脚底基线和头身量级；它不承担 NPC 的五官、发型、服装、色板、身份或武器。NPC 必须先有自己的高分辨率身份锚，提示词中明确“NPC 身份锚优先”。

生成 NPC 的目标方向时，参考职责固定为：

1. NPC 身份锚：身份、渲染、线条、服装、色板和比例的唯一真源；
2. 与目标方向一致的真实成帧或姿势图：只管朝向、可见面、前后层次、站距和重心；
3. 主角色锚：仅在任务明确要求统一总体量级时，补充总高与比例量级；
4. 白模：只能提供粗略朝向提示，不能单独作为最终转面真源。

当生成结果把目标方向错误地读成纯侧面或其他方向时，不继续堆叠方位词。保留 NPC 身份锚，补挂一张已验证的真实目标姿势图，并在提示词中声明该图只负责姿势与前后层次；下一次只修方向这一项。参照图必须逐张打开核验内容，文件名和尺寸不构成内容证明。

主角锚复用的生产顺序固定为：先定 NPC `right` 主锚，再逐张生成并目验 `rightup`，最后逐张生成并目验 `rightdown`。前一张未选定时，不生成后一张；不得把批量生成的同组彩稿互相当作身份来源。

每个单帧固定走 `raw → 文件事实检查 → normalized → 单帧/锚点对照 → Leo 目验`。总览只能在单帧完成后聚合，不能替代逐张目验。Leo 或其他来源提供的替换图仍是候选，须保存来源、执行同一套透明/尺寸/基线检查后才能标记 `selected`。

## 4. 按资产类型选择路线

一般角色、换装、武器、UI 和场景任务按各自需求选择最少的参考图，生成后检查内容、尺寸、背景与 alpha，再执行任务允许的确定性加工。以下主路线和修帧模板仅适用于角色动作帧，不自动约束持械敌人、武器素材、换装、UI、场景或新角色。

### 动作帧主路线

以下为已批准序列表任务的模板，不是所有任务一律三帧。若现行任务明确逐张生成或两帧动作，按该任务的帧数与目验停点执行；不得用本模板扩大帧数或批量生成。

```text
Leo 确认三拍动作设计
→ right 三帧序列表母版
→ rightup/rightdown 整表转面
→ 左系确定性镜像
→ 分帧规格化
→ 三帧连播、六向总览、机械门
→ Leo 目验
```

同一单帧的同一手/脚异常若连续三次原生失败，按 §5.1 处理；回退完成并通过目验前，不启动该动作的下一帧，也不把单帧回退扩大成批量换源。

单帧原生编辑只处理 Leo 已指出的局部问题；一次只改一个可观察目标。左右/方向问题优先用 Leo 标注图，不连续改写方位词猜测。

当前口径为：五官、人物比例和规格大小不得变化；动作语义、三拍相位和朝向仍须一致。任务书更严格时，以任务书为准。

## 5. 尝试上限与动作帧异常回退

- 一次生成、图像编辑或原生语义扣图各计一次尝试；本地确定性切帧、镜像、扣纯色底、归一、检测和拼对照不计生成尝试。
- 普通单帧默认最多两次原生尝试：第 1 次给完整候选，第 2 次只修一个明确缺陷；第二次仍不过门就停止该帧及其依赖分支并登记失败。
- 普通上限不授权自行换引擎。只有同一动作单帧、同一手/脚或动作异常已连续三次由 Codex 原生处理仍未解决，且任务上下文已有 Leo 对该条件回退的授权时，才进入 §5.1；这三次必须逐次保留 raw、prompt 和 QA 证据。
- 已被该条件回退授权覆盖的单帧，第三次原生尝试只用于完成这条触发条件；不得做第四次原生尝试，第三次失败后立即进入 §5.1 或停报。

### 5.1 `seedream-5.0-pro` 单图回退（严格例外）

1. 只处理触发异常的那一张目标帧；使用 mxai API 的精确模型 slug `seedream-5.0-pro`（Seedream 5 Pro）单图修正，成本固定 **6 积分/张**。任何其他 Seedream 变体或其他厂商模型均视为违红线。禁止批量提交、禁止把 contact sheet 当输入、禁止顺带生成同动作其他帧。
2. 回退只修已登记的手、脚或动作异常；身份锚、服装、色板、比例、朝向和画布规格继续按原任务冻结。它不是新的设计轮次，也不是无限重摇许可。
3. 在作业包写入 `credits.json`，至少记录 `provider=mxai`、`model=seedream-5.0-pro`、`modelDisplayName=Seedream 5 Pro`、`cost=6`、时间、触发帧、连续原生失败次数、具体异常、输入源 SHA 和输出 SHA；保留三次原生失败的 raw/prompt/QA。
4. 回退结果仍从 `raw/` 开始，执行与原生候选相同的模式、真实 alpha、外围透明、主体连通、尺寸、脚底、质心和命名检查，再进入 `normalized/` 与 `qa/`。成功不等于 release。
5. 必须重新经过 Leo 目验和 PM 规格门；两道门都通过前维持 candidate 状态，不写运行时目录。若 API 不可用、回退结果仍失败或门检失败，停止该帧并如实上报，不再换其他引擎或追加回退。

## 6. 动作修帧提示词骨架

本节只用于既有角色动作帧的局部修正。其他资产按其任务书组织 prompt，不继承这里的“禁止武器”或“必须保持服装”等条款。

```text
【任务】编辑图1中的既有游戏角色素材。
【参考职责】图1=动作与构图真源；图2=人物身份和画风真源；图3=目标朝向真源；图4=唯一允许改动区/方向标注。
【必须保持】五官、脸型、发型发饰、服装结构与配色、头身比例、相机视角、全身尺度、脚位和动作相位。
【本次唯一改动】<一个可观察改动>。
【生产背景】优先真实透明；若透明不可控，使用皮肤包指定的单一纯色隔离底，无渐变、纹理、棋盘格或阴影。
【禁止】武器、文字、水印、地面、投影、粒子、新配饰、额外肢体、重设计动作、改变脸和比例。
```

动作修帧禁用“更自然、更有力量、更精致”等开放词。画质要求写成可核对的断线、描边、噪点和边缘问题。

## 7. 条件扣图

先读取真实尺寸、模式、alpha 极值和四角颜色：

1. 有可用 alpha，外围透明且边缘干净：跳过扣图。
2. 无 alpha，但背景为与角色色板分离的单一纯色：走本地边缘连通域扣图，再做去染与多底衬检查。
3. 白衣、发丝或复杂背景无法确定性分离：最多用一次原生语义扣图；它计一次生成尝试，仍须复查五官、轮廓和动作。
4. 语义扣图重绘主体、仍无 alpha 或超过尝试上限：规格 FAIL，如实报告。

对不透明浅色棋盘背景，优先做画布边缘 flood-fill：只移除与外沿连通、且满足浅色中性背景判定的像素。若处理后出现脱离主体的背景残留，使用 alpha 阈值下最大的主体连通域确定裁框；不得用全图亮度阈值抠除角色浅色部位，也不得用横向压缩补救错误包围框。处理后仍须复验真实 alpha、可见框和主体尺寸。文件门至少记录：模式为 RGBA、alpha 极值同时含 0 与 255、四边外围透明、前景为一个主体连通域、可见框/脚底/中心符合任务规格。角色居中按任务指定算法计算；T45 使用全分辨率逐像素 `alpha > 32` 的前景质心，禁止用 bbox 中点、抽样像素或跳步扫描代替。任务未定算法时同时报告 bbox 中点和全像素前景质心，等待规格方选择，不能只写“已居中”。预览视觉、文件扩展名和“已抠图”描述均不能替代像素检查。

主角大面积青绿且有白衣白裤，隔离底默认候选为 `#FF00FF`；正式使用前对角色色板做距离检查并写入 skin manifest。严禁用全图亮度阈值抠除白衣。

## 8. 四道门

| 门 | 必检项 |
|---|---|
| 身份门 | 五官、脸型、发型发饰、服装结构/配色、头身比 |
| 动作门 | 相位、出手臂、伸屈、出招轴、脚位/重心、跨向同招 |
| 连播门 | 身高、体宽、腰线、衣饰和前后层次无跳变 |
| 文件门 | 任务书尺寸、真实 alpha、主体高度、中心、脚底基线、命名及该资产明确禁止的元素；**确定性加工零副作用**（清杂/抠底/归一/镜像后主体域像素零删除，见下） |

按资产类别只执行适用的门，不适用项标记 N/A 并注明依据。视觉候选与规格结果分开记录：Codex 可描述画面并核对冻结要求，Leo 作审美定稿，PM 作第二道规格门。预览像透明但实际 alpha 全 255 或 `hasAlpha=no` 的文件不过文件门。

### 8.1 交付自证三类证据（2026-09-10 T45 两批实锤）

任何本地确定性加工（清杂、抠底、归一、对齐、镜像）交付时，必须**同时**给出三类证据：

1. **目标达成**：本次要有意达成的可量化结果（例：清除后 `alpha>32`、4 邻接组件数=1）；
2. **改动安全**：副作用为零——对基线做掩膜差分，**主体域删除像素数=0**、被删像素数=目标元素像素数、逐像素 diff 的 RGB 变动=0；
3. **参照一致**：与**基准帧**的相对项（尺度/位置/尺寸），且**对照图必须把基准帧纳入同一张图**。

**只报前两类视为未过门。** 三批实锤：
- 只报①不报② → 清杂削到主体（自报"单连通"却删了本体轮廓）；
- 只报①不报② → 取格错致 6 对帧逐字节相同（自报"29/30 通过"）；
- 只报①②不报③ → **walk 组只有基准的 46%（118 vs 256）却自报 `allHardGatesPass=true`**。

**第③类是"显而易见的错却查不出"的根因**：以上所有检查项都是**输出帧自身**的（尺寸/RGBA/脚底/质心/边缘/连通），**没有任何一项拿基准帧或源图做参照**——所以一帧可以"内在完美"却尺度全错。

**但更根本的一层是：对照图生成了，却没人看。** 本批 contact sheet 里 walk 三帧就排在 atk 四帧旁边，肉眼差 **2.2 倍**（119 vs 268），第一眼就露；上批取格错致 6 对帧逐字节相同，两张一模一样的图并排也在同一张板上。**"生成了对照图"不等于"看过对照图"。**

**故四条同时成立才算过门**：①自检至少一项是与基准的相对量；②对照图必须含基准帧；③**交付前必须人眼过一遍对照图，并在回执里写出画面逐项描述**——至少含"批内各帧大小/姿态是否一致"与"与基准帧的关系"；**只给对照图路径不算交付**；④批内肉眼可见的尺寸/姿态不一致，**不得报绿**（宁可停报，也不要拿"门检全过"盖过去）。

三条配套硬约束：**(a) 判据与门检口径逐字一致**——连通性一律 `alpha>32` + 4 邻接，`alpha>0` 会被 1~15 的微弱光晕假性连通；**(b) 清除以元素（连通域像素集合）为单位**，禁矩形/膨胀框批量清零；**(c) 目标物若在判据下与主体真实相连，它就不是游离点**——停上报，禁强清。

**测法有效性前置**：任何**自动测法**（颜色掩码/区间扫描/连通域统计等）用于定系数或判合格之前，必须先在**已知同尺度的保留帧组**（hero：idle 三向 + cast 9 共 12 张）上自证其读数**波动 ≤5%**；不达标即判该测法不可用、换方法。（实锤：区间扫描窗上限致基准值饱和到窗口上限；颜色掩码取到腰带区非头部；PM2 侧肤色掩码在保留帧上波动 127%。）

清杂步骤级 SOP 与异常码见 [批次收尾与返工定位](references/batch-closeout.md)「清杂」节；对照像素证据落 `qa/`。

## 9. 作业包与状态

```text
assets-pipeline/characters/{role}/{skin}/{action}/{job_id}/
├── request.md
├── refs.json
├── prompts/
├── raw/
├── normalized/
├── qa/
├── contact/
└── job.json
```

作业目录使用任务指定的 job_id。同一 job 已存在时先读取状态并从未完成步骤继续，不因目录存在而另加后缀或覆盖已完成结果；新任务使用新的 Task ID/job_id。

状态用正交字段：

- `artifactStage`: `request | raw | normalized | candidate | release`
- `visualReview`: `unreviewed | selected | rejected`
- `specGate`: `pending | pass | fail`
- `integrationGate`: `not_handed_off | accepted_by_zcode | runtime_verified`

运行时目录只放 release 文件和 `manifest.json`。候选必须同时满足 `visualReview=selected` 与 `specGate=pass` 才能晋级 release；用户口头“可用/可入阵”若未明确替代 PM 规格门，只更新视觉状态。manifest 记录每个选定文件的来源、确定性处理、SHA-256 和门检状态。左系独立 PNG 的 manifest 必须记录 `derivedFrom` 与 `flipX`；左右不对称时按 `mirrorPolicy` 停止裸镜像。

多帧集成、镜像清理或发交付前，读取 [批次收尾与返工定位](references/batch-closeout.md)。其中包含加工/验算分离、精确帧集核账、镜像差分口径和只读交付检查工具。

## 10. Codex → ZCode

1. 详细正文落 `tasks/handoff/`、`tasks/questions/` 或 `tasks/answers/`；
2. 对应 thread 写摘要；`tasks/LOG.md` 写事件索引和文件路径；
3. 形成仓库交付物后，通过 projbus 发送带 `commit_sha` 与 `artifact_paths` 的 delivery；ZCode 回复须回显 Task ID、基线 commit、manifest 版本；
4. 未收到基线 ACK 前，不把 ZCode 侧实现视为已开始或已接受；等待 ACK 不影响 Codex 生产阶段已经完整交付的状态。
5. 共享工作区提交前检查 `git status`，只暂存并提交本任务显式路径；主线含他人并发提交或审查风险时，将本任务 commit 推到 `codex/` 隔离分支供门检，禁止夹带其他人的改动。

## 12. 线程轮换与上下文卫生（2026-09-10 实证新增）

**背景（实测）**：某美术线程连续工作 5 天、472 轮，被 **contextCompaction 压缩 68 次**，会话日志（rollout）涨到 **1.65 GB**。后果两层：①每次压缩有损 → 早先确立的判据与已拍板决策被摘要掉 → 反复"重新推导已经定过的事"（取格映射明明记在已过门 manifest 里仍推错）②rollout 超限后**会话库损坏**：新轮次持久化失败（`failed to project durable rollout … thread-store internal error`）、UI 永久显示"思考中"，且**重启与 resume 都无效**（问题在库里，不在进程里）。

### 12.1 一条线程只服务一个批次

- 批次（或一个大阶段）收尾即执行：**写交接文档 → 开新线程接续**。不要在同一条线程里连续跑多个批次。
- **触发轮换的硬指标**（任一达到即收尾轮换，不等卡死）：
  - 单线程轮次 **≥ 150**
  - rollout 文件 **≥ 300 MB**（路径形如 `~/.codex/sessions/YYYY/MM/DD/rollout-*-<thread>.jsonl`）
  - `contextCompaction` 条目 **≥ 30 次**
- **交接文档最小集**（落 `tasks/handoff/`）：①当前批次与范围 ②已定口径及其来源（任务单/打回单 seq、commit、manifest 版本）③未完成项与停点 ④禁碰区。新线程开工先读该文档 + 本 SKILL + 对应任务书。

### 12.2 上下文卫生：程序化检查优先，图按需单张读

- **能出指标表的就不要把图读进上下文**：尺寸/质心/连通域/差分/尺度比较等一律用脚本出数（本 SKILL §8.1 三类证据即为此）。
- **contact sheet 每批只读一张**——它是"一张图含全批"，已是最省的形式；**禁止**把批内单帧逐个读进上下文。
- 图只在**必须目验**时读（红线 15 要求的"人眼过图"），且一次一张、按需。
- **依据**：实测该线程 `imageView` 达 **1422 次**、`imageGeneration` 250 次、`reasoning` 7420 条——图片与推理块是 rollout 膨胀的主力，也是压缩频繁的诱因。

### 12.3 一句话

**规则要落文件、判据要机械可算；不要依赖"会话记得"。** 会话会压缩、会衰减、最终会损坏；仓库不会。
