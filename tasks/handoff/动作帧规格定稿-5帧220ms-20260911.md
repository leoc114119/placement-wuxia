## 三、关键帧怎么挑的（不是均匀抽样）

**用贪心最远点采样**（`tools/glb2d/select_keyframes.py`）：

```
① 必留首帧与末帧
② 每次新增「到已选集合的最小距离」最大的那帧
距离 = alpha 形状差 + 0.35 × RGB 颜色差
```

**为什么不用「均匀每 N 帧取一张」**：那样会漏掉动作的**极值帧**（下蹲最低点、腾空最高点）——恰好是动作最有表现力的两帧。

**实测覆盖度**（26 帧源 → 选 K 帧，数值越小覆盖越好）：

| K | 选中源帧 | 平均距离 |
|---|---|---|
| 3 | 0, 12, 25 | 8448 |
| **5** | **0, 12, 14, 18, 25** | **6816** |
| 8 | 0,5,10,12,14,16,18,25 | 4359 |

## 四、速度必须按「源时长」反推（本轮踩过的坑）

**我犯的错**：源动作 26 帧 @30fps = **833ms**，我压成 5 帧却只给 110ms/帧（总 550ms）→ **等于偷偷快放了 1.5 倍**。Leo 指出「gif 有点太快了」。

**规范（此后一律执行）**：
```
每帧时长 = 源动作时长 ÷ 帧数          （等时长档）
若观感偏快/偏慢，再在此基础上微调，并记录调整理由
```
本例：833 ÷ 5 ≈ 167ms（等时长档）；Leo 选 **220ms**（略慢于原速，手绘观感更稳）。

## 五、包体口径纠正（我此前算错了）

**我错用「微信主包 4MB」来限制帧数**。项目文档原文：

> 「六向全量不能长期按当前主包一次性预解码。**分包/CDN、按场景加载与 LRU 应另立资源工程卡**」

**结论**：
- **动作帧走分包/CDN，不进主包** —— 帧数不受 4MB 约束；
- 项目已定的 **PNG-8 + 图集** 方案特别适配本管线（渲出来仅 17~100 色），单帧可从 300KB（裸 RGBA）压到约 10~15KB。
