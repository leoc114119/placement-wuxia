# 研发 PM 交接：如何后台通知主架构（Codex arch）· 2026-09-11 · PM2

> **给研发 PM**：你要主架构出技术方案 / 做技术验收 / 答疑 / 解释规则时，**用本文的命令**。
> 已实测跑通（含一次 bug 修复），照抄即可。

---

## 一、一句话

```bash
scripts/notify_arch.sh <payload.json> <幂等键> [kind]
```

**它会做三件事**：发 projbus 消息（rd → arch）→ **立即命令行唤醒** arch 线程 → 打印 arch 状态。

---

## 二、为什么需要这个脚本（不能只发消息）

| 方向 | 能否秒级唤醒 | 原因 |
|---|---|---|
| **ZCode → Codex** | ✅ **能** | Codex 侧有对外 CLI（`codex queue`） |
| Codex → ZCode | ❌ 不能 | ZCode 无对外 CLI，只能定时巡检（10 分钟） |

**所以「你要 arch 干活」必须走本脚本主动唤醒**——只发消息，对方要等它自己轮询才看到。

---

## 三、怎么用（三步）

### 第 1 步：写 payload（JSON）

```json
{
  "subject": "一句话标题",
  "detail":  "正文/背景",
  "ask":     "需要主架构给什么（方案/验收/答疑）",
  "refs":    ["相关文档路径或 commit"]
}
```

**真实示例**（战斗行走帧换 run）：

```bash
cat > /tmp/q.json <<'JSON'
{
  "subject": "战斗行走帧换 run 素材，请出接入方案",
  "detail": "现有 walk 2 帧太慢，Leo 裁定战斗内移动改用 run 素材（5 帧）。素材已交付：assets/_trial_20260911/glb2d_v2/mixamo/run_6dir/（30 张，PNG-8 无损，240×320）。",
  "ask": "请给接入方案：①clipCounts 怎么配 ②帧时长怎么定（现 walkFrameMs=140，5帧×140ms=700ms，而 run 源 1292ms）③是否覆盖 walk 文件（W1）还是新增 run clip（W2）",
  "refs": ["tasks/handoff/接入需求-jump-1帧改5帧-20260911.md"]
}
JSON
```

### 第 2 步：发 + 唤醒

```bash
scripts/notify_arch.sh /tmp/q.json "walk-to-run-20260911" question
```

**幂等键**（第 2 个参数）：同 `(项目, 收件人, 键)` 重复发送只入库一条——**换个键就发新的**。建议用「主题-日期」命名。

**kind 取值**（第 3 个参数，默认 `question`）：
`question`（提问/要方案）｜`answer`（答复）｜`delivery`（交付）｜`acceptance`（验收结论）

### 第 3 步：看结果

脚本末尾会打印：

```
role=arch thread=01a0705a-013a-7f40-992e-cb16cd97ddd1
watermark=366 近一小时唤醒次数=2/6
水位线之后的新消息=0
是否在跑=False
```

- **`水位线之后的新消息=0`** = 已投递成功（水位线已推进）
- **`是否在跑=True`** = arch 正在处理

## 四、必须知道的三个坑（我已踩过）

### ① 只发消息不唤醒 = 对方看不到

projbus 是**信箱**，不是推送。**必须跟 `codex queue` 唤醒**（脚本已封装）。

### ② 唤醒有每小时上限

默认 **6 次/小时**。**人工派单加 `--force` 跳过上限**（脚本已加）。

### ③ 唤醒≠免除停点

消息若要求对方「停下等裁定」，它仍应停下。**唤醒只是让它看到消息，不代表可以越权执行。**

---

## 五、本次修复的一个真实 bug（供了解）

**通知链路原本只能服务一个角色**——状态文件 `~/.codex/projbus-drive-state.json` 只存单个 `role/thread`，配了 `arch` 会覆盖 `art`。

**已修**：状态改为多角色结构 `{"roles": {"art": {...}, "arch": {...}}}`，**每个角色独立线程/水位线/限频**；旧文件自动迁移。

**验证结果**：
- `--role art` → 线程 `01a08a45…`、水位线 362（**不受影响**）
- `--role arch` → 线程 `01a0705a…`、水位线 366（**独立**）

> 若你看到别人用旧命令报 `FATAL swallowed: watermark_seq` —— 那是修复前的残留，已解决。
