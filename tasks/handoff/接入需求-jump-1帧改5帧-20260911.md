## 一、为什么改（一句话）

现有 hero 的 `jump` 是 **1 帧**（Leo 09-06 裁定「只留腾空帧」）。现在**有了真实的多帧跳跃素材**（起跳→上升→腾空→落地），希望**用起来**——让跳跃有过程，不再是单帧瞬移。

### ③ `ui/battle-hex-render.ts:970-972` —— 选帧逻辑：单帧 → 按演出钟循环

```ts
// 现状（写死 ordinal 1）
if (ma.hopHeight > 0 || actor.isJump) {
  return { clip: 'jump', ordinal: 1 };
}
// 建议（与 walk 同构：沿演出钟在 1..5 间推进，播完保持尾帧）

}
```

## 三、⚠️ 一处必须研发拍板的冲突：帧时长 vs 跳跃时长

**实测到的矛盾**：

| | 值 |
|---|---|
| 现有跳跃演出时长 | `JUMP.baseDuration = 0.6s`（`config/battle-hex.ts:62`，基准 2 格；每超 1 格 +0.15s） |
| 我们定稿的帧播放速度 | **220ms/帧**（Leo 09-11 拍板，5 帧 = **1.1s**） |

**1.1s > 0.6s → 5 帧按 220ms 播，会超出跳跃演出时长。**

**注意区分两个概念**（我第一次看也混淆了）：
- **220ms/帧** 是**我们预览 GIF 的播放速度**（Leo 用它判断观感）；
- **游戏内**帧是由**跳跃演出时钟**驱动的（`ma.t / jumpFrameMs`），不由素材决定。

**所以游戏内怎么分布，请研发定**，两个可行方向：

| 方案 | 做法 | 效果 |
|---|---|---|
| **A. 按演出时长均分**（推荐） | `jumpFrameMs = ma.duration × 1000 / 5`，5 帧铺满整段跳跃 | 与现有 0.6s 跳跃时长**完全兼容**，不用改任何时长参数；2 格跳下每帧 120ms |
| **B. 改跳跃时长以匹配 220ms/帧** | 把 `baseDuration` 提到 ~1.1s | 跳跃变慢，**会改动战斗手感**，需 Leo 单独拍板 |

**PM2 建议 A** —— 不动战斗手感，帧数只是把过程铺开。

## 四、素材交付（我这边负责）

- **格式**：240×320 RGBA PNG（**与现有 battle45 帧完全同规格**，已实测）
- **命名**：`jump_{facing}_1.png` ~ `jump_{facing}_5.png`
- **帧序**（Leo 审定）：
  | 序号 | 内容 |
  |---|---|
  | 1 | 站立 |
  | 2 | 起跳（最低点） |
  | 3 | 上升 |

- **体积**：5 帧 ≈ **193KB**（现有同规格单帧均值 64.9KB，我们更小）；转 PNG-8 可到 ~10KB/帧

## 附：本批素材的技术背景（供参考）

- 来源：Mixamo `Jumping Up` 动作（Collada）→ 我们自研重定向器 → 本模型 3D 渲染 → 2D 帧
- 工具：`tools/glb2d/`（`collada2anim.mjs` 重定向 + `render.mjs` 渲染 + `postprocess.mjs` 描边量化 + `select_keyframes.py` 选关键帧）
- 全程本地、**0 积分**
- **已知局限**：源动作**没有下降段**（停在最高点），本批的「落地」是重排凑的；**后续会找含完整落地的动作替换**，届时帧序可能微调（版本会 bump）
