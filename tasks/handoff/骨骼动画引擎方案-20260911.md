# 骨骼动画引擎方案（Leo 2026-09-11 决策）· 从"逐帧拼接"改为"骨骼驱动"

**Leo 的判断**：「一个一个画面帧合并很麻烦，流程解决不了，所以我需要一个能做骨骼动作的引擎来解决」——**PM2 认同，且这是本日最有价值的判断**。

---

## 一、为什么这次换引擎是对的（与之前的区别）

| | 之前我反对换引擎的理由 | 你现在要解决的事 |
|---|---|---|
| 目标 | "让画面更好看" | **"不再逐帧拼接"** |
| 引擎的作用 | 不画画，救不了画质 | **骨骼驱动＝换掉"逐帧"这个生产方式本身** |

**我之前的分析错在**：把"引擎"和"素材生产"当成两件事。**实际上"骨骼动画"是一种素材形态**——一旦角色是骨骼装配的，"动作"就不再是 N 张图，而是**一组骨骼变换**。**这从根本上取消了"逐帧对齐/比例/抠图/换手"这一整类问题**：

| 逐帧拼接的痛点 | 骨骼驱动下 |
|---|---|
| 比例漂移（BUG-12） | **不存在**——同一套骨骼，尺度天然一致 |
| 抠图/清杂 | **大幅减少**——只需切分部件，不用逐帧抠 |
| **换手画不出来（12 次全败）** | **不存在**——换手＝移动一根骨头，100% 确定 |
| 动作加帧（2 帧→4 帧） | **不存在**——调时间轴即可 |
| 一天 48 批次 0 交付 | 动作是**数据**，可版本化、可复用、可批量 |

**这就是"一劳永逸"的正解**——不是把逐帧流程做得更快，而是**不再逐帧**。

## 二、技术路径（已核实的事实）

### 2.1 引擎选择：**Cocos Creator**（推荐）

| 项 | 事实（来源：Cocos 官方文档） |
|---|---|
| **骨骼动画支持** | ✅ **Spine** + **DragonBones** 两类资产均支持 |
| **运行时驱动** | ✅ 有 `SkeletalAnimation` 组件；支持**预烘焙**与**实时计算**两种模式，可运行时切换 |
| **微信小游戏** | ✅ **官方有 "Publish to WeChat Mini Games" 发布目标** |
| **微信官方适配** | ✅ 微信小游戏官方文档把 **Cocos** 列在适配清单首位 |

**为什么选 Cocos 而非 Laya/Egret**：①微信官方适配清单首位 ②骨骼动画双格式支持 ③生态与文档最成熟。

### 2.2 骨骼动画制作工具

| 工具 | 成本 | 说明 |
|---|---|---|
| **Spine** | **Essential $69**（促销价，原 $99）/ Professional $379 | 行业标准；试用版免费可评估；**按用户数授权** |
| **DragonBones** | **免费** | Cocos 原生支持，国产，曾是主流（维护状态需确认） |

**建议**：先用 **DragonBones（免费）** 或 **Spine 试用版**做技术验证，**确认管线跑通后再决定是否采购 Spine**。

### 2.3 素材生产（关键：AI 仍然有用，且用法更简单）

**骨骼动画需要的素材形态变了**：

| | 逐帧方案 | 骨骼方案 |
|---|---|---|
| 需要什么 | **每个动作每一帧**一张完整图 | **一个角色一套部件**（头/躯干/上臂/前臂/手/腿/脚） |
| AI 出图量 | 动作数 × 帧数（如 12 动作 × 3 帧 = 36 张） | **1 套部件**（约 10~15 个部件） |
| AI 难点 | 跨帧一致、换手、比例 | **只需切分准确**（不需跨帧一致！） |

**这是最大的好消息**：骨骼方案下，**AI 只需"画好一个角色、切对部件"**——**跨帧一致性问题被彻底绕开**（因为动作由骨骼产生，不靠 AI 画）。

## 三、代价（必须如实说）

| 项 | 代价 |
|---|---|
| **现有代码** | **6346 行全重写**（ui / systems / config / net）——渲染方式从"画 PNG 帧"变成"驱动骨骼" |

| **云函数** | **不受影响**（后端结算逻辑独立） |

| **风险** | ⚠️ **"纸片人感"**——切件动画的关节处可能露接缝、旋转像贴纸，**必须先做观感验证** |

## 四、建议的验证顺序（先小后大，控制风险）

### 第 1 步：**观感验证**（最关键，成本最低）
**只做一件事**：拿现有英雄帧，切成部件，用 Spine/DragonBones 或 Cocos 装配，做**一个出拳动作**。
**验证目标**：① 观感能不能接受（有没有纸片人感）② 换手能不能做到 ③ 骨骼动画在本项目的画风下好不好看。
- 成本：工具免费（DragonBones/Spine 试用）+ 现有素材；
- **这一步过了，才值得投入重写**。

### 第 2 步：**微信小游戏打通**
用 Cocos 做一个最小 demo，发布到微信小游戏，验证：
- 骨骼动画在小游戏环境能否正常运行；
- 性能（1v多、240×320 画布）；
- 资源包体积（微信小游戏有 4MB 主包限制，需确认骨骼资源可行性）。

### 第 3 步：**架构迁移评估**
前两步过了，再让研发线评估"6346 行迁移到 Cocos"的具体方案（哪些能复用、哪些重写、分几期）。

## 五、PM2 的明确建议

**按第 1→2→3 步走，不要直接重写。** 理由：

1. **第 1 步是"生死判据"**——如果观感不能接受（纸片人感重），**后面全部白做**。这一步成本几乎为零，却能决定整个决策；
2. **第 2 步验"能不能用"**——微信小游戏的限制（包体积/性能）可能在 Cocos 骨骼动画上有**具体约束**，不验证就重写是赌博；
3. **第 3 步才谈成本**——前两步过了，迁移就是**值得的投资**而非冒险。

## 六、与"确定性管线"方案的关系（不是二选一）

| 方案 | 解决 | 何时用 |
|---|---|---|
| **确定性管线**（今天已出方案） | 逐帧流程的**比例/抠图/门检**问题 | **过渡期仍需**（骨骼方案落地前，现有帧表还要用） |
| **骨骼引擎**（本方案） | **取消逐帧**这个生产方式本身 | **长期正解** |

**两者不冲突**：管线让"过渡期不再一天烧掉"，骨骼让"过渡期尽快结束"。
