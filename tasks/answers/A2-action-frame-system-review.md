## 一、§五 FE 六问逐条意见

### Q1 帧表数据结构：四维索引与换装切换

**结论**：现有 `ANIM_FRAMES`（animState→帧号）+ spriteKey 一维帧数组**不支持**四维索引，需升维重构；换装切换 = **换帧表指针**（预载完成后原子替换），不是逐帧重载。

**理由**：
- F1/F2：帧表组织是「每 spriteKey 一个平铺帧数组 + animState 查帧号 + facing 运行时翻转」，方向不是帧表维度——六向帧接入本身就必须先把「方向」升为查表键，正好与「角色/服装」两维一起做，一次契约冻结到位，避免二次返工。
- 换装若做成"逐帧重载"会产生加载中间态闪烁与半旧半新混播；指针替换是全有或全无，切换瞬间干净。

**建议**（落码归 T45 接线卡/战斗实装卡，本次零代码）：
1. 帧表键升为两段：`assets.frames: Map<`${roleId}/${skinId}`, FrameTable>`，其中 `FrameTable = Record<`${action}_${dir}`, WxImage[]>`——四维=role×skin 进 Map 键、action×dir 进 Record 键，查一次 `actor` 身上的 roleId/skinId/朝向即得帧。
2. `ANIM_FRAMES` 的 animState→帧组播报语义保留（组内单播/组间不跨铁律不变），仅把「帧号」泛化为「帧引用」，方向维度由快照朝向（见 Q6/风险 R3）参与选组。
3. 换装切换流程：家场景/战前菜单确认换装 → 后台预载目标皮肤整套（loading 态，现 loadBattleAssets 预载钩子同模式）→ 完成后原子换指针；战斗内不换装（MVP 无此需求，不为变身类需求预留）。同时驻留皮肤 ≤2 套（现装+新装），旧表 LRU 释放（见 R1）。

### Q2 palette swap 实现层

**结论**：**运行时换色**（加载期 offscreen canvas 一次性像素替换 + 结果缓存）为主，**禁止预生成换色 PNG 入包**；shader 路线不存在（Canvas 2D 无自定义着色器）。

**理由**：
- 预生成入包 = 每变体 +72~90 帧 ≈ +3.7~4.7MB（F5），一个变体就把主包额度吃穿，与 F7 主包 4MB 红线直接冲突；且变体矩阵是乘法增长，包体路线不可持续。远程 CDN 预生成可绕开包体，但每个变体多一次下载管理对象，不如运行时换色一份源图多套色。
- 运行时换色成本：240×320 单帧像素循环 <2ms，敌型全套 72 帧分帧异步处理 <200ms（加载页期间无感），完全可接受。
- 实现路径（微信 Canvas 2D 唯一可行）：`wx.createOffscreenCanvas({type:'2d'}) → drawImage(源帧) → getImageData → 按 palette manifest 替换 → putImageData`，产出 offscreen canvas 直接作 drawImage 源。

**建议**：
1. 管线侧 palette swap 脚本（§六-5）的产出物定为 **palette manifest**（源色→目标色精确 RGB 映射表 + 换色区域蒙版），而非换色成品 PNG；同一 manifest 双端复用（脚本离线出 Leo 目验对照图，FE 运行时按同一表换色），避免"预览≠运行时结果"。
2. **抗锯齿边缘坑必须防**：像素画边缘半透明像素的 RGB ≠ 调色板纯色，纯精确匹配会漏边/脏边。对策（按优先序）：manifest 附服装区域蒙版图（美术管线顺手产）+ 蒙版内色距容差匹配 > 纯色距容差 > 全帧调色板量化（改画风，不建议）。
3. 变体内存账要心里有数：**palette 变体省包体不省解码内存**——每个变体是一份独立换色位图驻留（≈21.6MB/敌型变体，F5 口径 72 帧）。建议同屏变体敌型 ≤2，超出用 HUD 血条/名字色区分。
4. 真机兼容 spike 先行（见 R5）：offscreen canvas getImageData 在部分基础库版本/安卓机型有差异，§六-5 开工前先出真机验证小卡。

### Q3 包体与加载

**结论**：主角一套 90 帧实测口径 ≈4.7MB（52KB/张）**单角色即超主包 4MB**，分包只能解 MVP 一时；**远程 CDN + 本地缓存是必然主路线**，且基建必须先于第一套换装/第二个角色交付立项。

**理由**（按 F5/F7 测算）：
- 主包 4MB：连 hero 一套都装不下，主包只能留代码 + UI 小图 + 兜底占位。
- 分包 30MB 总额：hero 90 帧 4.7MB + 山贼系 72 帧×N 型 + 每套服装 54~108 帧（2.8~5.6MB）——服装矩阵是线性膨胀的，30MB 撑不了几套，分包只适合承载"MVP 首发必需的角色帧表"。
- 远程资源不占包体，但要下载器/缓存/版本失效/失败降级四件套，这些是研发基建，不是美术管线能自带的。

**建议**：
1. 分层策略：**主包** = 代码 + UI 组件图 + 占位兜底（drawPieces 已有剪影降级，F8 同款）；**战斗分包** = 首发角色/敌型帧表（进战斗前加载，已有 loadBattleAssets 预载钩子承接）；**远程 CDN** = 换装套/变体 manifest/后续新角色（wx.downloadFile + FileSystemManager 本地缓存，版本号防缓存——沿用 `BATTLE_HEX_RES.ver` 模式）。
2. 加载器扩展卡（研发侧）：`ui/assets.ts` loadImage 现仅支持包内路径（F4），需扩「包内/远程/本地缓存」三态源 + 失败降级占位——建议与 T45 接线卡合并排期，排在第一套换装生产完成之前。
3. 报告 §5.3 的帧量估算口径微调：47KB/张是 13 张旧样本，35 张实测 51.8KB/张，90 帧 ≈4.65MB——结论不变（超限），预算口径建议按 52KB 更新，留 10% 余量。

### Q4 渲染性能

**结论**：**性能不是瓶颈，包体与解码内存才是**。Canvas 2D 下 drawImage 开销极低，六向接入是查表变更零额外绘制；未来 paperdoll 多层叠加在同屏 ≤7 棋子规模下也无压力。

**理由**：现网每帧绘制 = ≤7 棋子 ×1 层 drawImage + HUD；武器硬分层后 = ×2 层 ≤14 次 drawImage；即便未来 paperdoll 三层（身体/服装/武器）= 21 次/帧——Canvas 2D 千级 draw call 才需要谈合并优化，21 次完全无感。真正要管的是 F5 的解码位图内存（见 R1）。

**建议**：报告相关章节可明确"渲染性能无约束"以止住不必要的担忧；研发侧把注意力放在内存驻留策略（R1）与加载态体验（Q3）上。

### Q5 武器锚点标定工作流

**结论**：美术出图附 manifest json → 研发誊录常量表的工作流**可行且已定**（A1-T45 ③），补四点强化。

**建议**：
1. manifest schema 先冻结：帧画布基准 240×320 art-px、每帧 `{x, y, angle?}`（angle 默认冻结垂向右下、出招跟手不转，例外帧显式写）、外加帧清单/版本号——schema 进 T45 接线卡需求表，冻结后才开工（契约先行）。
2. 誊录对表脚本化：`scripts/` 加 manifest vs 常量表逐帧 diff 脚本，进接线卡 DoD（A1-T45 ③ 遗留挂账 #3 的落地形态）——人眼誊录必漂移，diff 门是唯一防线。
3. 美术侧标定工具建议 PIL 点选脚本（点手心出坐标自动生成 json），比手写 json 稳；此为管线侧优化项，落 §六 清单时可挂到 §六-5 同一工具卡。
4. 锚点数量预留：每帧武器挂点 1 个起步，manifest 结构预留挂点数组位（双手/特效挂点未来扩，不改 schema 不迁移）。

### Q6 动作帧接口预留（hit/dead/PvP）

**结论**：**hit 不产帧**（维持事件驱动方案）；**dead 复用 die_{dir} 帧组**；**PvP 对手=主角系帧表无结构影响**，但阵营色区分依赖 palette 维度——role/skin/palette 三段键现在冻结。

**理由与建议**：
1. hit：T21 事件驱动反馈（震动/冒字/红闪）已交付且休眠钩子语义明确（F10），六向体系下受击继续复用当前向当前帧 + 程序反馈，不新增受击帧——省 18 帧/角色 ≈1MB 包体 + 一整套生产成本。
2. dead：需要 die_{dir} 各向帧（倒地有方向感）；MVP 可先统一 die_down（俯视 Q 版下倒地方向感弱），是否补向归 Leo 目验拍板——数据结构按 die_{dir} 全键预留，缺向回退 die_down。
3. PvP/未来主角系敌人：数据结构 role_id 键控天然支持（spriteKey 已泛化，F1），无结构改动；唯一增量 = 同 role_id 需区分阵营 → palette_id 维度（敌我同模不同色），与 Q2 的 palette manifest 正好咬合。**三段键 `role/skin/palette` 一次冻结进 types.ts**，避免 PvP 立项时二次改契约。

## 二、§三 复用模型评审（动作模板库 × 角色皮肤包）

**结论**：解耦模型**成立**，且报告最关键的认知（"可复用的是设计+流程+prompt 骨架，生成产物不可跨角色直接复用"）判断正确、诚实——FE 只消费产物，与模板库无耦合，模型对 FE 端零负担。目录约定 `assets/characters/{role_id}/battle45/{action}_{dir}_{n}.png` **基本够用但缺两维**，建议趁资产量小立即升为四层。

**理由与建议**：
1. 现状已是双轨（F6）：hero 走 `assets/characters/hero/battle45/`，enemy 走工作目录形态 `assets/characters/enemy/shanzei_{a,b}/`（含 raw/gen/cut/frames 管线产物），现役敌帧又在旧 `assets/ui/frames/battle/` 小表。三处口径不收敛，越晚统一迁移成本越高。
2. 建议冻结约定（与 Q1 帧表键同构）：
   - 现役帧表：`assets/characters/{role_id}/{skin_id}/battle45/{action}_{dir}_{n}.png`，`skin_id` ∈ base/c01/c02…（hero 现目录一次 `git mv` 到 `hero/base/battle45` 即完成迁移，现在是一个目录的事，一年后是一百个）；
   - 每皮肤一份 `manifest.json`（帧清单/帧尺寸/锚点/palette/动作词表映射/版本号）——FE 接线与誊录的唯一对表物（Q5/F9），也是资源外置铁律"路径唯一出处=配置表"的载体；
   - palette 变体**不占目录**（manifest 派生，Q2）；
   - 管线工作目录（raw/gen/prompts）与现役帧表分树存放（建议 `assets-pipeline/` 或目录内约定归档层），现役树只放成品——FE 路径表不该扫到中间产物。
3. 动作词表统一：帧命名 atk/walk/cast/jump/die/idle 与 `ANIM_FRAMES` 组名（idle/walk/charge/strike/basic/hit/dead）是两套词表，映射关系写进 manifest（如 basic→atk），FE 常量表按映射生成，禁双处硬编码。

## 三、§四 换装三轨制评审

**结论**：三轨制方向**正确**（武器硬分层已定不重议；palette swap 定变体辅轨合理）；**换装 AI 换皮主轨附两条硬约束 + 一条定案建议**；§4.3.2「代表性帧换皮」**明确建议：不裁剪，全帧换皮**。

**理由与建议**：
1. **换皮单位必须是序列表（整表 img2img），禁逐帧独立换皮**——报告 §4.2 写"逐帧 img2img"未明确单位，这是试点 P1 教训（逐帧独立生成帧间不连贯）的直接复刻风险：换皮同样有帧间连贯问题（服装褶皱/摆动轨迹/描边粗细跨帧一致），必须以母版表/转面表为单位整表换皮，继承帧间几何对位。建议写进 SOP（§六-6 换装管线）作为铁律。
2. **画风漂移风险真实存在，防线=参照链+门检**：换皮帧与原帧的差异（色阶/描边/渲染风格）在混播时会放大。对策：换皮主输入=原帧本身（报告已定"原图=现有动作帧"，正确，保持）+ 换皮帧与原帧的结构 diff 门检（体宽/高度门沿用）+ 每套换装出六向总览图过 Leo 目验（与普攻六向同标准）。
3. **§4.3.2 代表性帧换皮——不裁剪（定案建议）**。从帧动画连续性角度：3 帧连播 140ms/帧（walkFrameMs 口径），帧间服装元素（袖摆/衣摆/配饰）在动作中有连续位移，若仅代表帧换皮、其余帧"继承"，相邻帧间配饰/衣纹会跳变——这不是静态画风差异，是**每拍一次的高频闪烁**，比换皮整体画风漂移刺眼得多（外部调研 §2.2 引的"闪烁稳定化"三大件正是此坑）。且"继承帧"与"换皮帧"混播=新旧服装逐帧交替出现，视觉上是服装穿了又脱。降本走 §4.3.1 分档（换色/换饰/换款）+ §4.3.3 方向继承（右系实绘+左系镜像，108→54 帧）已经把全款成本减半，足够。
4. **服装 ID 目录膨胀：可控，前提是走远程**。每套 54~108 帧（2.8~5.6MB）按 Q3 分层走 CDN 不占包体；目录数量本身无技术约束（manifest 索引）。真正的膨胀风险在**目验/门检工作量随套数线性涨**（见 R6），门检自动化必须先于第一套换装落地。
5. **换皮×武器锚点联动风险**（报告未提，见 R4）：锚点按原帧手位标定，换皮若手部像素漂移则武器脱节——换皮 prompt 冻结「手部/持械区零改动」+ 手部区域像素 diff 门检，锚点表 per-skin 校验。

## 四、§1.4 SOP v2 与 §六 规范/skill 优化：研发协作角度补充

**结论**：SOP v2 流程链完整（设计先行→母版→转面→修正→镜像），从消费端看**缺一块关键交付界面：美术产出物→FE 接线卡之间的交付物规格**；§六 7 项全为美术侧落点，**缺研发侧承接项**——§五 六问的答案会悬空。

**建议**：
1. **交付物规格四件套**写进 SOP v2 尾段 + 任务书模板（§六-1/§六-4 落点）：每批帧表交付必须含——①帧 PNG（命名/240×320/透明底/网格对齐）②manifest.json（帧清单+锚点+palette+动作映射+版本，Q5/Q2/§二-2 三处要求的合集，一份文件三处消费）③六向总览预览图（Leo 已验标记随图）④门检记录（尺寸/体宽/左右臂 checklist 结果）。**缺 manifest = FE 无从接线**（誊录制 F9 的前提），这条要当交付硬门槛而不是可选项。
2. **§六 增补第 8 项（研发侧承接卡）**：types.ts 契约冻结（role/skin/palette 三段键 + BattleFacing 六向化，Q1/Q6/R3）+ 加载器三态源扩展（Q3）+ 帧表 LRU/释放（R1）+ manifest→常量表誊录 diff 脚本（Q5）。不补此项，§五 六问只是问答没有落点。
3. 版本与缓存失效：远程资源沿用 `BATTLE_HEX_RES.ver` 版本号模式（URL 参数），SOP 明确"换皮返工重交 → ver bump → FE 缓存自动失效"——返工重交是常态，缓存失效链路要在第一套远程资源上线前定死。

## 五、成本模型复核（§1.3 / §3.2）

**结论**：**量级合理、可作拍板依据**；漏 4 项成本（2 项一次性、2 项系统性），另 1 处口径不一致需统一。

**复核明细**：
- §1.3 边际成本 8~14 分/动作/角色：核算自洽（母版 2 + 转面 4 + 修正余量单侧 2~4），与试点实证吻合，**认可**。首套 28 分含 24 分探索损耗的归因诚实，认可。
- §3.2 主角 40~70 分 = 5 动作 × 8~14，**自洽**；敌人 72 帧 32~56 分同口径，**自洽但漏项**（见下）。
- 漏项 1（一次性）：**新敌型/新角色的皮肤包首建成本未计**——各向待机锚三件套、体型设定、首套门检口径调试，首敌实际成本会高于区间上沿（首套学费同理），建议 §3.2 备注列明"不含皮肤包首建"。
- 漏项 2（系统性）：**palette swap"≈0 分"只计生成成本**——palette manifest 制作校对 + FE 运行时换色改造 + 真机 spike 是研发工时卡，总账视角应单列（美术分账可为 0，项目分账不为 0）。
- 漏项 3（系统性）：**远程资源/分包基建**（下载器/缓存/降级，Q3）不在任何成本表——属研发分账，但它是换装体系的前置依赖，建议 §六-8 卡（本评审 §四-2）带预算 Estimate。
- 漏项 4（小）：换装 216 分/套未含服装设计稿 Leo 过目轮次与换皮帧门检/目验轮次的软成本；动作帧数按恒 3 帧估算（die 实际 1~2 帧、jump 2~3 帧）偏差有限可接受。
- 口径不一致：§4.2 按每向 18 帧×6 向=108 帧/套，§5.3 按 5 动作=90 帧——差异=idle 是否计入动作数。两处预算差 2×18 帧×2 分=72 分，**拍板前统一**（建议按 90+idle 18=108 的明细写法，两处自然对齐）。
- 小注：§1.3"2 分≈0.28 元"的分→元换算基准未注明，供 Leo 读数时补注。
