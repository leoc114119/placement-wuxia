# 执行前流程检查单（PRE-FLIGHT · 2026-09-07 立）

> 触发时机：**每次派发研发/美术任务卡之前**、**每次交付合并 main 之前**，逐项打勾后才动手。
> 本单源起：09-07 出招速度战役"L 环过了就 merge main、跳过主架构验收"的顺序违规——铁律没被违反，是被**顺序**漏掉的。
> 用法：执行者（PM 或代理）在产出文档/交付回执中附"检查单已过"字样与逐项 ✓；发现任何一项 ✗ = 停，先补齐该项再继续。

## A. 派单前（发任务卡/派代理前）

- [ ] A1 **需求文档已定稿**：有需求文档（或规格条目/任务卡需求表），模糊点已逐个向 Leo 确认，零自填
- [ ] A2 **语义级变更已走链**：新语义/已验收行为改动 → 主架构方案先行 → Leo 拍板 → 才发卡（参数级可 PM 背书，但须声明）
- [ ] A3 **文件面已核对**：改哪些文件列清了；与他人在飞卡同核心文件 = 串行不并行
- [ ] A4 **基座陈述已核 git 事实**：工单里写的"某分支已含某代码/某文档"逐条 `git log/ls-tree` 核实过（09-07 Q1 教训）
- [ ] A5 **执行代理档位确认**：子代理模型档位与任务量级匹配（20M tokens 事故教训）
- [ ] A6 **真源版本号写入卡面**：需求文档版本/方案版本/commit SHA 引用明确（防施工读到旧版）

## B. 交付/合并前（commit 进 main 之前）

- [ ] B1 **四门原文齐**：typecheck/lint/build 三零 + test:battle 全绿 + behavior 14/14（+shot/e2e/DBG 视卡面）
- [ ] B2 **主架构技术验收 PASS 已取得**（书面结论，不是"应该没问题"）——**L 环通过 ≠ 可跳过此步**
- [ ] B3 **PM 纯净态复验已做**（checkout 干净分支复跑，或明确声明本轮豁免理由并记录）
- [ ] B4 **Leo L 环验收通过**（功能面验收；与 B2 是两道独立的门，**顺序=B2 在 B4 前完成、合并前两者都须在案**）
- [ ] B5 **归档顺序正确**：B1→B2→B3→B4 全 ✓ 才 merge main；shared worktree 下 merge 走临时分支+push refspec。**硬保证：push main 会被 .zcode 钩子拦截——先在 tasks/.preflight-log 追加一行「<日期> PRE-FLIGHT B1-B6 已过 checked by <事由>」方可通过**
- [ ] B6 **LOG 双写+收官记忆**：threads 交付行 + LOG 一行 + 关键裁定进记忆

## C. 每次 git 操作前（日常）

- [ ] C1 `git branch --show-current` 在预期分支
- [ ] C2 `git worktree list` 无他人活跃占用冲突；main 被占 = push refspec 或等 merge
- [ ] C3 路径级 commit（显式路径），不夹带他人未提交文件
